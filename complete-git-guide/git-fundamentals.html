Section 1 · Introduction

Git vs GitHub

They're two different things. Git is a program on your computer; GitHub is a website that hosts copies of Git repositories.

  • Git is a distributed version-control system. In plain words, it tracks every change to the files in a folder (a repository), so you can go back to any earlier version. No more report_v1, report_v2 copies.
  • Under the hood Git is a persistent hash map: the key is a hash, the value is the content. Section 4 shows exactly this.
  • Git works entirely locally and offline, with full access to history.
  • GitHub is a repository hosting service (Bitbucket is similar). It's used for collaboration, as a backup if your local copy is lost, and for extras like free websites on github.io with SSL.

Section 4 · The course's most important section

How Git works under the hood

The course builds a repository with no add and no commit, only low-level commands, so each object can be seen being created.

Initializing a repository git init · the .git folder

git init run inside a folder creates a hidden .git folder. That folder is the repository. Your project files sit beside it in the working directory. Never edit .git by hand.

The four object types Git object types

blobA file's contents: any file, text, image or video. No file name.
treeA folder: a list of blobs and other trees, with names and permissions.
commitA snapshot: points to one tree, plus author, message and parent.
annotated tagA permanent named pointer to a specific commit.

Writing a blob by hand git hash-object

echo "Hello, Git" | git hash-object --stdin      # only prints the hash
echo "Hello, Git" | git hash-object --stdin -w   # -w writes it into .git/objects
b7aec520dec0a7516c18eb4c68b64ae1eb9b5a5e

git hash-object ../new-file.txt -w               # or hash an existing file
4400aae52a27341314f423095846b1f215a7cf08

The pipe | sends one command's output to the next as standard input, which is what --stdin reads. Once written, the object stays even if you delete the source file: the repository is independent of your files.

Git as a key-value database JSON vs Git database

Like a JSON object, Git's database is a set of key → value pairs with unique keys. The difference: in JSON two keys can hold the same value, but in Git the key is calculated from the value. Identical content always gives the same key, so Git stores it only once.

Hash functions What is a hash · overview · SHA-1

  • A hash function turns input of any size (a short string or a multi-GB video) into output of fixed length.
  • It's one-way: you can't recover the input from the hash. That's why websites store password hashes.
  • It's deterministic: the same input always gives the same hash, which is why your blob hashes match the instructor's.
  • A tiny change in input gives a completely different hash.
  • Common functions: MD5 (128 bits), SHA-1 (160 bits, used by Git), SHA-256, SHA-384, SHA-512.
  • Hashes are written in hexadecimal (0–9, a–f): 160 bits = 40 hex characters. It's far shorter than binary and easy to compare by the first few characters.

How many files, and could two collide? Capacity · dice game · collision probability

  • Possible SHA-1 values: 2160 ≈ 1.46 × 1048, far more files than any repository will hold.
  • The dice analogy: with two dice, any specific pair has probability 1/36, and "some matching pair" has 6/36. A hash collision means any two files in the repository share a hash. The optional lecture extends the dice formula to files.
  • Even then the chance is around 10−48 for small repositories. In practice, treat every hash as unique.

Reading objects git cat-file

git cat-file -p b7aec5   # print contents → Hello, Git
git cat-file -t b7aec5   # type          → blob
git cat-file -s b7aec5   # size in bytes → 11

A short hash works if it's at least 4 characters and unique. An unknown hash gives fatal: Not a valid object name.

What's inside every object Why blobs have no names · contents of Git objects

Key ideaA blob stores only content, size and type. File names live in trees. That's what lets Git reuse one blob for many files with the same contents.

Trees and permissions Tree objects · object permissions · git mktree

A tree's content is one line per entry: mode type hashTabname. Modes: 040000 folder, 100644 regular file, 100755 executable file. Git needs them to recreate files correctly when it checks them out.

cat ../temp-tree.txt | git mktree
3b95df0ac6365c72e9b0ff6c449645c87e6e1159
find .git/objects -type f            # list every object file

The three areas Working directory, staging area, repository

git ls-files               # files in the staging area
git ls-files -s            # with mode, blob hash and stage number
100644 b7aec520dec0a7516c18eb4c68b64ae1eb9b5a5e 0	file1.txt
100644 4400aae52a27341314f423095846b1f215a7cf08 0	file2.txt

After read-tree the prompt shows the yellow ✗, and git status lists file1.txt and file2.txt as "changes to be committed". The index has content that no commit holds yet.

Section 5 · Basic Git operations

Commits and the everyday workflow

Now the normal direction: working directory → staging area → repository.

What a commit is What is a commit · exploring a commit object

A commit is a wrapper around one tree, the root folder of your project at that moment, plus metadata:

$ git cat-file -p 44e073
tree 31b1e96ca47eb9a6c2a506d8a1d6530da7786ea7     # the snapshot
parent 6fb73b…                                  # previous commit (none on the root commit)
author Bogdan Stashchuk <…> 1561… +0300          # who wrote it, Unix time, time zone
committer Bogdan Stashchuk <…> 1561… +0300       # who ran git commit (usually the same)

Second commit                                    # message

Because author, email and timestamp are inside the content, everyone's commit hashes differ, even with identical files.

Identity Configuring author name and email

git config --global user.name "Your Name"     # quotes needed if there's a space
git config --global user.email "you@example.com"
git config --list                             # check it

These settings are local to your computer and attached to every commit. Use the same email as your GitHub account. --global applies to all repositories; leave it out to set it for one project only.

Section 6 · Git branches and HEAD

Branches, HEAD and moving through history

Two tiny text files are behind everything here.

GitHub Desktop Installing · overview

A free graphical client used alongside the terminal. Skip the GitHub sign-in, confirm your name and email, then Add existing repository → first-project. It shows the current repository and branch (dropdown to switch or create branches), a Changes tab (commit from here with a summary), and a History tab with each commit's hash, author and file diffs.

What a branch and HEAD really are What is a branch · what is HEAD

  • A branch is a text file in .git/refs/heads/ holding one commit hash. The default branch is master.
  • The current branch tracks new commits: each commit moves its pointer forward automatically.
  • Branch names can't contain spaces; use dashes (refactor-main-menu, DEV-1512).
  • HEAD is the file .git/HEAD. It says what's checked out, normally a branch (ref: refs/heads/master). There's exactly one HEAD, and it's local to your computer.
cat .git/HEAD                 # ref: refs/heads/master
cat .git/refs/heads/master    # a82c… (hash of the latest commit)

The third commit Third commit · repository changes

  • The instructor deletes all three files (rm), stages the deletions with git add ., and runs git commit without -m. That opens Vim: press i to insert, type the message, then Esc and :wq (write, quit).
  • The new commit points to an empty tree, 4b825dc6…, the same hash in every Git repository in the world.
  • master moved to the new commit and HEAD moved with it. All old blobs and trees are still in .git/objects.

Checking out a commit: detached HEAD Checking out a specific commit

Watch outCommits made while HEAD is detached belong to no branch. Switch away and Git eventually deletes them, unless you first create a branch there. Use branch names, not hashes, to move around.

Why branches exist Why do we need branches?

  • Build a feature without touching the main line (master), and keep it only if it works.
  • Several people work in parallel, each on their own branch, shared through GitHub or Bitbucket.
  • Readable names instead of 40-character hashes.
  • Pick one naming convention and stick to it (for example a ticket number like BR-102, or descriptive names like refactor-main-menu).

Branch commands Git branches management · creating a new branch

CommandDoes
git branchList local branches; * marks the current one
git branch tempCreate a branch at the current commit, without switching to it
git checkout tempSwitch to it; Git just rewrites .git/HEAD to ref: refs/heads/temp
git checkout -b BR-1Create and switch in one step (the branch must not exist yet)
git branch -m temp new-tempRename
git branch -d new-tempDelete, only if merged (or it has no new commits)
git branch -D nameForce-delete an unmerged branch, losing its commits

Right after git branch temp, both .git/refs/heads/master and .git/refs/heads/temp contain the same hash. A new branch is a copy of a 40-character pointer.

A commit on a new branch reuses a blob Committing in the new branch · why Git reuses blobs

git checkout -b BR-1
echo "Hello, Git" > file4.txt
git add file4.txt
git commit -m "First commit in the BR-1 branch"
git log        # 4 commits; HEAD -> BR-1; master still on the third

Switching branches swaps the whole working directory: git checkout BR-1 shows only file4.txt; git checkout master shows an empty folder.

Practice

Try it yourself in 10 minutes

This replays the course's whole path. Type the text exactly and your blob and tree hashes will match the diagrams above.

mkdir first-project && cd first-project && git init   # newer Git may call the first branch main
echo "Hello, Git" | git hash-object --stdin -w                 # b7aec5…
echo "Second file in Git repository" | git hash-object --stdin -w   # 4400aa…
printf "100644 blob b7aec520dec0a7516c18eb4c68b64ae1eb9b5a5e\tfile1.txt\n100644 blob 4400aae52a27341314f423095846b1f215a7cf08\tfile2.txt\n" | git mktree   # 3b95df…
git read-tree 3b95df && git checkout-index -a && ls          # file1.txt file2.txt

git config --global user.name "Your Name"; git config --global user.email "you@example.com"
git commit -m "Our very first commit in the project"
echo "This is third file in our Git repository" > file3.txt
git add file3.txt && git commit -m "Second commit"
git cat-file -p HEAD                                           # tree 31b1e9…, parent …
find .git/objects -type f                                      # 7 objects

git checkout -b BR-1 && cat .git/HEAD                         # ref: refs/heads/BR-1
git checkout HEAD~1                                            # detached HEAD, then: git checkout BR-1

HEAD~1 means "one commit before HEAD". The course uses copied hashes instead, which works the same way.
