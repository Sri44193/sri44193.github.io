Some of the technology here is now dated. The course itself says SOAP has largely been superseded by REST, and that object brokers (CORBA) are legacy. Module 1 · Service-oriented architecture

Services and SOA

Just as you use a laundromat or a ride service, software can use outside services for the weather or exchange rates. Unlike a component, a service is external to the software requesting it and often remote. The two roles are service requester and service provider, similar to client and server. SOA means reaching your goals by building, using and combining services.

Service principles What makes a service reusable

Modular, loosely coupledRequests follow the interface: either a method-like call or a request document.
ComposableServices combine into apps or new services, like composing objects.
Platform- and language-independentA Java service can serve a Ruby client, thanks to standard protocols (XML, HTTP).
Self-describing and self-advertisingDescribes its own interface (WSDL) and can be found (UDDI or a catalogue).

Practitioner advice from the lectures: break the client's problem into conceptual chunks (e.g. a "management of change" service for engineering sign-offs) and define each one's interface. Hide information, keep coupling simple, and document complicated interactions between services, because that's where the risk is.

Module 1 · Web standards

HTML, XML, JSON, HTTP and JavaScript

  • HTML structures content but doesn't style it (<!DOCTYPE>, <head> for metadata, <body> for content). CSS adds the styling.
  • XML stores and transports structured data with your own tags, which can be validated by a schema.
  • JSON uses name–value pairs in { } and arrays in [ ]. It converts easily to JavaScript objects, which makes it the usual format between browser and server.

HTTP Request/response over TCP port 80 (HTTP/1.1)

  • URI vs URL: a URI identifies a resource; a URL also says how to locate it. All URLs are URIs. In http://etsy.com/user/favoriteitems/widebrimsunhat/sunhat.png the parts are protocol, host (resolved through DNS), path and resource.
  • Request: a request line (method, URI, version), headers (Host and Accept are required; Content-Type and Content-Length when there's a body), a blank line, then an optional body.
  • Response: a status line (e.g. 200 OK), headers, a blank line, then the body.
  • URL encoding: characters are limited to ASCII, so a space becomes %20 or +, and queries use ?a=1&b=2.
  • Stateless: HTTP doesn't link one request to the next, so sites use cookies to track sessions.

JavaScript runs in the browser (interpreted at runtime) and edits the page through the DOM. Example: clicking a cat thumbnail toggles it between 25% and 100% size. It can validate forms in the browser without reloading, takes work off the server, and lets you embed services such as Disqus comments with a pasted snippet.

Because WSDL is machine-readable, binding code can be generated automatically. Its modular parts can be reused (one interface over SMTP and HTTP), and WSDL files can import other WSDL files.

UDDI: publication and discovery A phone book for services

  • White pages: the business (businessEntity).
  • Yellow pages: the industry category and the service (businessService), e.g. food → delivery → pizza.
  • Green pages: technical details (bindingTemplate + tModel, which points to the WSDL).
  • API: save_*/delete_* to publish; find_*/get_*Detail to discover, all called with SOAP messages.
  • In practice discovery happens at design time by a person, since contracts and error handling need human judgment, while binding can be generated but is tested by people.

Module 3 · REST architecture

REST: representational state transfer

A client/server, request/response style in which messages are representations of resources: documents, images, objects. It's defined by five constraints:

1 · Client–serverSeparate concerns, so each side can evolve and scale independently.
2 · LayeredProxies and gateways can be added or removed to improve performance, translate messages or manage traffic.
3 · StatelessEach request carries everything needed, including authentication every time.
4 · CacheableThe server labels responses cacheable or not, which offsets the cost of statelessness.
5 · Uniform interfaceHTTP methods (GET, POST, PUT, DELETE), URIs for resources, and representations in XML, JSON or text.

Designing a REST API Eight practices from the lecture

  1. Use nouns in URIs; the HTTP method is the verb. Write /teachers, not /getAllTeachers.
  2. GET must never change state.
  3. Use plural nouns consistently: /students, /students/3.
  4. Use sub-resources for relationships: /students/3/courses/2.
  5. Use Content-Type and Accept headers to state input and output formats.
  6. Support filtering and paging: /courses?department=CMPUT&offset=20&limit=10.
  7. Version the API: /v2/students.
  8. Return the right status codes: 200 OK, 201 Created, 204 No Content (e.g. after a delete).

Module 3 · Microservices

Microservices: SOA at application scale

Benefits
  • The best language and framework for each service, and room to try new tech.
  • Scale by replication, independently per service, which also tolerates failures.
  • Update one service at a time.
  • Small parallel teams.
  • Reuse.
Costs
  • It's a distributed system, so it needs central coordination.
  • Transactions and data span services.
  • Harder testing and bugs that are hard to reproduce.
  • Callers must handle a failed service gracefully.
  • Messaging overhead; statelessness means cookies to track users.
  • Rigid old monoliths may need wrapping first.

Across the four coursesThe same few ideas recur at every scale: abstraction, encapsulation and information hiding, low coupling with high cohesion, separation of concerns, and composition over inheritance. They apply to a class (course 1), a pattern (course 2), an architecture (course 3) and a set of services (course 4).
