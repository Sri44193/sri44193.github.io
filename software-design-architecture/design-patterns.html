Module 1 · What is a design pattern?

Proven solutions to recurring problems

  • A design pattern is a practical, proven solution to a recurring design problem, used in real industrial software. It's conceptual knowledge, not code to paste. The course compares beginners and experts to chess: beginners know how the pieces move; experts recognise patterns on the board.
  • Why use them:
    • You skip the trial and error experts already went through.
    • They give a team a shared design vocabulary: "use an observer here" replaces a paragraph of explanation and leaves less room for misunderstanding.
  • Source: Design Patterns: Elements of Reusable Object-Oriented Software by Gamma, Helm, Johnson and Vlissides, the Gang of Four. It catalogues 23 patterns; this course covers a selection.
  • Pattern language: the set of patterns for a problem space. Games use encounters and quests; accounting uses double-entry bookkeeping. The implementation language also matters. JavaScript clones prototypes instead of instantiating classes, so different creational patterns fit there.
CreationalHow objects are created (or cloned).
StructuralHow objects are connected: like flavour pairings, from fully blended (hummus) to side by side (wine and cheese).
BehaviouralHow objects divide work toward a common goal, like a pit crew.

Every pattern has consequences, such as extra memory or processing, so choose the one that fits the problem. Some patterns span more than one category.

Module 1 · Creational patterns

Singleton and Factory Method

Singleton Exactly one instance, globally accessible

public class Preferences {
    private static Preferences uniqueInstance = null;
    private Preferences() { }                       // no `new` from outside
    public static Preferences getInstance() {
        if (uniqueInstance == null) uniqueInstance = new Preferences();
        return uniqueInstance;
    }
}

Factory object → Factory Method The knife store

  1. The problem: orderKnife(type) has a growing if/else of new SteakKnife(), new ChefsKnife()… (concrete instantiation) before the steps that never change: sharpen, polish, package.
  2. Factory object (not a Gang of Four pattern): move creation into a KnifeFactory.createKnife(type) and pass the factory into the store. Many clients can share it, and new knife types touch only the factory. The store now codes to an interface (Knife), not an implementation.
  3. Factory Method pattern: make KnifeStore abstract with an abstract createKnife(), and let subclasses decide what to make. BudgetKnifeStore makes budget knives; QualityKnifeStore makes quality knives. All of them inherit orderKnife().

Adapter Make incompatible interfaces work together

Composite Trees whose parts and wholes are treated alike

Module 3 · Principles underlying design patterns

Open/Closed, Dependency Inversion, Composition, Interface Segregation, Least Knowledge

Open/Closed Principle Open for extension, closed to change

Once a class is tested and stable, close it: change it only to fix bugs. Add features by extending it, either through a subclass or by implementing an abstract class or interface polymorphically. Use final to stop further extension. This keeps stable parts separate from changing parts, and every design pattern applies it in some form.

Dependency Inversion Principle Depend on generalizations, not details

Composing Objects Principle Favour aggregation and delegation over inheritance

  • Why: inheritance couples a subclass to all of its ancestors' non-private members. Composition keeps classes at arm's length and lets you combine behaviour at runtime, as Composite and Decorator do.
  • Cost: with no shared superclass code, you may write similar implementations more than once.
  • How to choose: ask whether the classes are related, whether you need specialised classes or just a different implementation, and what behaviour they really share.

Interface Segregation Principle No one should depend on methods they don't use

Principle of Least Knowledge (Law of Demeter) Only talk to your immediate friends

A method M of object O may call methods only on:

  1. O itself;
  2. objects passed to M as parameters;
  3. objects that M creates;
  4. O's own fields (direct components).

Don't "reach through" objects: driver.car.getEngine().start() is out; car.drive() is in, because you tell the car to drive, not its engine. Don't call methods on unknown types returned to you either (a driver who rents a motorcycle he never declared). The cost is more design work, so judge how much coupling you can tolerate.

Module 3 · Anti-patterns

Code smells and refactoring

Refactoring changes a program's internal structure without changing its external behaviour, in small steps with frequent tests. It's best done while you add features rather than as one big overhaul. The smell catalogue comes from Martin Fowler's Refactoring: Improving the Design of Existing Code.

SmellSignTypical fix
Comments as deodorantComments explaining a complicated design, or "remember to also change X"Simplify the design. Keep comments for APIs and for why a choice was made
Duplicated codeCopy-pasted posting code for feed, wall and groupExtract one shared method (D.R.Y.)
Long methodDoing too much (no fixed line limit; UI setup can be long)Split it into focused methods
Large class (God, Blob, Black Hole)Keeps attracting responsibilitiesKeep classes cohesive; extract classes early
Data classOnly getters and setters (e.g. a bare 2D point)Move the behaviour that uses the data into the class
Data clumpsx, y, z passed around togetherIntroduce Point3D, and give it real methods
Long parameter listHard to call correctly; needs commentsA parameter object, like a graphics context (not global variables)
Divergent changeOne class changed in many ways for many reasonsSeparation of concerns: extract classes
Shotgun surgeryOne change touches many classesMove related methods together (without creating a God class)
Feature envyA method mostly uses another class's dataMove the method to that class
Inappropriate intimacyTwo classes call each other back and forthFactor out shared parts, or make communication one-way
Message chainsa.getB().getC().doIt()Follow the Law of Demeter
Primitive obsessionPostal code "T6G 2R3" kept as a String everywhereA PostalCode class with validation
Switch statementsswitch on a type code (dog → "woof")Polymorphism: Dog.say(), Cat.say()
Speculative generality"We might need this someday"Just-in-time design: generalize when you need to
Refused bequestSubclass inherits things it doesn't want (Aunt Trudy's figurines)Move those members to the subclasses that use them, or don't inherit

Fixing one smell can create another. Turning data clumps into a class can produce a data class, so give the new class methods too.
