Module 1 · Architecture overview

The big picture of a system

Software architecture is the fundamental structure of a whole system: what its elements are, what each does, and how they relate. Like a skyscraper's architect, the software architect asks what the system is for, who uses it, which qualities matter, and where it runs. Without that shared plan, teams build to their own priorities and you get conflicts and duplication.

  • Who cares about it:
    • Developers get direction and know where responsibilities live.
    • Project managers see risks, task dependencies and the impact of changes.
    • Clients can see the team knows what it's doing.
    • End users don't see the structure, but care that it works well, the way a family cares that its house won't collapse.
  • Practitioners' view: architecture is "boxes and lines" made precise by choosing an architectural style. The architect keeps every stakeholder's perspective in mind and plays the long game on non-functional qualities.
  • Technology risk: the architect restrains enthusiasm for new technology, since a new language may not exist in ten years. Insulate the system against change, e.g. by sticking to standard relational database features so you can switch vendors.
  • Agile still needs architecture, done just in time in small cycles. The Agile Manifesto authors were all highly experienced system builders.

Module 2 · Language-based systems

Object-oriented, and main program and subroutine

The language's paradigm shapes the architecture. Object-oriented style centres on data: break the system into abstract data types (classes) using the four principles and the design patterns. Example: an automatic pet feeder with a Pet class (collar ID, maximum and current daily intake, reset each morning) and a FoodDispenser class (authorised pets, food left, dispense(), flashLight()). It's a poor fit for heavy scientific computation, where classes add complexity and cost performance.

Module 2 · Interpreter, dataflow, implicit invocation and process control

Four more styles

Interpreter-based Excel formulas · scripts · macros · JVM

A built-in interpreter turns user scripts, macros or rules (=SUM(A1:A4), a browser extension in JavaScript) into new combinations of the system's features, so developers don't have to build every combination themselves. Offering a domain-specific language makes this easier for end users. Running the system on an interpreter gives portability, but naive line-by-line interpretation is slow. The JVM interprets bytecode and compiles frequently run code to machine code, with lazy linking to reuse those translations.

Module 3 · Architectural trade-offs

Quality attributes

Design patterns solve specific technical problems. Architecture coordinates them to also meet business needs and non-functional qualities that patterns don't address, such as testability, usability and availability. No architecture is inherently good or bad, only right or wrong for its context. A repository architecture is wrong for a fast-changing online game; it's like fitting a person-sized door on a garage. Most real systems combine several styles.

Developers' perspectiveMaintainability · reusability · flexibility · modifiability (the most expensive to achieve) · testability · conceptual integrity
Users' perspectiveAvailability (uptime) · interoperability · security (who can see versus change) · performance (throughput, latency) · usability
  • Measurable: each attribute needs an objective metric. Prioritise them per system, involve a technical lead, and look at the design from every stakeholder group's point of view.
  • Keep it simple: prefer the simplest architecture that meets the requirements.
  • Document it: the architecture shouldn't live in one person's head.
  • Set structural rules: well-defined subsystems, one shared implementation per common task, and rules for using resources (e.g. bandwidth goes to transactions before queries).
Module 3 · Analyzing and evaluating

Quality attribute scenarios and ATAM

ATAM (Architecture Tradeoff Analysis Method, from the SEI at Carnegie Mellon) lets evaluators who don't know the system review it. It has three participant groups: the evaluation team (designers, peers or outsiders, who must be unbiased), the project decision makers, and the architecture stakeholders (users, developers, support staff).

  1. Present ATAM.
  2. Present the business drivers.
  3. Present the architecture.
  4. Identify the architectural approaches.
  5. Build the quality attribute utility tree.
  6. Analyse the approaches against the architecturally significant requirements (ASRs): find risks, non-risks, sensitivity points (e.g. traffic raises latency) and trade-offs (e.g. capping users protects latency at the cost of availability).
  7. Stakeholders brainstorm and prioritise scenarios. Many scenarios outside the utility tree signal a risk.
  8. Re-analyse with the top 5–10 scenarios.
  9. Present the results, with risks grouped into risk themes linked to business drivers.
