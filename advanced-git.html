Section 13 · Git tags

Tags, releases and semantic versioning

Tags are static pointers Git tags overview · lightweight vs annotated

git tag v1.0.0                                  # lightweight
git tag -a v1.0.0 -m "First major release"      # annotated
git tag                                         # list (doesn't show which kind)
git show v1.0.0                                 # tag details + the commit; the course uses git tag -v v1.0.0
git push --tags                                 # tags are NOT pushed by plain git push
git push origin v1.0.1                          # push one tag (and only the tag, not new commits)
  • Tags aren't pushed automatically, so collaborators' local tags with the same name don't collide.
  • Pushed tags appear on GitHub under Releases → Tags. Draft a new release on GitHub can create a tag too, with a title, notes and downloadable zip/tar.gz. git pull then brings the new tag down.

Section 14 · Rebasing

Rebasing: a linear history

An alternative to a 3-way merge. History becomes a straight line with no merge commits, but it's rewritten: commits are copied and the originals discarded.

RuleNever rebase public branches (master, release, dev) that other people have pulled. Rebase only your own private feature branches.
git checkout feature1
git rebase master          # step 1: move feature1 on top of master
git checkout master
git merge feature1         # step 2: "Fast-forward"
git log --graph            # a single straight line
git branch -d feature1 && git push
  • Trade-off: merging keeps the full history (who did what on which branch). Rebasing gives a clean line but hides where branches started and ended, and discards the original commits. The instructor personally prefers merging.
  • Two dates: git cat-file -p on a rebased commit shows the original author date and a new committer date. git log shows the author date, so rebased commits can look older than their parent. SourceTree shows the commit date.
Section 15 · Ignoring files

.gitignore

UntrackedNew file Git offers to add.
TrackedUnmodified, modified or staged: Git watches it.
IgnoredMatches a .gitignore rule: Git doesn't report or offer it.

Create .gitignore at the start of a project, usually in the root (it can live in any folder), and commit it.

# Ignore a single file
new-file.txt
# Ignore everything in the bin directory
bin/
# Ignore all .tmp files anywhere (* = zero or more characters)
*.tmp
  • When pushed, the remote gets .gitignore itself but none of the ignored files.
  • Start tracking a previously ignored file: remove or change its rule. It shows up as untracked; add and commit it.
  • Ignore a file you already committed: add the rule, then git rm --cached <file>. It's deleted from the repository but kept on disk. Commit both changes. (Or delete the file and add the rule, but that loses your local copy.)
  • What to ignore:
    • Build output (bin/, build/) and dependency folders (node_modules/, packages/). Anyone can rebuild or reinstall them.
    • Compiled files and logs (*.pyc, *.log).
    • OS files (.DS_Store, Thumbs.db).
    • Secrets such as .env.
  • Templates: gitignore.io (type a language or OS) and github.com/github/gitignore.

Section 17 · Advanced Git

History tools, undo tools and clean-up

The course clones the vuejs/vue repository (50,000+ objects, default branch dev) to have a real history to experiment on. Any busy public repository works.

Searching history git log options · shortlog · filtering · pretty format · merge filters

git log --oneline                 # one line per commit
git log --graph                   # ASCII graph: see which commits have two parents
git log --stat                    # files changed, +/- lines per commit
git log -p                        # full diffs (easier to read in a GUI)
git log -4 --oneline              # last 4 commits

git shortlog -n -s -e             # commits per author, most first, counts only, with emails
git log --author="AchillesJ"      # filter by author (a regex, so part of a name works)
git log --grep="dev" --oneline    # filter by words in the message
git log --pretty=format:"%h %cn %cd %s"   # %H full hash, %h short, %cn committer, %cd date, %s subject
git log --merges --oneline        # only merge commits
git log --no-merges               # only "human" commits

Projects that squash pull requests (like Vue) have very few merge commits.

Undoing: reset vs revert git reset · git revert

git reset <commit> modeRepository (commits)Staging areaWorking directory
--softResetKept (changes stay staged)Kept
--mixed (default)ResetReset (changes unstaged)Kept
--hardResetResetReset: changes are gone
git reset HEAD~2                  # drop the last 2 commits, keep the changes as unstaged edits
git reset --hard <hash>           # go back completely (a later git pull brings pushed commits back)
git revert HEAD                   # new commit inverting the last one; opens editor for the message
git revert <hash>                 # on conflict: fix files, git add ., git revert --continue
git show <hash>                   # see what a commit changed

Amend and cherry-pick --amend · cherry-picking

git commit --amend -m "Fixed message"                       # replace the last commit (new hash)
git commit --amend --author="Mike Githubber <mike@…>"      # fix its author

git cherry-pick <hash>                # copy one commit from anywhere onto the current branch
git cherry-pick --no-commit <hash>    # apply its changes only; commit yourself

reflog: your safety net Reflog – log of all Git operations

git reflog                  # every move of HEAD: commits, checkouts, resets, rebases…
git reflog show temp        # only one branch's history
git checkout HEAD@{6}       # where HEAD was 6 operations ago (detached)
git reset --hard <hash-from-reflog>   # undo a bad reset --hard

The reflog is local only; it doesn't include other people's work or remote operations. Entries expire after about 90 days by default. HEAD@{0} is always the latest entry, so the numbers shift as you work.

Stash Terminal · GitHub Desktop

git stash          # save uncommitted (staged + unstaged) work; working tree is clean again
git checkout dev   # …do something else…
git checkout temp
git stash pop      # re-apply and drop the stash

Under the hood a stash is a temporary commit (two parents) referenced by .git/refs/stash. The file disappears after pop. In GitHub Desktop, switching branches offers Leave my changes on temp; coming back shows View stash → Restore / Discard.

Garbage collection git gc

Git runs it automatically, but you can run git gc yourself. It deletes unreachable objects and old reflog entries, and packs loose objects into a new .pack + .idx pair. Afterwards .git/objects has far fewer folders.

Squashing Squash on GitHub · interactive rebase locally

git rebase -i <hash-of-commit-before-the-branch>   # or: git rebase -i HEAD~3
# the editor lists the commits oldest first; keep the first as "pick",
# change the others to "squash" (or "s"), then :wq
# a second editor shows the combined message; edit it, then :wq
pick 1a2b3c File4 was created in the feature2 branch
s    4d5e6f File5 was created in the feature2 branch
s    7a8b9c File6 was created in the feature2 branch

git checkout master && git merge feature2          # fast-forward

Day-to-day workflow Git development workflow

  • Public branches (master, release, dev) are protected; only owners merge pull requests into them.
  • While you work on a long feature, other features keep landing on dev. Merge dev into your feature branch often (GitHub Desktop: Choose a branch to merge into feature1), or rebase your branch on dev. Small, frequent syncs mean small conflicts; waiting weeks means many.
Section 18 · GitHub Pages

Free static hosting with GitHub Pages

Two kinds of site Simple site · hosting any repository

Repository nameURLHow to enable
<username>.github.io (one per account)https://<username>.github.ioPublic repo with index.html in the root; works automatically
Any other repo, e.g. gh-pages-statichttps://<username>.github.io/gh-pages-staticSettings → Pages → Source: choose a branch

Every push updates the site, usually within a minute or two.

If Git pushes with the wrong saved account (403 permission denied to …), clear the cached helper for that repository with git config credential.helper ""; Git then asks for the username and token again.

Publishing a React app Create React App · preparing · SSH · verifying

npx create-react-app gh-pages-react && cd gh-pages-react   # needs Node.js (node -v, npm -v)
npm start                                                   # dev server on localhost:3000
npm install -D gh-pages

// package.json
"homepage": "https://mikegithubber.github.io/gh-pages-react",
"scripts": {
  "predeploy": "npm run build",
  "deploy": "gh-pages -d build"
}

npm run deploy                      # then Settings → Pages → Source: gh-pages
  • SSH instead of HTTPS fixes repeated wrong-account errors:
    1. Generate a key pair (ssh-keygen; files land in ~/.ssh/).
    2. Paste the public key (id_rsa.pub) into GitHub → Settings → SSH and GPG keys. One key per computer covers all your repositories.
    3. Switch the remote: git remote set-url origin git@github.com:<user>/<repo>.git.
  • If you see "branch gh-pages already exists", deleting node_modules/.cache fixed it in the course.
  • Install VS Code's code shell command with Cmd/Ctrl+Shift+P → "Shell command: Install 'code' command in PATH". Ctrl+` opens the built-in terminal.

Custom domain Configuring a custom domain

  1. Settings → Pages → Custom domain, e.g. gh-pages.stashchuk.com (no https://, no trailing slash).
  2. At your DNS provider, add a CNAME record: gh-pages → <username>.github.io. DNS can take a while to update.
  3. For a React app on a custom domain, set homepage to the root (https://<username>.github.io), not the sub-path, or the JS and CSS files return 404. Then redeploy.
  4. In the course, each deploy wiped the custom-domain setting. A common fix (not shown in the course) is to add a CNAME file containing the domain to React's public/ folder so it's included in every build.

The section ends with a no-code Markdown site: GitHub generates an index.md with a theme you can switch in Settings and edit online.

Section 19 · Git hooks

Git hooks: automating checks

Without hooks Git accepts any commit, any message and any push. A hook is an executable script Git runs before or after an event. For "before" hooks, exit code 0 lets Git continue; anything else aborts.

Typical uses: check or prepare the commit message (e.g. require a ticket number); run tests before commit or push; lint and auto-fix code (ESLint, Pylint); send notifications after a commit; deploy on the server after a push to master.

Local hooks by hand pre-commit · post-commit · pre-rebase · email regex

  • git init creates samples in .git/hooks/ (pre-commit.sample, commit-msg.sample, …), all disabled by their .sample extension.
  • To enable a hook: copy or rename it to the exact hook name (pre-commit). The file must be executable (chmod +x); otherwise Git prints "hook was ignored because it's not set as executable".
  • To see .git in VS Code: Settings → Files: Exclude → remove **/.git.
  • The sample pre-commit blocks file names with non-ASCII characters.
#!/bin/sh
# .git/hooks/post-commit
echo "Thanks for committing $GIT_AUTHOR_NAME"

#!/bin/sh
# .git/hooks/pre-rebase: block all rebasing
echo "Rebasing is not allowed in this repository"
exit 1

#!/bin/sh
# .git/hooks/pre-commit: only company emails may commit
regex="@company\.com$"
email="$GIT_AUTHOR_EMAIL"
if [[ $email =~ $regex ]]; then
  echo "Your email $email satisfies Git policy"; exit 0
else
  echo "Your email $email doesn't satisfy Git policy"; exit 1
fi

The regex test uses bash's [[ =~ ]], so for portability make that script's first line #!/bin/bash.

The catch.git/hooks is not pushed or cloned. Teammates don't get your hooks. The course stores the scripts in the working directory for reference, and solves sharing with npm packages that install hooks during npm install.

Shared hooks in a Node.js project Jest · pre-commit · Husky · --no-verify

npm init -y                       # package.json
npm install -D jest               # "test": "jest"; add node_modules to .gitignore
# src/sum.js, src/mult.js + tests/sum.test.js, tests/mult.test.js
#   it('should return correct sum', () => { expect(sum(2, 5)).toBe(7); });
npm test

npm install -D husky              # replaces the simpler "pre-commit" package; supports every hook
  • Installing the package writes real scripts into .git/hooks that call it. Anyone who clones and runs npm install gets the same hooks.
  • Anyone can skip hooks with git commit -n (--no-verify). Hooks are a convenience, not security. Protect the central branches too: branch protection plus CI checks on pull requests (GitHub Actions, Travis CI).

Lint, test only what's staged, check the message ESLint · lint-staged · post-commit · commitlint

npm install -D eslint eslint-plugin-import eslint-config-airbnb-base \
               lint-staged @commitlint/cli
npx eslint --init                 # the course runs it via a temporary npm script; choose CommonJS, Node, JS config
// .eslintrc.js → extends: 'airbnb-base'
{
  "scripts": {
    "test": "jest",
    "lint": "eslint src/**",
    "lint-fix": "eslint src/** --fix",
    "success-message": "echo Thanks for committing $GIT_AUTHOR_NAME"
  },
  "husky": {
    "hooks": {
      "pre-commit": "lint-staged",
      "commit-msg": "commitlint -E HUSKY_GIT_PARAMS",
      "post-commit": "npm run success-message"
    }
  },
  "lint-staged": {
    "*.js": ["eslint", "jest --findRelatedTests"]
  },
  "commitlint": {
    "rules": { "references-empty": [2, "never"] },
    "parserPreset": { "parserOpts": { "issuePrefixes": ["ISSUE-"] } }
  }
}
  • lint-staged passes only the staged .js files to ESLint, and Jest runs only the tests related to them. Commits stay fast even with big test suites. With no staged JS it prints "No staged files match any configured task".
  • ESLint errors block the commit; warnings (e.g. console.log) don't. --fix adds missing semicolons and newlines but won't remove code.
  • commitlint with that config rejects any message without an ISSUE-<n> reference ("references may not be empty"). [ISSUE-12] Added post-commit hook passes, which suits Jira-style ticket linking.
  • This is the Husky v4 format. Husky v5+ uses npx husky init and scripts in a committed .husky/ folder, but the idea is the same.
  • Learn more: githooks.com and pre-commit.com, which supports any language.
