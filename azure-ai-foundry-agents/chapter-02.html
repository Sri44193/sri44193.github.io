The six phases, with maintenance feeding back into development
PhaseKey activities (hotel example)
📋 PlanningInterview managers, front-desk staff and past guests; resolve conflicts (managers want billing answers, staff warn prices change often); feasibility study, mock-ups; ends when everyone agrees on features, boundaries and goals.
✏️ DesignChoose reactive / deliberative / hybrid; write the personality ("Welcome to Crystal Hotels!"); pick services (translation for many languages, vision for room photos); map user journeys; plan accessibility (screen readers, text size).
🛠️ DevelopmentBuild an MVP (check-in times, directions), gather feedback ("doesn't understand late check-out", "recommends a closed restaurant"), add features in agile cycles; then harden: databases, timeouts, security, responsible AI, CI/CD and containers.
🧪 TestingUnit (right pool hours), integration (booking in one language updates the reservation system), UAT with real staff and sample guests, plus performance, regression, security and load tests.
🚀 DeploymentPilot (staff or a few guests) → soft launch (more guests, support on standby) → full release, still watched closely.
🔧 MaintenanceAnalytics on speed and satisfaction; update for new amenities (a new spa); refresh the knowledge base; scheduled health checks; escalation rules to human staff.
MVP
Minimum viable product: the smallest version with only the critical features, used to prove the idea works.
UAT
User acceptance testing: real users try the system in a controlled way before launch.
Soft launch
Releasing to a larger but still limited audience, with support ready to step in.
🧩 Example from the reading The pilot reveals the agent can't handle Wi-Fi password requests after midnight: a bug only real usage found, fixed before the soft launch.
📌 Remember No lifecycle fits every project: startups may iterate loosely and fast (risking missed details); legal or medical agents need more controls and compliance checks. Choose a structure that fits your goals, resources and risks.
➕ Not in the course: what's different about testing agents Classic unit tests expect one exact output. Agent answers vary in wording, so tests usually check properties instead: does it contain the right fact, stay in scope, refuse when it should, use the right tone? AI Engineering Ch 3–4 covers how to score these.
❓ Check yourself
Which phase ends when all stakeholders agree on features, boundaries and objectives?
Planning.
What's the difference between UAT and a pilot launch?
UAT is a controlled test before launch with staff and sample guests; a pilot is the first real release to a small group, in production.

The design workshop: four design documents

The blueprint before you build 🎬 Design workshop demo

🎯 Analogy You wouldn't build a house without a blueprint. For an agent, the blueprint is four documents, and for a tester they are the acceptance criteria.

🎭 1. Persona

Name ("Hotel Assistant"), traits ("helpful, professional, calm, especially with guest problems"), sample phrases ("Hello and welcome to the hotel. How can I assist you today?").

🔀 2. Conversation flows

Happy path: "Dinner is 6 pm–11 pm. Would you like to make a reservation?" Complaint with decision points: AC broken → maintenance → still unhappy → front desk.

🚧 3. Boundaries

Medical/legal: "I cannot provide medical or legal advice… dial 911… consult the front desk." Opinions: "As an AI assistant, I don't have a personal opinion, but…".

📏 4. Success metrics

From Monitoring → Resource usage: total requests, token counts, latency, requests over time.

The complaint flow from the demo
Total requests
How many times the model endpoint was called: each chat message or completion is one request.
Prompt tokens
Input tokens sent to the model (instructions + conversation + question).
Completion tokens
Output tokens the model generated.
Total tokens
Prompt + completion. Tokens drive cost.
Latency
How long the model takes to start responding. Lower is better.
➕ A realistic latency target The demo calls under 100 ms "excellent" for chat agents. In practice, large hosted models like GPT-4.1 usually take several hundred milliseconds or more before the first word, so treat 100 ms as optimistic. Set your target from your own measurements (for example, a 95th-percentile time to first token) rather than a fixed number.
🧪 Testing angle Turn each document into test cases. Persona → greeting and tone checks. Flows → one test per branch (happy path, unhappy-then-escalate). Boundaries → a negative test set (medical, legal, opinion, other hotels' prices, phrased many ways). Metrics → thresholds that fail the build.
❓ Check yourself
Why are boundaries a separate design document, not just part of the persona?
They protect users and the business from wrong or dangerous advice; they need explicit examples and their own tests.

Understanding agent configuration parameters

Five levers and their trade-offs 📄 Understanding agent configuration parameters

🧒 Plain English Configuration isn't a one-off technical setup; it's a cycle that keeps the agent aligned with business goals and guest needs. Done well, guests barely notice; done badly, the agent miscommunicates, frustrates guests, or creates legal risk.

🧠 Model choice

Fast, cheap models for routine FAQs; advanced models for complex, sensitive or multilingual requests. Some chains blend: light model for standard queries, advanced for VIPs or complex cases.

🌡️ Temperature

Low = predictable (check-out time, rules, safety). Higher = varied and friendly (anniversary ideas). Real agents use low for compliance, warmer for experiences.

🛡️ Guardrails

Content filters (offensive language), topic restrictions (no medical or legal advice), data protection (no personal details leaked).

📏 Response length

Lobby kiosk: longer answers OK. SMS or mobile: short. Frequent follow-up questions are a sign that default answers are too short.

📚 Grounding

Connect answers to up-to-date sources (reservation system, today's menu), cite them, and so reduce hallucination.

Temperature
How random the model's word choices are. 0 ≈ the same answer every time; higher = more variety and creativity.
Grounding
Making the agent answer from specific, authoritative data you provide, rather than from its general training.
Hallucination
A confident, plausible-sounding answer that is false ("the sauna is open 24 hours" when there's no sauna).

⚠️ Three trade-offs to remember • High creativity engages guests but risks mistakes if safety filters are weak.
• Advanced models serve better but cost more; sometimes only worth it for luxury properties or high-value guests.
• Tight grounding avoids mistakes, but if the source data is stale, grounded answers are still wrong.
• Filters tuned too tight make the agent seem reserved; the course says that's still better than a privacy breach.
🧪 Testing angle Stale-data test: change a policy in the source document (pets now allowed) and check the agent's answer changes. If it still gives the old rule, your knowledge pipeline, not the model, is the bug.

Agents interface deep dive: settings in practice

Model, instructions, temperature, Top P, safety, knowledge, versions 🎬 Agents interface deep dive

⚙️ Building the Hotels Assistant, step by step 
# 1. A model must be deployed first
deploy "GPT-4.1"                 # "balanced": good language skills, reasonable cost
# 2. Shape the default agent in the setup panel
name         = "Hotels Assistant"
deployment   = "gpt-4.1 (2025-04-14)"
instructions = "You are a friendly and professional assistant for a hotel..."
# 3. Model settings
temperature  = 0.5              # demo: 0.2 = plain facts, 0.9 = same facts, livelier tone
top_p        = 0.5              # keeps word choice focused, avoids odd or off-topic replies
# 4. Safety: Azure AI Content Safety filters are on by default (no controls shown here)
# 5. Grounding: Knowledge → Add → Files → upload the hotel policy document
ask("What is your pet policy?")   # answer now comes from the document
# 6. Versions: Agents → select → Copy → edit the copy → compare in the Evaluation tab
Top P
The model only picks from the most likely next words whose probabilities add up to P. Lower Top P (0.5) = a smaller pool of words = more focused, less surprising replies.
Response length limit
A cap on how long answers can be (max tokens). In the demo it runs on the deployment's defaults behind the scenes.
Azure AI Content Safety
Built-in filters that block harmful content in prompts and answers, on by default.
Temp 0.2
facts
Temp 0.5

Temp 0.9

➕ Not in the course: change one knob at a time The demo sets both temperature 0.5 and Top P 0.5. Model providers usually advise adjusting one or the other, not both, because they both control randomness and the combined effect is hard to reason about. As a tester, change one setting per experiment so you know what caused a difference.
🧪 Testing angle Versions + Evaluation tab = A/B testing built in. Run the same test questions against "formal" and "friendly" versions and compare side by side. Keep the question set fixed and saved so every future version is compared on the same ground (a regression suite).
❓ Check yourself
Why was 0.2 chosen first for the hotel agent?
Guests asking factual questions (checkout time) need the same, consistent answer every time.
How do you create a second version of an agent to compare?
In the Agents tab, select the agent and use Copy, edit the copy's instructions or settings, then compare both in the Evaluation tab.

The art of prompt engineering: four components

Better answers without changing the model 🎬 The art of prompt engineering

🧒 Plain English Prompt engineering means writing clear instructions that tell the model how to behave. With only "You are a helpful bot", the hotel agent's reply to "Hi, how are you?" was generic and flat. Four components fixed it.
ComponentInstruction added in the demoEffect
🎭 Persona"You are the virtual concierge… warm, professional, helpful. Always greet warmly and end by asking if there's anything else."Greets, helpful tone, concierge-style structure
🚧 Boundaries"Do not answer medical, legal or financial questions… recommend a professional or hotel staff. Serious complaint → apologise, offer the front desk manager.""I have a headache, what medicine?" → politely declined
📍 Context"This week the city hosts its annual summer jazz festival, within walking distance.""What is there to do?" → mentions the festival
📋 Format"Use a bulleted list for restaurant hours or amenities."Clean, scannable list instead of a long sentence
🎯 Analogy Briefing a temp receptionist on day one: who you are (persona), what never to do (boundaries), what's happening this week (context), how to write things down (format).
🧪 Testing angle One check per component: tone/greeting check (persona), refusal tests (boundaries), "does it mention this week's event?" (context), "is the answer a bullet list?" (format; easy to automate).

Ask at each step: does the prompt fix it? does another model? is my case truly unique?
Fine-tuning
Training an existing model further on your own examples (approved guest questions and answers), so it adopts your style or knowledge. Like extra coaching.
Few-shot learning
Putting a few example questions and ideal answers in the prompt so the model copies the pattern.
RAG
Retrieval-augmented generation: look up relevant documents at question time and give them to the model. This is how "knowledge" grounding works.

🏋️ Fine-tune only if…

Prompts and model choice miss your accuracy target · language or processes are so unique no model knows them (brand terms, local dialects, proprietary booking rules) · you need exact templates or rigid compliance that prompts can't guarantee.

⏱️ Need speed?

Try a smaller base model first. Fine-tune a small model only if you need speed and custom responses.

💸 Cost reality

Prompting: days of testing, no extra cost, instant updates. Fine-tuning: compute, storage, retraining every time policies change; pays off only at thousands to millions of daily interactions.

🧩 When fine-tuning is justified A luxury group in five countries whose agents keep giving wrong multi-language answers about its loyalty programme, even after prompt work: fine-tuning a multilingual model on its documents could be worth it.
⚠️ Hallucination: causes and fixes Causes: no boundary like "only answer from uploaded documents"; ambiguous or out-of-scope questions ("the chef's favourite dish?"); real-time data the model can't see ("is my room ready now?").
Fixes: grounding; a fallback answer ("I don't have that information right now. May I ask a staff member?"); tell it not to guess; when unsure, ask for clarification or escalate to a human.
🧪 Testing angle Build an "unanswerable" test set: things the hotel doesn't have (sauna, helipad), real-time questions (room ready?), opinions (chef's favourite dish). Pass = fallback or escalation; fail = any invented detail.
➕ About the reading The model names in the reading (GPT-4o, GPT-4 Turbo, GPT-3.5) are already older generations, and a placeholder ("Visual 3: … to be added after client review") was left in the published text. The decision logic still holds.

Advanced prompting strategies: five techniques

From simple tool to reliable assistant 🎬 Advanced prompting strategies

🅰️🅱️ Manual A/B testing

Copy the agent, rename it "Friendly", make the tone warmer, then ask both "Hi, how are you?" via the Agent ID dropdown and compare.

🪜 Chain of thought

"Think step-by-step before you answer." Now "What time does the pool close, and can I get a late checkout tomorrow?" gets both parts answered.

📝 Few-shot examples

Show Q → A pairs: "What are the restaurant hours?" → "The Crystal Grill is open for breakfast 6–11 am, dinner 5–10 pm." The agent copies the format and detail.

🚧 Boundaries

"No medical or legal advice; suggest a professional. Don't discuss other hotels' details or prices."

🛟 Fallback

"If you don't know, say: I don't have that information, but I can check with the front desk. Would you like me to?" Test: "Where is the helicopter landing pad?"

Manual A/B testing with two agent versions
⚠️ Common trap Judging an A/B test on one question. Tone and quality vary run to run; use the same 20+ questions, several runs each, and score them the same way for both versions.
➕ Note on chain of thought Newer "reasoning" models already think step by step internally, so this instruction matters less for them; it still helps with standard chat models. Also check whether you want the steps shown to guests or just used internally.
❓ Check yourself
Which technique stops the agent inventing a helipad?
The fallback strategy (plus boundaries telling it not to guess).
A two-part question gets only one part answered. Which technique helps?
Chain-of-thought: "Think step-by-step before you answer."
What do few-shot examples control?
The desired format, tone and level of detail of answers.

  10. 🪜 Prompt first, other model second, fine-tune last (only for unique language, rigid templates or huge scale).

  12. 🅰️🅱️ Advanced: A/B versions, chain of thought, few-shot, boundaries, fallback.

Try it: the module's activities

What the course asks you to do, plus a QA twist

  1. Hotel agent blueprint and lifecycle plan: write the persona, two conversation flows, boundaries and three success metrics.
  2. Hotel agent creation in the Agents UI: deploy GPT-4.1, name and instruct the agent, set temperature, upload a hotel policy file.
  3. Prompt engineering for your agent (60 min): add persona, boundaries, context and format; then few-shot, chain of thought and a fallback.
  4. ➕ QA twist: make a 20-question test set in four groups: FAQs, multi-part questions, out-of-scope (medical, legal, other hotels), unanswerable (helipad, "is my room ready?"). Run it on two versions and record pass/fail per group.
