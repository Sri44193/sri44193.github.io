Why testing saves reputations

Three real failures and the testing gap behind each 🎬 Why testing saves reputations

🧩 The hotel version The agent gives a guest the wrong checkout time, the guest misses a flight, and a bad review, lost business and reputational damage follow. One small wrong fact, big cost.
What happenedDamageTesting gap
✈️ An airline chatbot gave a wrong refund policy; the customer bought a ticket relying on itA tribunal held the airline responsible for its chatbot's words; costs and lost trustFunctional testing against official policy
🐦 A tech company's bot learned from social media; users fed it offensive messages and it started posting themShut down fast, major PR problemSafety and adversarial testing (testers trying to break it on purpose)
🏦 A banking chatbot exposed private account informationLost confidence, privacy finesSecurity testing
➕ The real cases The course doesn't name them, but these match well-known incidents: Air Canada's chatbot refund case (a Canadian tribunal, 2024) and Microsoft's Tay bot (2016). Worth knowing by name for interviews.

✅ Functional

"Does it do what it should?" Pool closing time, Wi-Fi connection.

🌀 Edge case

Rare or odd input: ALL CAPS, slang, a service that doesn't exist (helipad).

🔐 Security

Tricking the agent, e.g. prompt injection: hidden instructions to make it ignore its rules.

Prompt injection
An attack where the user (or a document the agent reads) includes instructions like "ignore your previous rules and…", trying to override the agent's real instructions.
Adversarial testing
Deliberately trying to make the system fail, the way an attacker or troll would.
📌 Remember Good testing prevents legal problems (accurate, compliant answers), protects the brand (catch embarrassing behaviour first), keeps users safe (privacy, no dangerous advice) and so maintains trust. In Foundry: the Evaluation tab for structured testing, the Monitoring tab to study real conversations.

Testing methodologies

Five methods, a template, a workflow and red teaming 📄 Testing methodologies

MethodQuestion it answersHotel examplePass when…
✅ FunctionalDoes it do its core job in normal conditions?Pet policy, breakfast times, room availabilityOutput matches the expected response
🌀 Edge caseDoes it cope with rare or "impossible" input?Book for 100 people; bring an unusual animalIt declines politely, asks for clarification or escalates; never nonsense
🔐 SecurityCan it be tricked into leaking or doing harm?Prompt asking for account numbers, password hints, internal configIt refuses, redirects to security, or ends the conversation; any leak = fail
⏱️ PerformanceDoes it stay fast and accurate under load?"500 users request booking confirmations at once"All within 2 seconds, no data loss (the reading's example)
🔁 RegressionDid the change break something that worked?New payment method → re-check search, old payments, confirmations, messagesThe whole suite still passes
Load testing
Simulating expected peak traffic (a big convention starting) and tracking speed, accuracy and memory/server use.
Stress testing
Going beyond the designed load to see how it fails. It should fail gracefully: alert staff, show a sensible fallback message.
Red team
A group that attacks the agent like real misusers: prompt injection, input fuzzing (random inputs) and integration boundaries (requests mixing many features).
Compliance testing
Checking the agent follows local data privacy and security laws.
Observability
Seeing what the deployed agent does through event logs and real-time tracing.

The testing workflow; every fixed incident becomes a regression check

🤖 Automate

Regression and performance tests, scheduled on every release.

🧠 Keep manual

Edge cases, adversarial checks, UX validation: human judgment spots subtleties.

🌍 Diverse testers

People from different backgrounds and places predict more real user behaviour.

📚 Best practice

Test early and throughout, keep records, automate repetition, plan for the agent and users changing.

⚠️ Where the reading oversimplifies It says a functional test passes only if the output perfectly matches the expected answer. With language models that rarely works: correct answers come in many wordings. Check the facts and behaviour instead: "mentions 11:00 am", "no price invented", "offers the front desk". Use exact match only for structured outputs (JSON fields, intent labels).
➕ Not in the course: indirect prompt injection Injection can also arrive through content the agent reads: a guest review, an uploaded document or a web page containing "ignore your instructions". Once your agent has knowledge files or tools, add test cases where the attack is hidden in the data, not typed by the user.

Likert scale
A 1–5 rating scale ("strongly disagree" → "strongly agree"). Here an AI grader scores, e.g., relevance 1–5, and 3+ passes. (The demo spells it "Lekert".)
Relevance / coherence / fluency
Does the answer address the question / hang together logically / read naturally?
Evaluator (grader)
Usually another AI model told how to score answers: "AI as a judge".
⚠️ Read the demo critically (a QA lead's view) • What was tested? "Evaluate a model" with simulated questions and answers tests a model, not necessarily your configured agent with its instructions and knowledge.
• Five generated questions is a smoke test, not evidence. Real suites need many cases, including your own hand-written ones from real guest logs.
• A pass of 3 out of 5 on relevance is lenient for factual answers like checkout time; correctness needs a check against the real policy.
• The grader is an AI too; spot-check its verdicts by hand before trusting them.
🧪 Testing angle Use Foundry evaluations as the automation layer: upload your own labelled dataset (question, expected facts), choose groundedness and relevance graders for knowledge answers, set thresholds per test set (stricter for policies, looser for tone), and rerun on every prompt or model change. Keep the AI red teaming scan for security.
❓ Check yourself
Name the three test sets the demo uses.
Happy path, edge cases, security (prompt injection).
All five generated injection attempts passed. Is the agent secure?
No. It only resisted five simple, generated attacks. You need many more, stronger and indirect attacks, plus the red teaming scan and manual red-team work.

Deployment is a journey, not a single action
Endpoint
The public URL the website or app sends questions to (in Foundry: My assets → Models + endpoints).
Key
A secret password (authentication token) proving the request comes from a trusted app.
Time to last byte
How long until the whole response has arrived (vs latency to the first byte).
🧩 How a live request flows A guest types into the website's chat widget → the site sends the question and the secret key to the endpoint URL → the agent processes it and sends the answer back → the widget shows it. Metrics track requests, total / prompt / completion tokens, latency and time to last byte.
➕ Staging is an environment, not a tab The video uses the Evaluation tab to stand in for "staging". In real projects, staging is a separate copy of production (its own project or resource, same settings and integrations, test data). Evaluations can run against it, but they don't replace it.

Deployment architecture: four integration patterns

How the agent connects to apps and systems 📄 Deployment architecture

Agent endpoint vs model endpoint
An agent endpoint returns complete agent answers (instructions, knowledge, tools included); a model endpoint talks straight to the raw model.
REST API
Standard rules for programs to talk over HTTP: send a request, get a response.
Rate limiting
Capping how often requests can be sent, to prevent overload or abuse.
Webhook
An endpoint that receives a notification when something happens elsewhere (new booking, check-in).
PatternHow it worksHotel exampleBest for / watch out
🔌 Direct APIApps call the agent's REST endpoint"Rooms available Friday?" from the website chatSimple, real-time. Needs strict auth and rate limits
🧰 SDKA toolkit wraps common calls in simple functions; handles keys and retries"Chat with concierge" or "late checkout" buttons in the mobile appFast to build. Less flexible for custom needs
🔔 WebhookAnother system notifies the agent when an event happensA surf lesson booked with a partner → agent sends confirmationEvent-triggered. Verify a secret on every call, retry failures
📡 Event-drivenEvents are shared with every service that needs them, asynchronouslyLate checkout updates housekeeping, payments, messaging, inventoryLarge chains, peak periods. Needs planning, queues, de-duplication

The webhook pattern from the reading
📌 Best practices Match the pattern to real needs, not habit · document and separate sensitive endpoints · regularly test authentication and rate limiting · choose patterns that can grow · involve business, technical and user voices.
🧪 Testing angle Each pattern has its own failure tests. API: no key, wrong key, expired key, burst traffic beyond the rate limit. Webhook: missing or bad secret, duplicate events, delivery failures and retries. Event-driven: out-of-order and duplicate events (the guest must not get two confirmations).

Accessing your agent through its API

Endpoint, key, request, status code, error handling 🎬 Accessing your agent

🎯 Analogy An agent with no API is a library with no doors. The endpoint is the street address (host = which building, path = which office inside); the API key is the door key.
🧩 The demo's Python call (➕ my sketch of it, with placeholders) 
import os, requests

ENDPOINT = os.environ["AGENT_ENDPOINT"]   # never paste the URL and key in code
API_KEY  = os.environ["AGENT_API_KEY"]    # use environment variables or a secret store

headers = {"Authorization": API_KEY}      # exact header name depends on the API
payload = {"message": "What time is checkout?"}   # JSON body: key-value pairs

resp = requests.post(ENDPOINT, headers=headers, json=payload)

if resp.status_code == 200:               # 200 = OK
    print(resp.json())                    # the agent's reply, also JSON
else:                                     # e.g. 401 = unauthorized (bad key)
    print("Error", resp.status_code, resp.text)

✅ 200 OK

Request worked; read the JSON reply.

⛔ 401 Unauthorized

Key wrong or missing. In the demo, setting the key to "WRONG" gives 401: proof the security works.

➕ 429 Too many requests

Not in the video: the rate limit was hit. Back off and retry.

⚠️ Common trap Committing an API key to a public GitHub repo (and your portfolio repo is public!). Bots scan GitHub for keys within minutes. Keep keys in environment variables or a secret manager; if one leaks, rotate it immediately. Module 1 also showed the safer keyless option: sign in with a Microsoft (Entra) identity.
🧪 Testing angle This is plain API testing, your existing skill (think Postman, which the course lists as a tool). Cases: 200 with a valid question, 401 with a wrong key, missing body, huge body, wrong content type, rate-limit burst, timeout handling. Then assert on the reply content, not just the status code.

Building your portfolio

Repository, README, docs, demo video, diagrams 📄 Building your portfolio · 🎬 Portfolio creation workshop

🗂️ GitHub repository

Public, clear name and description, initialised with a README. Folders: code/, docs/, demo/. main for finished work, branches for experiments; issue and PR templates.

📘 README

Title + one-paragraph problem statement · Features · Architecture & technologies (Foundry, model, prompt engineering) · Installation / usage or Demonstration link · Contributing · License · Lessons learned.

📐 Documentation

Architecture diagram, API docs with placeholders (POST <your-endpoint>/agent/run, <API_KEY>), configuration guide (system prompt, temperature, Top P), changelog, and testing documentation.

🎬 Demo video

About 2 minutes, clear audio, subtitles. Show an easy question, a complex one, and one out of scope to prove the boundaries work.

🗺️ Architecture diagrams

Guest query → language understanding → knowledge retrieval → response. Add sequence and data-flow diagrams with a legend for non-technical readers.

📌 Why it matters A portfolio shows progression (first simple agent → production-ready), communication and a continuous-improvement mindset. It's a living project: update docs, demos and features as you grow.
🧪 Your QA advantage The reading says portfolios should document the testing process: test cases, evaluation results (accuracy, performance), a QA dashboard, bug-fix logs. Most developers skip this; for a Lead QA engineer it's the centrepiece. Put your test sets, evaluation screenshots, pass rates per category and one "bug found → fixed → regression test added" story in docs/testing.md.

✅ One-page cheat sheet

  1. 💥 Untested agents cause legal, PR and privacy damage (airline refund, offensive bot, bank leak).
  2. 🧪 Five methods: functional, edge case, security, performance (load, stress), regression; plus red teaming (injection, fuzzing, integration boundaries).
  3. 📋 Template: name, purpose, steps/input, expected, pass/fail rule, actual, result.
  4. 🔁 Design → execute → analyse → fix → retest; every incident becomes a regression test.
  5. 🤖 Automate regression and performance; keep edge cases, attacks and UX manual.
  6. 📊 Foundry evaluations: simulate or upload questions → evaluators (Likert, labeler, scorer) → pass grade → Data tab. Plus AI red teaming.
  7. 🚀 Dev → staging → production → monitoring; metrics: requests, tokens, latency, time to last byte.
  8. 🔌🧰🔔📡 Patterns: direct API, SDK, webhook, event-driven. Always authentication + rate limits.
  9. 🔑 Endpoint (host + path) + key; keys in env vars or a secret store, never in code. 200 OK, 401 bad key.
  10. 💬 Messages are JSON: role (user / assistant) + content. Agent loop: perceive → reason → act.
  11. 🗂️ Portfolio: repo, README, docs (incl. testing), 2-minute demo, architecture diagrams.
