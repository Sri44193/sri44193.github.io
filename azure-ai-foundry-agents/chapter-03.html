Why language understanding matters

NLU in the Language playground 🎬 Why language understanding matters

🧒 Plain English Natural language understanding (NLU) is the part of AI that works out what a message means: what the person wants, which details matter, and which language it's in. It lets guests book, ask about amenities and find attractions in their own words and language.

📝 Summarise for call center

Turns a conversation into Recap, Issue, Resolution. Demo: the "unresolved case" about an espresso machine. The issue line is effectively the guest's intent.

🏷️ Extract named entities

Pick entity types, run the Travel sample, see every date, place and preference tagged with details.

🌍 Multilingual

Run the non-English call center sample with English output: recap, issue and resolution come back in English.

📌 Three benefits for hotels 1) Understand guest needs → personal service. 2) Extract details automatically → staff freed for real guest care. 3) Handle many ways of saying the same thing → consistent service across languages. The course cites a hotel chain that cut misrouted queries by 60% with intent recognition (a course claim; no source given).

The four capabilities working on one guest message (➕ combined example)
Intent
What the guest wants to do. Demo instruction: classify messages as Book Room, Modify Reservation, Check Availability, Amenity Request. "I would like to book a room for next week Monday" → Book Room, then the agent asks for the missing details.
Entity
A specific detail that goes with the intent: dates, room type, number of guests. "A double room for two adults from October 5th to the 8th" → room type, guest count, date range, passed to the reservation system.
Key phrase
The important words that reveal preferences: "a king bed and a sofa bed". Tagged for personalisation and to notify the right hotel department.
Dynamic language detection
Spotting the guest's language on the fly and routing to the right pipeline; in Foundry the recap, issue and resolution come back translated.
🎯 Analogy A good receptionist hears "Could I possibly get somewhere to sleep on the 5th?" and knows it's a booking (intent), notes the date (entity), remembers you mentioned a king bed (key phrase), and switches to your language (detection).
🧪 Testing angle These are classification and extraction tasks, so you can test them like ordinary functions. Build a labelled set (message → expected intent and entities), include paraphrases, typos, mixed languages and two intents in one message, and measure intent accuracy and entity exact-match. Re-run it whenever the instructions change.
❓ Check yourself
"Can you move my Friday booking to Saturday?" Intent and entities?
Intent: Modify Reservation. Entities: original date Friday, new date Saturday.
What's the difference between an entity and a key phrase?
An entity is a typed detail (date, number of guests, room type) a system needs; a key phrase is an important phrase revealing preferences (king bed and sofa bed) used for personalisation.

Knowledge as the agent's foundation

Structured, unstructured and dynamic knowledge 🎬 Knowledge as agent foundation

📊 Structured

Organised data such as policy tables in CSV or JSON. Gives precise answers: check-in time, parking fee. Easy to index and search.

📄 Unstructured

Free text: PDFs, training manuals, guest feedback. Covers broad topics and nuance for real conversation.

⚡ Dynamic

Live sources through APIs: the reservation system, hotel databases. Current, real-time answers.

🧒 Plain English In the agent's setup panel, Knowledge → Add lets you upload local files (structured and unstructured) or connect an API endpoint (dynamic). A good knowledge base mixes all three. The payoff is grounding: "which room types are available?" is answered from the latest system data, not the model's memory.
🧪 Testing angle Test each knowledge type differently. Structured: exact values ("parking fee is $25") as strict checks. Unstructured: does the answer agree with the manual (judge or human review)? Dynamic: change the live data (room sold out) and check the agent's answer changes, and that it fails gracefully when the API is down.
➕ About the "90%" claim The video says a strong knowledge base can cut misinformation by 90% or more. Treat that as a motivating claim; measure your own agent's error rate before and after adding knowledge.

Search mechanisms: score, search, rank, filter

How the agent finds the right passage 📄 Search and retrieval concepts

🧩 The challenge "Does the gym have towels, and what are the opening hours on holidays?" A human concierge connects this to the right policies instantly. An agent must extract the intent, find the relevant policies and filter the rest, or it answers slowly, partly or wrongly.

🔢 Relevance scoring

Gives every passage a usefulness number. "pool towels policy" → pool passages score high, meeting-room text scores zero, even if it shares a word.

🧭 Semantic vs keyword

Keyword finds exact words. Semantic matches meaning: "When can I print a document?" finds "business center hours".

🏆 Ranking

Orders results using score, recency, credibility (official policy beats a forum post or old brochure) and past feedback.

🚧 Filtering

Rules: only policies updated in the last year, never confidential staff material, no members-only perks for regular guests.

Embedding
A list of numbers (a vector) that captures the meaning of a text. Texts with similar meaning get similar numbers, so "printing a document" lands near "business center".
Semantic search
Search that compares embeddings (meaning) instead of exact words.
🔑 Keyword search🧭 Semantic search
MatchesExact termsMeaning (vectors)
StrengthsFast, transparent (you can see why it matched)Flexible, handles paraphrases and other languages
WeaknessesMisses synonymsMore resources; if poorly configured, finds plausible but wrong passages
➕ Not in the course: hybrid search Many production systems (including Azure AI Search) run both keyword and vector search and merge the results, then often apply a re-ranker model. That gets exact matches (room codes, product names) and paraphrases.
⚠️ Common trap Semantic search returns something for every query, even when the answer isn't in the knowledge base. Without a minimum relevance threshold, the agent answers from a loosely related passage. Test with questions whose answer truly isn't there.

Steps 1–3 build the index; steps 4–5 run on every question
Vector store
A database built to store embeddings and quickly find the closest ones (the reading names Milvus and Pinecone; Foundry agents create their own).
Dimensionality
How many numbers are in each embedding. More dimensions can capture more nuance but need more storage and compute.
Recall
Of all the passages that could answer the question, how many did we find?
Precision
Of the passages we returned, how many were actually useful?
Context injection
Putting the retrieved passages into the prompt so the model answers from them. Too much or too little context → hallucination or "I'm not sure".
⚙️ Worked example: precision and recall (➕ my numbers) 
# The knowledge base has 4 passages about the pet policy
# The search returns 5 passages; 3 of them are about pets
precision = useful returned / all returned  = 3 / 5 = 0.60
recall    = useful returned / all useful    = 3 / 4 = 0.75
# Return more passages → recall usually goes up, precision goes down

🔁 Query expansion

Recognise alternative phrasings: "pet-friendly" ↔ "dogs allowed". Raises recall.

📖 Synonym handling

Map guest words to internal terms: "Wi-Fi" → "internet access".

🎖️ Contextual ranking

Re-rank by conversation history or guest status (loyalty perks first for members).

🧪 Testing angle Test retrieval separately from the answer. For each test question, list which passages should be found, then check what was retrieved (precision, recall). If retrieval is right but the answer is wrong, it's a prompt/model bug; if retrieval is wrong, fix the index or ranking. Also watch the edge cases the reading names: no result, ambiguous questions, and questions spanning several services.
➕ Correction to the reading The reading says embeddings may come from models such as GPT-4, Claude or Llama. Those are chat models; embeddings normally come from dedicated embedding models (in Azure, for example, text-embedding-3-small or -large). The query must be embedded with the same embedding model as the documents.
❓ Check yourself
The agent answers using an outdated brochure instead of the current policy. Which mechanisms failed?
Ingestion/cleaning (the old brochure shouldn't be there), ranking (official and recent should win) and possibly filtering (only policies updated in the last year).
Search returns 10 passages, 2 relevant; there are 2 relevant in total. Precision and recall?
Precision 2/10 = 0.2, recall 2/2 = 1.0. Everything was found, but with a lot of noise.

Knowledge system demo: grounding the hotel agent

Vector store, files and a live connection 🎬 Knowledge system demo

⚙️ Steps in the Foundry agent's setup panel 
# Structured knowledge
Knowledge → Add → Files → create new vector store
  Upload local → StructuredPolicies.json → Upload and save
# Unstructured knowledge, into the same store
vector store ⋯ → Manage → add unstructured_hotel_policy.docx → Update
# Dynamic knowledge
Knowledge → Add → Microsoft Fabric → Create connection (keys, name)
# Tell the agent what to trust first
Instructions += "Prioritise structured knowledge documents over unstructured ones"
# Test with paraphrases
ask("Do you have a gym in your hotel?")
ask("Is there a fitness center in your hotel?")   # should give the same facts
➕ What's really going on The video calls the "prioritise structured documents" instruction fine-tuning the relevance score and says it gives the agent semantic search. More precisely: the vector store (embeddings) already provides semantic search, and the instruction only nudges how the model weighs what it retrieved. No model is fine-tuned; this is prompt engineering. The demo also mentions chunking (splitting documents into passages) and metadata, which affect what gets retrieved.
🧪 Testing angle The gym / fitness centre pair is a paraphrase consistency test: different words, same expected facts. Make it a pattern: 3–5 phrasings per fact, all must agree. Add a conflict test: put different values in the JSON and the DOCX and check that the structured one wins, as instructed.

Service integration: three combinations

One agent, several senses 🎬 Service integration vision

🌍 Translation + intent

Instruction: reply in English and the guest's language, and classify intents. "Quiero reservar un cuarto, por favor" → Book Room, answered in Spanish and English.

😠 Sentiment + routing = smart escalation

Instruction: note the tone; if the guest seems angry or unhappy, escalate to management, otherwise reply positively. "My room is too small and the AC is not working" → escalated, asks for details.

🖼️ Vision + knowledge

Attach hotel_room.png: "What type of room is this, and is there availability?" → standard king room, asks for dates.

Smart escalation
⚠️ Common trap In the demo, the "escalation" is only the model saying it escalated; nothing is actually sent to a manager. A real agent needs a tool or workflow (ticket, email, Logic App) behind that promise. Test that the escalation really happens, not just that the reply mentions it. (Later courses in the series cover workflows.)
🧪 Testing angle Sentiment edge cases: sarcasm ("Great, another cold shower 🙃"), polite-but-angry, mixed ("lovely staff, filthy room"), and other languages. Count false escalations (annoy managers) and missed escalations (angry guest ignored) separately.

✅ One-page cheat sheet

  1. 🧠 NLU: what the guest means. Playground tools: call-centre summary (recap, issue, resolution), named entities, multilingual.
  2. 🎯🏷️🔑🌍 Four skills: intent, entities, key phrases, language detection. Keyword bots match words; agents understand intent.
  3. 📊📄⚡ Knowledge: structured (CSV/JSON), unstructured (PDF, manuals), dynamic (APIs). Mix all three for grounding.
  4. 🔢🧭🏆🚧 Search: score → semantic/keyword search → rank (recency, credibility) → filter (rules).
  5. 🧬 Embeddings = meaning as numbers; semantic search compares them. Not a silver bullet: plausible-but-wrong matches.
  6. 🔄 Pipeline: ingest/clean → embed → index → retrieve (precision vs recall) → inject context.
  7. 🛠️ Optimise: query expansion, synonyms, contextual ranking; watch no-result and ambiguous queries.
  8. 🗃️ Foundry: Knowledge → Files → vector store; Manage to add files; Fabric for live data; test with paraphrases.
  9. 🤝 Integrations: translation + intent, sentiment + escalation, vision + knowledge, speech for hands-free.
  10. 🧪 Test each stage separately: intent accuracy, entity match, retrieval precision/recall, then the final answer.
