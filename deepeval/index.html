QA field notes · LLM evaluation

DeepEval, read through a tester's eyes

What the framework does, how it scores, where it can mislead you, and a full blueprint for standing up an LLM quality program from an empty repository.

Reviewed against deepeval 4.x Latest on PyPI: 4.3.1 (16 Oct 2026) Python ≥ 3.9 Apache-2.0 Notes dated 28 Oct 2026
Read this firstDeepEval moves fast — a release roughly every one to two weeks through 2026, including breaking changes inside the 4.x line. Code here follows the 4.x API. Pin your version, and confirm any API detail against deepeval --help and the docs for that exact version before you build on it.

01Why LLM QA is different

Classic test automation assumes a deterministic function and an exact oracle. LLM systems break both assumptions.

DimensionTraditional softwareLLM applicationWhat QA has to change
DeterminismSame input → same outputSame input → many valid outputs; drift between model versionsAssert on properties (relevant, grounded, safe) instead of exact strings; run repeats to measure variance
OracleassertEqual(expected, actual)"Correct" is fuzzy and often contextualUse rubric-based judges (LLM-as-a-judge), reference answers, and deterministic checks where possible
Pass/failBinaryContinuous score 0–1Thresholds become test design decisions that must be calibrated against humans
Failure surfaceLogic bugs, crashesHallucination, retrieval misses, tool misuse, loops, role breaks, toxicity, prompt injectionNew defect taxonomy and new test types (component, multi-turn, adversarial)
Test dataFixturesCurated "goldens" that are a product assetDataset versioning, ownership, coverage reviews
Cost of a test~FreeEach judged case costs judge-model tokens and secondsTiered suites (smoke / regression / full), caching, budget gates
Regression sourceYour codeYour code and prompts, retrieval data, model provider updatesRe-run evals on prompt, data, and model changes — not only code changes
QA insightThe evaluator is itself a model. That means your test oracle has its own error rate. A mature LLM QA practice tests the tests: it measures how often the judge agrees with humans before trusting its verdicts as a release gate.

02What DeepEval is

DeepEval is an open-source (Apache-2.0) Python framework from Confident AI for unit-testing LLM applications. Its own description is "Pytest, but specialised for LLM apps": you write test cases, attach metrics, and run them with a pytest-based CLI. Evaluations run locally in your environment; the hosted Confident AI platform is optional and adds shared dashboards, dataset management, regression tracking, and production tracing.

Test runner

Pytest-native

assert_test() inside normal pytest files, executed with deepeval test run. Fits any CI that can run Python.

Metrics

50+ ready-made

RAG, agentic, multi-turn, MCP, multimodal, safety, plus custom G-Eval, DAG, and code-based metrics. Every metric returns a score and a reason.

Granularity

End-to-end and component

Black-box tests on final output, or @observe tracing to score individual spans — retriever, tool call, sub-agent.

Data

Goldens & synthesis

Datasets of goldens; a Synthesizer generates single- and multi-turn goldens from documents; a simulator drives multi-turn conversations.

Integrations

Framework hooks

OpenAI, Anthropic, OpenAI Agents, LangChain, LangGraph, Pydantic AI, CrewAI, LlamaIndex, Google ADK, Strands, AWS AgentCore, OpenTelemetry.

Ecosystem

DeepTeam & TypeScript

Red teaming lives in the sibling project DeepTeam. A TypeScript SDK (Vitest-based) now covers most metric types.

Which fields each metric family needs

Most "my metric errored" issues come from missing fields. Design your capture layer so these are always populated.

FieldPopulated byNeeded for
inputGoldenEverything
actual_outputYour app at test timeNearly every output-quality metric
expected_outputGolden (human or synthesized)Contextual Recall, Contextual Precision, correctness-style G-Eval
retrieval_contextYour retriever at test timeFaithfulness, all Contextual* metrics

Design ruleKeep goldens and test cases separate. Goldens are versioned, reviewed data. Test cases are ephemeral, built at run time by calling the system under test. Mixing them (hard-coding actual_output into fixtures) silently freezes yesterday's output and turns your suite into a snapshot test of nothing.

04How a DeepEval run works

  1. Load goldens from a file, Python list, or Confident AI (versioned).
  2. Invoke the system under test for each golden. With tracing on, every @observe-decorated function becomes a span.
  3. Build test cases from the golden plus what the app actually produced (output, retrieved chunks, tool calls).
  4. Measure. Each metric runs — concurrently by default — making one or more judge calls (claim extraction, verdicts, reason generation) or pure code checks.
  5. Decide. A metric passes when score ≥ threshold; a test case passes only when all its metrics pass. assert_test raises on failure so pytest reports it.
  6. Report. Console table, structured JSON in a results folder, optional HTML/Markdown export, the deepeval inspect terminal trace viewer, and a sync to Confident AI if logged in.

Three ways to execute

Keep the gating set small — three to five metrics per use case. Every extra LLM-judged metric adds cost, latency and another source of judge noise.

06How scoring works (and where it misleads)

The common knobs on every metric

ParameterEffectQA guidance
thresholdPass if score ≥ threshold (default typically 0.5)Never ship the default. Calibrate per metric (see §15).
modelJudge model — provider object, custom DeepEvalBaseLLM, or a model-name stringPin an exact model version; keep it different from the app's model to reduce self-preference bias.
include_reasonGenerate a natural-language explanationOn in CI (it's your bug report). Off for bulk scoring to save cost.
strict_modeBinary scoring: 1 or 0, threshold forced to perfectUse for zero-tolerance rules (e.g. "never reveals internal prompt").
async_modeConcurrent internal judge callsLeave on; reduce concurrency instead if you hit rate limits.
verbose_modePrints intermediate steps (claims, verdicts)Turn on when debugging a disputed verdict.

Scoring techniques under the hood

QAG-style

Claim → verdict → ratio

Faithfulness, relevancy and similar metrics extract statements or claims, ask the judge for a yes/no/idk verdict on each, then score as the fraction supported. Explainable, but sensitive to how claims get split.

G-Eval

Criteria → steps → weighted score

The judge turns your criteria into evaluation steps (or uses yours), scores the case, and weights the final score by token log-probabilities when the model exposes them.

DAG

Decision tree

You define nodes (task, binary judgement, non-binary judgement, verdict). The judge answers narrow questions; the graph — not the model — decides the score.

Deterministic

Plain code

Tool Correctness, JSON Correctness, Tool Permission, Loop Detection: no judge, no variance, near-zero cost. Prefer these wherever a rule can be expressed in code.

Judge caveats
  • G-Eval's log-prob weighting needs a judge that returns log-probabilities; the DeepEval docs warn that some newer model families without them can't be used as G-Eval judges.
  • LLM judges show position bias, verbosity bias, and self-preference (favouring their own family's outputs).
  • The same case can flip between pass and fail across runs near the threshold. Measure this before gating (repeat runs, §15).
  • Judge prompts are tuned for English; validate separately for other languages.

Minimal end-to-end test

tests/test_smoke.py
from deepeval import assert_test
from deepeval.metrics import GEval, AnswerRelevancyMetric
from deepeval.test_case import LLMTestCase, SingleTurnParams

correctness = GEval(
    name="Correctness",
    criteria="Is the actual output factually consistent with the expected output?",
    evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT, SingleTurnParams.EXPECTED_OUTPUT],
    threshold=0.7,
)

def test_refund_policy():
    case = LLMTestCase(
        input="What if these shoes don't fit?",
        actual_output=my_app("What if these shoes don't fit?"),   # call the real system
        expected_output="Customers get a 30-day full refund at no extra cost.",
    )
    assert_test(case, [correctness, AnswerRelevancyMetric(threshold=0.7)])
API namingSingleTurnParams and MultiTurnParams are the current names for the field selectors used by G-Eval (they replaced the older LLMTestCaseParams). Tutorials from 2024–2025 still show the old name.

08Datasets & synthetic data

Golden sources, in order of trust

  1. Production traffic — real user inputs (anonymised), especially failures and escalations. Highest realism.
  2. SME-authored — domain experts write input + ideal answer. Highest label quality, slowest.
  3. Synthetic — DeepEval's Synthesizer generates goldens from documents or contexts, with "evolutions" that make questions harder (reasoning, multi-context, comparative, hypothetical…), plus filtering and styling configs. Fast coverage; must be reviewed.
  4. Adversarial — hand-crafted or DeepTeam-generated attacks and edge cases.
scripts/synthesize.py
from deepeval.synthesizer import Synthesizer

synth = Synthesizer()                        # uses the configured judge model by default
goldens = synth.generate_goldens_from_docs(
    document_paths=["kb/returns.pdf", "kb/shipping.md"],
)
synth.save_as(file_type="json", directory="data/goldens/_review_queue")
# Never write straight into the gated suite. A human reviews, edits, then promotes.

Recent releases added multi-turn golden generation (scenarios, expected outcomes, user descriptions), contexts that span multiple source files, a generate CLI command, and dataset versioning on Confident AI.

Multi-turn: the conversation simulator

Writing 10-turn conversations by hand doesn't scale. A ConversationalGolden describes a scenario and expected outcome; the ConversationSimulator plays the user against your chatbot through a callback, producing ConversationalTestCases you then score. Newer versions add stopping controllers, simulation graphs for scripted flows, and voice simulations.

Dataset design rules for QA

  • Tier the suite: smoke (20–50 cases, every PR), regression (200–500, nightly), full (1,000+, pre-release), adversarial (separate, scheduled).
  • Tag every golden with feature, intent, difficulty, risk, source, owner. Coverage reports come from tags.
  • Every production incident becomes a golden before the fix ships — the LLM equivalent of a regression test.
  • Version datasets with the code (Git, or Confident AI versions) and record the dataset version on every run.
  • Hold out a calibration set with human verdicts — used only to validate judges and thresholds, never to tune prompts.
  • Watch for overfitting: if prompt engineers iterate against the gated set, scores inflate. Rotate a hidden set.

09Tracing, safety, benchmarks, prompt optimisation

Component-level evaluation with tracing

End-to-end scores tell you that something failed. Component scores tell you where. Decorate functions with @observe; attach metrics to a span; set the span's test case with update_current_span. Framework integrations (LangChain/LangGraph callback handler, OpenAI and Anthropic client wrappers, CrewAI/ADK/Strands/AgentCore instrumentors, Pydantic AI, LlamaIndex, OpenTelemetry/OpenInference) create spans for you.

component-level pattern
from deepeval.tracing import observe, update_current_span
from deepeval.test_case import LLMTestCase
from deepeval.metrics import ContextualRelevancyMetric, TaskCompletionMetric

@observe(metrics=[ContextualRelevancyMetric(threshold=0.6)])
def retrieve(query: str) -> list[str]:
    chunks = vector_store.search(query, k=5)
    update_current_span(test_case=LLMTestCase(input=query, actual_output="", retrieval_context=chunks))
    return chunks

@observe()
def answer(query: str) -> str:
    return llm.generate(query, context=retrieve(query))

# Trace-level metric on the whole run, span-level metric on retrieve()
for golden in dataset.evals_iterator(metrics=[TaskCompletionMetric()]):
    answer(golden.input)

Safety and red teaming

DeepEval holds the safety metrics (Bias, Toxicity, Misuse, Role Violation, Tool Permission). Adversarial attack generation — prompt injection, jailbreaks, PII leakage, and the other vulnerability categories — lives in DeepTeam, a separate open-source project from the same team. Plan it as its own test stage with its own schedule and sign-off.

Benchmarks

Built-in academic benchmarks (MMLU, HellaSwag, DROP, BIG-Bench Hard, TruthfulQA, HumanEval, GSM8K, MathQA and others) evaluate a model, not your application. Useful for model-selection spikes; not a substitute for app-level goldens. Note that 2026 releases fixed silent scoring bugs in several benchmarks — older results may be understated.

Prompt optimisation

DeepEval can automatically search for better prompts against your metrics (algorithms include COPRO and SIMBA). From a QA standpoint, treat optimised prompts like any code change: they must pass the held-out set, not just the set they were optimised on.

10Building a QA framework from scratch: design principles

Part two. You're a QA lead with an LLM product and an empty repo. These principles shape every later decision.

P1

Deterministic first

Anything expressible as code (schema, regex, allowlist, length, latency) is a code check. LLM judges are for what code can't judge.

P2

Separate data, system, oracle

Goldens, app adapter and metric config live in different modules so each can change independently.

P3

Config over code

Thresholds, judge model, suite membership in versioned YAML. Changing a threshold is a reviewed PR, not a silent edit.

P4

Test the oracle

Judges are validated against human labels before they gate anything, and re-validated on every judge model change.

P5

Reproducible runs

Every run records: app commit, prompt version, dataset version, deepeval version, judge model, thresholds.

P6

Tiered cost

Fast cheap suites on every PR; expensive suites nightly or pre-release. Budget is a test constraint.

P7

Framework-agnostic core

Wrap DeepEval behind thin factories. If APIs change (they will), you fix one module, not 400 tests.

P8

Failures are data

Every failure lands with its reason, trace and inputs in an artifact a developer can open without re-running.

Metric factory — the single upgrade seam

evalkit/metrics_factory.py
from deepeval.metrics import (
    GEval, AnswerRelevancyMetric, FaithfulnessMetric,
    ContextualRecallMetric, ContextualPrecisionMetric, ContextualRelevancyMetric,
    ToolCorrectnessMetric,
)
from deepeval.test_case import SingleTurnParams
from evalkit.custom_metrics.pii import NoPIIMetric

def _correctness(threshold, model):
    return GEval(
        name="Correctness",
        evaluation_steps=[
            "List the factual claims in the expected output.",
            "Check whether the actual output states each claim, or a faithful paraphrase.",
            "Heavily penalise any statement that contradicts the expected output.",
            "Do not penalise extra helpful detail that does not contradict it.",
        ],
        evaluation_params=[SingleTurnParams.INPUT, SingleTurnParams.ACTUAL_OUTPUT,
                           SingleTurnParams.EXPECTED_OUTPUT],
        threshold=threshold, model=model,
    )

_REGISTRY = {
    "correctness":          _correctness,
    "answer_relevancy":     lambda t, m: AnswerRelevancyMetric(threshold=t, model=m),
    "faithfulness":         lambda t, m: FaithfulnessMetric(threshold=t, model=m),
    "contextual_recall":    lambda t, m: ContextualRecallMetric(threshold=t, model=m),
    "contextual_precision": lambda t, m: ContextualPrecisionMetric(threshold=t, model=m),
    "contextual_relevancy": lambda t, m: ContextualRelevancyMetric(threshold=t, model=m),
    "tool_correctness":     lambda t, m: ToolCorrectnessMetric(threshold=t),
    "no_pii":               lambda t, m: NoPIIMetric(threshold=t),
}

def build_metrics(specs: list[dict], judge_model: str):
    """Fresh metric objects per test: metrics hold state (score, reason)."""
    out = []
    for s in specs:
        if s["name"] not in _REGISTRY:
            raise KeyError(f"Unknown metric '{s['name']}' in config")
        out.append(_REGISTRY[s["name"]](s["threshold"], judge_model))
    return out

A deterministic custom metric

evalkit/custom_metrics/pii.py
import re
from deepeval.metrics import BaseMetric
from deepeval.test_case import LLMTestCase

_PATTERNS = {
    "email": re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"),
    "card":  re.compile(r"\b(?:\d[ -]?){13,16}\b"),
    "phone": re.compile(r"\+?\d[\d -]{8,}\d"),
}

class NoPIIMetric(BaseMetric):
    """Fails if the output contains anything that looks like PII. No judge, no variance."""
    def __init__(self, threshold: float = 1.0):
        self.threshold = threshold

    def measure(self, test_case: LLMTestCase) -> float:
        hits = [k for k, p in _PATTERNS.items() if p.search(test_case.actual_output or "")]
        self.score = 0.0 if hits else 1.0
        self.reason = f"PII patterns found: {hits}" if hits else "No PII patterns found."
        self.success = self.score >= self.threshold
        return self.score

    async def a_measure(self, test_case: LLMTestCase) -> float:
        return self.measure(test_case)

    def is_successful(self) -> bool:
        return self.success

    @property
    def __name__(self):
        return "No PII"

Adapter, dataset loader and case builder

import json, time, pathlib, httpx
from dataclasses import dataclass, field
from deepeval.dataset import Golden
from deepeval.test_case import LLMTestCase

# ---- adapter.py ----
@dataclass
class Response:
    output: str
    retrieval_context: list[str] = field(default_factory=list)
    latency_s: float = 0.0

class AppClient:
    def __init__(self, base_url: str, timeout: float = 60):
        self.http = httpx.Client(base_url=base_url, timeout=timeout)

    def ask(self, question: str) -> Response:
        t0 = time.perf_counter()
        r = self.http.post("/chat", json={"message": question, "debug": True})
        r.raise_for_status()
        body = r.json()
        return Response(body["answer"], body.get("sources", []), time.perf_counter() - t0)

# ---- datasets.py ----
def load_goldens(folder: str, tags: list[str]) -> list[Golden]:
    goldens = []
    for f in sorted(pathlib.Path(folder).glob("*.json")):
        for row in json.loads(f.read_text()):
            if set(tags) & set(row.get("tags", [])):
                goldens.append(Golden(
                    input=row["input"],
                    expected_output=row.get("expected_output"),
                    context=row.get("context"),
                ))
    if not goldens:
        raise ValueError(f"No goldens matched tags {tags} in {folder}")
    return goldens

# ---- cases.py ----
def build_case(golden: Golden, resp: Response) -> LLMTestCase:
    return LLMTestCase(
        input=golden.input,
        actual_output=resp.output,
        expected_output=golden.expected_output,
        context=golden.context,
        retrieval_context=resp.retrieval_context or None,
    )

Aggregate pass-rate gate (for noisy suites)

Per-case assert_test is right for smoke tests where every case must pass. For large regression suites, gate on the aggregate so a single borderline judge flip doesn't block a release.

scripts/gate.py
import os, sys, json, yaml
from deepeval import evaluate
from deepeval.evaluate.configs import AsyncConfig
from evalkit.adapter import AppClient
from evalkit.datasets import load_goldens
from evalkit.cases import build_case
from evalkit.metrics_factory import build_metrics

cfg = yaml.safe_load(open("config/thresholds.yaml"))
suite = cfg["suites"][os.getenv("EVAL_SUITE", "regression")]
app = AppClient(os.environ["APP_BASE_URL"])

cases = [build_case(g, app.ask(g.input)) for g in load_goldens("data/goldens/single_turn", suite["tags"])]
result = evaluate(
    test_cases=cases,
    metrics=build_metrics(suite["metrics"], cfg["judge"]["model"]),
    async_config=AsyncConfig(max_concurrent=8),
)

passed = sum(1 for r in result.test_results if r.success)
rate = passed / len(result.test_results)
summary = {"passed": passed, "total": len(result.test_results), "pass_rate": round(rate, 4)}
json.dump(summary, open("eval_summary.json", "w"), indent=2)
print(summary)
sys.exit(0 if rate >= suite["min_pass_rate"] else 1)

15Thresholds & judge calibration

The step most teams skip, and the reason most LLM gates are either ignored or wrong.

  1. Build a calibration set. 100–300 real outputs per metric, spanning clearly good, clearly bad and borderline. Two humans label pass/fail independently; resolve disagreements.
  2. Measure human–human agreement first (Cohen's kappa). If people agree less than ~0.6, the criterion is ambiguous — rewrite the rubric before blaming the judge.
  3. Score the set with the metric and sweep thresholds from 0.3 to 0.95. For each, compute precision and recall of "fail" against human labels.
  4. Choose by cost of error. Safety metrics favour recall (catch every bad output; accept false alarms). UX metrics favour precision (don't block releases on noise).
  5. Probe variance. Run the set 3–5 times (-r). Cases whose verdict flips are your noise band; if many sit near the threshold, prefer an aggregate pass-rate gate.
  6. Record it. Commit judge model, threshold, agreement stats and date into thresholds.yaml comments or a calibration report.
  7. Re-run whenever the judge model, deepeval version, or rubric changes — and on a schedule (quarterly).
SignalInterpretationAction
Judge–human agreement ≥ 0.8Trustworthy oracleHard gate is fine
0.6 – 0.8Usable with noiseAggregate pass-rate gate; human review of failures
< 0.6Not an oracle yetTrack only; refine criteria, use evaluation_steps or a DAG, try a stronger judge
Flip rate > 10 % across repeatsThreshold sits in the noiseMove threshold, switch to strict/binary DAG, or gate on pass-rate
Tip: tighten G-EvalExplicit evaluation_steps instead of a one-line criteria make G-Eval scores markedly more stable. If you need a rubric with fixed score bands, G-Eval supports a rubric; if you need deterministic branching ("if it mentions a refund, check the amount; else…"), move to a DAG metric.

17Operational concerns

Cost & speed

  • Estimate before you run: cases × LLM metrics × ~3–6 judge calls. A 500-case suite with 4 judged metrics can mean 6,000+ calls.
  • Recent releases report judge token usage and cost per metric — export it and trend it like any other metric.
  • Use -c caching on reruns; turn off include_reason for bulk scoring; use a smaller judge for smoke if calibration allows.
  • Cap concurrency to your provider's rate limits rather than letting retries thrash.

Flakiness

  • Set app temperature to 0 (or fixed seed) in eval environments where the product allows it.
  • Distinguish infra errors (timeouts, 429s — retry, or -i) from quality failures (never retry until green).
  • DeepEval 4.1.5+ can mark metrics and test cases as flaky so they're tracked separately and warn instead of fail. Use it as a quarantine with an owner and expiry date, not a dumping ground.
  • Track per-case flip rate over time; persistent flippers need a better golden or a better rubric.

Security, privacy & compliance

  • Judge calls send your inputs, outputs and retrieved context to the judge provider. Treat that as a data flow needing approval; use a self-hosted or in-region judge for sensitive data.
  • Anonymise production samples before they become goldens; store goldens with the same classification as the source data.
  • Keep API keys in CI secrets; never in .env committed to the repo.
  • DeepEval sends anonymous usage telemetry (via PostHog, per its docs). Review the data-privacy page and opt out if your policy requires.
  • Logging into Confident AI uploads test cases. Decide deliberately which suites sync (regional endpoints for EU and AU exist).

Upgrades

  • Pin deepeval==x.y.z in a lockfile. Upgrade on a branch, never via a floating range.
  • On upgrade: read the changelog's Breaking Change section, re-run the calibration set, diff scores per metric against the previous version on a frozen snapshot of outputs, then merge.
  • Because all deepeval.metrics imports sit in the metric factory, renames touch one file.

Triage flow for a failing case

  1. Read the reason. Every metric explains itself; most triage ends here.
  2. Open the trace (deepeval inspect or Confident AI) to locate the failing span.
  3. Ask: is the test right? Check the golden's expected output and the judge's reasoning. Roughly a fifth to a third of early failures in a new suite are test defects — budget for it.
  4. Classify using the taxonomy, attach the run ID and manifest, file against the owner.
  5. Lock it in. The failing input stays in the regression set with a tag linking the defect ID.

20Checklists

Before the first gated run

  • deepeval and provider SDKs pinned in a lockfile
  • Judge model pinned, differs from the app model, credentials in CI secrets
  • Every gating metric has a calibration record (agreement, threshold, date)
  • Goldens are tagged, reviewed, and versioned; calibration set held out
  • Adapter populates every field the chosen metrics need
  • Run manifest written per run (app commit, prompt version, dataset version, deepeval version, judge)
  • Results stored outside CI logs
  • Triage owner and SLA defined for eval failures
  • Data-flow approval for sending outputs to the judge provider; telemetry/sync decisions documented

Before each release

  • Full regression above pass-rate gate and within tolerance of the previous baseline
  • Multi-turn suite green on core journeys
  • Safety metrics green; latest red-team run reviewed; no open P1
  • Flaky quarantine list reviewed; nothing critical hidden there
  • Cost and latency per request within budget
  • New production incidents since last release added as goldens
  • Run marked as baseline (e.g. --official) for the next comparison

On every deepeval upgrade

  • Changelog breaking changes read and noted in the PR
  • CLI help output re-captured and diffed
  • Calibration set re-scored; per-metric score deltas reviewed
  • Thresholds adjusted where scoring direction or formula changed

21Anti-patterns

✗

Default thresholds everywhere

0.5 is a placeholder, not a quality bar. Uncalibrated gates get ignored within a month.

✗

Metric buffet

Twelve metrics per case triples cost and drowns signal. Gate on a few; track the rest.

✗

Same model judges itself

Self-preference bias inflates scores. Use a different model family as judge.

✗

Synthetic data straight into the gate

Unreviewed synthetic goldens contain wrong "expected outputs". Review first.

✗

Retry until green

Re-running a quality failure hides real regressions. Retry infra errors only.

✗

Tuning prompts on the gate set

Overfits the suite. Keep a hidden holdout.

✗

Only end-to-end tests

You'll know it broke but not where. Add span-level metrics.

✗

Floating dependency versions

A minor release changed metric direction in 2026. Pin and upgrade deliberately.
