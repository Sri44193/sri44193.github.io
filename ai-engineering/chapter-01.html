1

Language models and tokens

What a language model actually is 📖 PDF p. 26–28

🧒 Plain English A language model has learned, from huge amounts of text, how likely each word is to come next. That's all it knows: likelihoods. Given "My favourite colour is ___", it has learned that "blue" is far more likely than "car".
🎯 Analogy Your phone keyboard's next-word suggestions, trained on most of the internet instead of your old messages.

🧱 Tokens: the model's building blocks

Models don't read whole words or single letters. They read tokens: chunks that can be a whole word, part of a word, or a character. The book's examples:

cooking→cooking
chatgpting→chatgpting
can't→can't

Why not whole words?

There are too many words. Tokens keep the list of building blocks (the vocabulary) smaller, which makes the model more efficient.

Why not single letters?

Letters carry no meaning. "cook" + "ing" still carries meaning.

Bonus

Made-up words still work: the model splits them into pieces it already knows.

📌 Remember
  • For GPT-4, 100 tokens ≈ 75 words (a token is about ¾ of a word).
  • Vocabulary = every token a model knows. GPT-4 has about 100,000; Mixtral 8x7B has 32,000.
  • Tokenization = splitting text into tokens. Each model family does it differently.
🧪 Testing angle API pricing and length limits are counted in tokens, not words or characters. When you test a "max length" rule or estimate the cost of a test run, count tokens. Non-English text often uses more tokens per character, so give it its own boundary tests.
❓ Check yourself
Roughly how many tokens is a 300-word bug report for GPT-4?
About 400. If 100 tokens ≈ 75 words, then 300 words ≈ 300 ÷ 0.75 = 400 tokens.
Why do models use tokens instead of whole words?
A smaller vocabulary (more efficient), pieces that still carry meaning, and the ability to handle words the model has never seen.
2

Two kinds of language models

Fill-in-the-blank vs. predict-what's-next 📖 PDF p. 28–30

🎭 Masked model (e.g. BERT)

Fills in a blank anywhere, using words on both sides.

My favourite ___ is blue → colour

Used for: classifying text, sentiment, understanding code around a bug.

➡️ Autoregressive model (e.g. GPT)

Predicts the next token, using only what came before.

My favourite colour is ___ → blue

Used for: generating text. This is what ChatGPT and Claude are.

🧒 Plain English An autoregressive model is a completion machine. You give it the start of a text (the prompt) and it keeps adding the most likely next token, one at a time, until it decides to stop. Many jobs can be phrased as "complete this text": translating, summarising, coding, even classifying spam ("Is this email spam? Answer: ___").
⚙️ Algorithm: how a completion is generated 
input  prompt                       # e.g. "To be or not to be"
tokens ← tokenize(prompt)
repeat:
    probs ← model(tokens)             # a likelihood for every token in the vocabulary
    next  ← pick_one(probs)          # usually a likely one, not always the top one (Ch 2)
    if next = <END>: stop          # the special "end of sequence" token
    tokens.append(next)            # the new token becomes part of the input
output detokenize(tokens after the prompt)
sequenceDiagram
  participant U as 🙂 You
  participant M as 🤖 Model
  U->>M: "To be or not to be"
  M->>M: likeliest next token? → ","
  M->>M: likeliest next token? → " that"
  M->>M: … one token at a time …
  M->>M: next token = END, so stop
  M-->>U: ", that is the question."
One token per step. That's why long answers take longer to arrive.
⚠️ Common trap A completion is a prediction based on probabilities, not a looked-up fact. It can sound confident and still be wrong. And a plain completion machine isn't a chat partner: ask it a question and it might "complete" it with another question. Extra training after the first round (Chapter 2) teaches models to actually answer.
🧪 Testing angle Because the next token is picked from probabilities, the same prompt can give different outputs. Exact-match assertions on free text will be flaky. You'll learn how to test this properly in Chapters 3–4.
❓ Check yourself
Which type of model is ChatGPT, and how do you know?
Autoregressive. It generates text left to right, one token at a time, using only what came before.
How could a completion machine act as a spam classifier?
Write the prompt so the most natural completion is the label: "Is this email spam? Email: … Answer:" and let it complete with "Likely spam" or "Not spam".

Self-supervision: the trick that made models huge

Why language models could grow when other models couldn't 📖 PDF p. 30–32

🧒 Plain English Most models learn from labelled examples: someone has to mark each photo "cat" or each transaction "fraud". Labelling is slow and expensive. A language model doesn't need anyone to label anything. Every sentence already contains its own answers: hide the next word, and the real next word is the label.
🧩 Example (my own sentence, same idea as the book's) The sentence "Tests catch bugs early." gives free training questions:
Model sees (context)Must predict (label)
<START>Tests
<START> Testscatch
<START> Tests catchbugs
<START> Tests catch bugsearly
<START> Tests catch bugs early.
<START> Tests catch bugs early .<END>
The <END> marker matters: it's how the model learns when to stop talking.
Learning styleWhere the labels come fromExample
🏷️ SupervisedHumans label every example (costly)Fraud / not fraud on each transaction
🔁 Self-supervisedThe data labels itselfNext word in a sentence
🌫️ UnsupervisedNo labels needed at allGrouping similar customers
📌 Remember
  • Labelling cost grows fast: the book estimates $50,000 to label a million images at 5¢ each, and labelling cancer scans would cost far more.
  • Parameters are the numbers inside a model that change during training. More parameters usually means more capacity to learn, and a need for more data.
  • "Large" keeps moving: GPT-1 (2018) had 117 million parameters; now 100 billion counts as large.
🧪 Testing angle The model learned from whatever text was online, nobody checked it line by line. So it absorbs the internet's errors and biases. That's a reason to test for wrong facts and biased answers, not just whether the output looks right.
❓ Check yourself
Self-supervised vs unsupervised: what's the difference?
Self-supervised learning still has labels, but they're taken from the data itself (the next word). Unsupervised learning uses no labels at all.
Why did self-supervision let language models become "large"?
It removed the labelling bottleneck. Any text anywhere becomes training data for free, so the training sets (and models) could grow enormously.

More senses, and one model for many jobs 📖 PDF p. 32–35

🧒 Plain English Text-only models were extended to understand images, audio, video too. A model that handles more than one kind of input is multimodal. The book calls these big, general models foundation models, because so many products are built on top of them.

🎯 Analogy: a new hire Prompt engineering = a clear brief for each task. RAG = handing them the right documents for each task. Finetuning = sending them on a training course so the skill becomes part of them.

❓ Check yourself
Someone "trained ChatGPT" by pasting their old diary into the chat. What did they really do?
Prompt engineering. They gave the model context in the input; the model's weights never changed. (The book uses exactly this example, PDF p. 66.)
6

Why AI engineering took off now

Three forces at once 📖 PDF p. 36–39

🧒 Plain English AI engineering = building applications on top of models someone else already trained. Classic ML engineering mostly meant building your own models.
🦾

1 · Models can do much more

Anything involving communication can be partly automated: emails, support replies, explaining contracts, images, code.

💰

2 · Money is pouring in

Cheaper and faster to build means better returns. One team saw their AI costs drop about 100× in a year.

🚪

3 · Easy to start

One API call gets you a powerful model, and you can instruct it in plain English. No GPUs or ML degree needed.

🧪 Testing angle "Low barrier to entry" means many teams ship AI features without ML experience, which is where QA becomes essential. Someone has to ask "how do we know it works?".

What people build with foundation models

Eight families of use cases 📖 PDF p. 40–52

💻

Coding

The #1 use case: completion, tests, docs, translating between languages. Biggest gains on simple tasks.

🎨

Images & video

Creative work suits AI's randomness: ads, headshots, design.

✍️

Writing

Emails, reports, marketing copy. In one study, people were ~40% faster with ~18% better quality.

🎓

Education

Personalised lessons, quizzes, tutoring (like these notes!).

💬

Conversational bots

Customer support, product copilots, companions, smart game characters.

🗞️

Information aggregation

Summaries and "talk to your documents".

🗂️

Data organisation

Pull structured data out of PDFs, receipts, contracts; search photos.

🤖

Workflow automation

Booking, invoicing, data entry. AI that plans and uses tools is called an agent (Ch 6).

📌 Remember Companies ship internal tools first (lower risk), and many AI apps are still close-ended (e.g. classification) because those are easier to evaluate.
🧪 Testing angle Notice the pattern: how easy something is to evaluate shapes what companies dare to ship. As a QA lead, making open-ended features measurable is how you unlock riskier, more valuable products.

Increase automation only as quality is proven (a Microsoft framework cited in the book)
🧩 Example A support chatbot starts by suggesting replies to human agents. If agents send ~95% of suggestions for simple requests unchanged, let the bot answer those simple requests directly.
🛡️ Defensibility (moats) If it's easy for you to build, it's easy for competitors too. The three advantages are technology (mostly the same for everyone now), distribution (big companies win), and data: usage data from shipping first can become your edge.
🧪 Testing angle Crawl-Walk-Run is a release-gating strategy, and QA owns the gates. "% of AI suggestions accepted unchanged by humans" is a measurable exit criterion for moving from Crawl to Walk.
❓ Check yourself
Why do proactive AI features need a higher quality bar than reactive ones?
Users didn't ask for them. A poor unrequested suggestion feels intrusive, while a poor answer to a question you asked is more easily forgiven.

Setting goals, and the "last mile"

Success metrics, milestones, maintenance 📖 PDF p. 56–60

🎯 Two kinds of goals

📈 Business metrics

For a support bot: % of messages automated, messages handled, response speed, staff hours saved, plus customer satisfaction.

🚦 Usefulness threshold

How good it must be before customers see it: quality, latency, cost per request, plus fairness and explainability.

TTFT
Time to first token: how long until the answer starts appearing.
TPOT
Time per output token: how fast it keeps typing after that.
Total latency
Time for the whole answer. "Fast enough" depends on the use case: if humans take an hour today, a minute is a big win.

🏔️ The last mile is the hardest

LinkedIn's experience, quoted in the book:

Month 1
80% of the target experience
Months 2–5
4 more months to pass 95%
⚠️ Common trap A great demo in a weekend makes teams badly underestimate the remaining work. Going from 0 to 60 is easy; from 60 to 100 is very hard, mostly fixing rough edges and hallucinations (confident, made-up answers).

🚄 Maintenance: riding a bullet train

Models, prices and laws change fast. The cheapest option today can be the most expensive in three months. Switching models is getting easier because APIs look alike, but each model has its own quirks, so prompts and data need re-tuning.

🧪 Testing angle The book says that without versioning and evaluation infrastructure, switching models "can cause a lot of headaches". That's a regression suite for AI: fixed test cases you re-run whenever the model, prompt or provider changes. You'll build one in Week 3.
❓ Check yourself
Your demo answered 8 of 10 test questions correctly after one week. What should you tell your manager about the release date?
That the last 20% will likely take much longer than the first 80% (the "last mile"). Agree on a usefulness threshold, measure against a larger test set, and plan for months, not days.

The three layers of the AI stack

Start at the top, go down only when needed 📖 PDF p. 60–63

🧩 Application developmentPrompts and context, evaluation, user interface. Most activity happens here, and it's where you start.
🧠 Model developmentTraining and finetuning, dataset engineering, inference optimisation, evaluation.
🏗️ InfrastructureServing models, managing data and compute (GPUs), monitoring.
📌 What didn't change Old ML lessons still apply: link business metrics to model metrics, experiment systematically (now with models, prompts and retrieval settings instead of only hyperparameters), make things faster and cheaper, and learn from production feedback.
🧪 Testing angle Notice that evaluation appears in two layers. It isn't a phase at the end; it runs through the whole stack.

AI engineering vs ML engineering

What's actually different 📖 PDF p. 63–68

🔁

1 · Adapt, don't build

You use someone else's model, so the work is adapting it, not training it.

🐘

2 · Bigger models

More compute and slower responses, so speed and cost tuning matter more.

🌊

3 · Open-ended outputs

Many possible good answers, so evaluation is a much bigger problem.

🧩 Latency maths (from the book) Tokens come out one after another. At 10 ms per token, a 100-token answer takes 1 second, and users expect ~100 ms from typical web apps. That's why speed tuning matters so much.
🧪 Testing angle Labelling open-ended outputs is much harder than labelling close-ended ones: deciding "spam or not" is easy, judging an essay is hard. Expect to spend real effort building reference answers and scoring rules. That's the core of the job you're training for.

The application layer: evaluation, prompts, interfaces

Where teams now compete 📖 PDF p. 68–72

🧒 Plain English When everyone uses the same few models, the model is no longer your advantage. How you use it is. That happens in three places: evaluation, prompt engineering (plus context), and the AI interface.

🔍 Evaluation: the lesson from Google Gemini

Google reported Gemini beating GPT-4 on a well-known benchmark (MMLU). But Gemini had been tested with a different prompting method (32 worked examples vs 5). Same model, different prompting:

Gemini Ultra · 5 examples
83.7%
Gemini Ultra · CoT@32
90.04%
🧪 Testing angle: compare like with like A score only means something together with how it was measured. When you compare two models or two prompt versions, fix everything else: same test set, same prompting method, same settings. In QA terms, control your test conditions.

✍️ Prompt engineering and context

Prompting is more than instructions. It's also giving the model the context and tools it needs, and for long tasks, a way to remember what happened earlier (Chapters 5–6).

🖥️ AI interfaces

Standalone apps (ChatGPT), plug-ins (Copilot in VS Code), browser extensions, bots in Slack or WhatsApp, voice. Chat makes it easy for users to give feedback in plain language, but that feedback is harder to analyse (Chapter 10).

❓ Check yourself
A vendor says "our model scores 90%, theirs scores 87%". What's your first question?
"Measured how?" Same test set? Same prompting method and number of examples? Same settings? Without equal conditions, the comparison means nothing.
Name the three parts of the application layer.
Evaluation, prompt engineering (and context construction), and the AI interface.

✅ One-page cheat sheet

  1. 🔤 A language model predicts likely next tokens. 100 tokens ≈ 75 words.
  2. ➡️ Autoregressive models (GPT, Claude) generate one token at a time. Outputs are probabilistic, not guaranteed facts.
  3. 🔁 Self-supervision: text labels itself, so models could train on the whole internet and become "large".
  4. 🧠 Foundation models = large, often multimodal, general-purpose, and built upon.
  5. 🛠️ Adapt a model with prompting (no weight change), RAG (add retrieved facts), or finetuning (change weights).
  6. 🚀 AI engineering grew from capability + investment + easy access.
  7. 🤔 Before building, ask why, the AI's role, the human's role (Crawl → Walk → Run), and your moat.
  8. 🎯 Set business metrics and a usefulness threshold (quality, latency TTFT/TPOT, cost).
  9. 🏔️ The last mile (60→100%) takes far longer than the demo (0→60%).
  10. 🏗️ Stack: application → model → infrastructure. Start at the top.
  11. 🌊 AI vs ML engineering: less training, bigger models, open-ended outputs, which makes evaluation the hard part.
  12. 🔍 Compare scores only under equal test conditions (the Gemini lesson).
