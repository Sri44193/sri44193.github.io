The big picture

The whole chapter on one page. Come back here after each topic.

📌 The chapter in one sentence Open-ended AI output can't be checked against one right answer, so you need a mix of methods: exact ones (run the code, compare to references) and subjective ones (an AI judge, or ranking models against each other). Each has blind spots, so never rely on just one.
🧩 Why it matters (from the chapter's opening) A chatbot encouraged a man who later took his own life. Lawyers submitted evidence an AI made up. Air Canada had to pay damages after its chatbot gave a passenger false information. Without quality control, AI's risks can outweigh its benefits. For some teams, working out evaluation is most of the development effort.

Why evaluating foundation models is hard

Five reasons, and why teams settle for "vibe checks" 📖 PDF p. 138–142

🎓

1 · Smarter = harder to check

Anyone can spot a wrong first-grade sum; few can check a PhD proof. A fluent summary may need you to read the whole book to verify it.

🌊

2 · Open-ended

So many correct answers that you can't list them all to compare against.

📦

3 · Black boxes

Providers hide architecture and training data, so you can only judge by outputs.

💯

4 · Benchmarks saturate

Models hit the top score quickly. GLUE (2018) was saturated within a year; MMLU (2020) was largely replaced by MMLU-Pro (2024).

🔭

5 · Wider scope

You're not only checking known tasks, but also discovering what the model can and can't do.

⚠️ Common trap: the vibe check Because evaluation is hard, many teams judge by word of mouth or by eyeballing a few favourite prompts (in one survey, 6 of 70 decision makers chose models by word of mouth). That might do for a prototype, never for iterating a product.
🧪 Testing angle The book notes that evaluation gets far less investment and tooling than model building. That gap is the opportunity for a QA lead for AI: bring systematic test design where others are eyeballing. Also: design for observability. The book says you may need to redesign a system just so its failures become visible.

Entropy and cross entropy

How "surprised" a model is by text 📖 PDF p. 142–145

🧒 Plain English These are the scores used while training a language model. They measure how well the model predicts the next token. Lower = better predictions. You won't compute them daily, but they show up in model reports and in a few evaluation tricks (topic 3).
🧩 Entropy, with the book's square example

Language A: 2 tokens

"upper" / "lower". Needs 1 bit per token. Entropy = 1. Easy to predict.

Language B: 4 tokens

upper-left / upper-right / lower-left / lower-right. Each token tells you more, but needs 2 bits. Entropy = 2. Harder to predict.

Entropy = how much information each token carries = how hard the next token is to guess. If you can perfectly predict what I'll say, what I say carries no new information.
Cross entropy
How hard it is for a model to predict the next token in some text. It equals the text's own entropy plus how far the model's learned picture is from the real thing (the KL divergence). A perfect model's cross entropy equals the data's entropy.
Bits per character (BPC)
Cross entropy per character, so models with different tokenizers can be compared. 6 bits per token ÷ 2 characters per token = 3 BPC.
Bits per byte (BPB)
Per byte of original text, which avoids character-encoding differences. 3 BPC with 7-bit characters → 3 ÷ ⅞ = 3.43 BPB, i.e. the model could compress text to less than half its size.
📌 Remember All four metrics (cross entropy, perplexity, BPC, BPB) are versions of the same idea: how well the model predicts text. Know one and the others can be calculated. Units can be bits (base 2) or nats (base e, used by PyTorch and TensorFlow), a common source of confusion.

Perplexity, and its surprising uses

"How many options was the model torn between?" 📖 PDF p. 145–149

🧒 Plain English Perplexity turns cross entropy into an intuitive number: roughly how many equally likely choices the model felt it had for each next token. A model that perfectly learned the 4-position language has perplexity 4. Lower = more confident = better at predicting that text.
⚙️ Algorithm: perplexity of a sentence (my own numbers) 
input  probs = [0.5, 0.25, 0.5]        # probability the model gave each actual next token
n ← len(probs)                         # 3 tokens
joint ← product(probs)                 # 0.5 × 0.25 × 0.5 = 0.0625
perplexity ← joint ^ (−1 / n)          # 0.0625 ^ (−1/3) ≈ 2.52
# ≈ the model was "choosing between about 2.5 options" per token.
# Needs the model's token probabilities (logprobs), which many APIs don't expose.

📉 Lower perplexity when…

The text is more structured (HTML is more predictable than chat) · the model sees more context.

📈 Higher perplexity when…

The vocabulary is bigger (War and Peace vs a children's book) · the text is unusual or gibberish.

🛠️ Uses beyond training

🔍 Detect contamination

If a model has suspiciously low perplexity on a benchmark's questions, it probably saw them in training, so its score there can't be trusted.

🧹 Deduplicate data

Only add new training text if the model finds it surprising (high perplexity).

🚨 Spot abnormal text

Gibberish ("home cat go eye") or very odd claims get high perplexity.

⚠️ Common trap Perplexity is a poor guide for post-trained chat models. SFT and RLHF teach a model to complete tasks, which usually makes it worse at raw next-token prediction, so its perplexity goes up even though it's more useful. Quantisation (Chapter 7) can shift it unpredictably too.
🧪 Testing angle When a vendor reports a great benchmark score, ask whether contamination was checked. Perplexity on the benchmark data is one way to check.

Exact evaluation: functional correctness

Does it actually do the job? 📖 PDF p. 149–151

🎯 Exact evaluation

No ambiguity: answer A was expected, B was given, so it's wrong.

🧑‍⚖️ Subjective evaluation

Depends on who grades, like essay marking. AI judges fall here: change the judge model or prompt and the score changes.

🧒 Plain English Functional correctness asks: does the output do what it was meant to? Did the generated website meet the requirements? Did the booking actually happen? It's the ultimate metric, but it's often hard to automate. Code is the easy case: just run it.
🎯 Analogy: unit tests This is exactly how LeetCode and HackerRank grade submissions, and how you already test code: run it against test cases. For AI-written code it's called execution accuracy. Benchmarks: HumanEval, MBPP (code); Spider, BIRD-SQL, WikiSQL (text-to-SQL).

How code benchmarks check functional correctness
⚙️ Algorithm: pass@k 
solved ← 0
for problem in problems:
    samples ← generate(problem, k)        # k attempts per problem
    if any(passes_all_tests(s) for s in samples):
        solved ← solved + 1
pass_at_k ← solved / len(problems)        # 10 problems, 5 solved with k = 3 → pass@3 = 50%
# More attempts = more chances, so pass@1 ≤ pass@3 ≤ pass@10.
🧪 Testing angle Whenever a task has a measurable outcome (code runs, SQL returns the right rows, a game score, energy saved), prefer functional correctness to "does it look right". And when comparing pass@k numbers, check that k is the same.
❓ Check yourself
Why is pass@10 usually higher than pass@1?
A problem counts as solved if any of the k samples passes. Ten tries give more chances than one.

Reference data: exact match and lexical similarity

Comparing outputs to known good answers 📖 PDF p. 151–156

🧒 Plain English If you can't run the output, compare it with reference answers (also called ground truths). Metrics that need references are reference-based; ones that don't are reference-free. References are usually written by people, increasingly by AI and then reviewed.

1 · Ask an evaluator

A human or AI decides whether two texts mean the same (topic 7).

2 · Exact match

Identical to a reference: yes/no.

3 · Lexical similarity

How much the words overlap: a score.

4 · Semantic similarity

How close the meaning is: a score (topic 6).

✅ Exact match

Works for short, exact answers: "What's 2 + 3?", "What's my account balance?", trivia. A looser version accepts any output that contains the reference ("The answer is 5").

⚠️ Common trap: "contains" can accept wrong answers Q: "What year was Anne Frank born?" Reference: 1929. The output "September 12, 1929" contains 1929, but the date is wrong (she was born 12 June). And for anything longer than a fact, exact match fails: "How is it going?" is a fine translation of "Comment ça va?" but won't match a reference list that doesn't include it.

🔤 Lexical similarity

🧩 Word overlap (the book's example) Reference: "My cats scare the mice"
"My cats eat the mice"
4 of 5 words · 80%
"Cats and mice fight all the time"
3 of 5 words · 60%
Edit distance
"Fuzzy matching": how many deletions, insertions or substitutions turn one text into another. "bad" → "bard" is 1 edit; "bad" → "cash" is 3.
n-gram
A run of n tokens. "My cats scare the mice" has 4 bigrams: my cats · cats scare · scare the · the mice. Similarity = how many reference n-grams appear in the output.
BLEU, ROUGE, METEOR++, TER, CIDEr
Classic lexical metrics, common in translation before foundation models; less used now.
⚠️ Three ways lexical scores mislead
  • Missing references: a correct answer scores low if no reference resembles it (Adept's Fuyu model was marked down for correct captions).
  • Wrong references: the WMT 2023 organisers found many bad reference translations in their own data.
  • Look-alike ≠ correct: on HumanEval, correct and incorrect code got similar BLEU scores.
🧪 Testing angle Use exact match for short, factual answers and labels, with careful normalisation (case, spacing, number formats). For anything longer, word overlap is a weak signal. Don't gate a release on BLEU alone.

Semantic similarity and embeddings

Comparing meaning, not wording 📖 PDF p. 156–160

Different words, same meaning

"What's up?" vs "How are you?" Little word overlap, close meaning.

Same words, different meaning

"Let's eat, grandma" vs "Let's eat grandma". Nearly identical, very different.

🧒 Plain English An embedding is a list of numbers that tries to capture what a piece of text (or image, or audio) means. Texts with similar meanings should get similar lists. "The cat sits on a mat" might become [0.11, 0.02, 0.54]; real embeddings have 100 to 10,000 numbers.

Semantic similarity: embed both texts, then measure the angle between them
⚙️ Algorithm: cosine similarity (my own tiny vectors) 
input  A = [1, 2, 2],  B = [2, 1, 2]
dot   ← 1×2 + 2×1 + 2×2               # = 8
lenA  ← sqrt(1² + 2² + 2²)            # = 3
lenB  ← sqrt(2² + 1² + 2²)            # = 3
return dot / (lenA × lenB)             # 8 / 9 ≈ 0.89 → very similar

📌 Remember
  • Metrics: BERTScore, MoverScore. Needs fewer references than lexical matching.
  • A good embedding model puts "the cat sits on a mat" closer to "the dog plays on the grass" than to "AI research is super fun". Benchmark: MTEB.
  • Multimodal embeddings (CLIP) put images and text in one space, so a photo of a man fishing lands near the text "a fisherman". That's what makes text-to-image search work.
  • Embeddings return in Chapter 6 (RAG and vector search) and Chapter 8 (deduplication).
⚠️ Common trap Semantic similarity is only as good as the embedding model: with bad embeddings, two answers that mean the same can still score low. It also costs compute to run. And note "Let's eat, grandma": embeddings may not catch a small change that flips the meaning.

AI as a judge: why, and three ways to use it

Using a model to grade a model 📖 PDF p. 160–163

🧒 Plain English An AI judge (or LLM-as-a-judge) is an AI model asked to evaluate another AI's output. It became practical around 2020 with GPT-3, and is now one of the most common evaluation methods in production. On LangChain's platform in 2023, 58% of evaluations used AI judges.

⚡ Fast and cheap

Much cheaper and quicker than human reviewers.

📭 No reference needed

Works in production, where there's no "right answer" to compare against.

🎛️ Any criterion

Correctness, toxicity, hallucination, tone, "does this sound like Gandalf?"

💬 Explains itself

Can give the reason for a score, which helps when auditing results.

🧩 How well do judges agree with people?
GPT-4 vs humans
85% agreement
Humans vs humans
81% agreement

On the MT-Bench benchmark (Zheng et al., 2023). AlpacaEval's judges also correlated 0.98 with a human-voted leaderboard.

🧰 Three ways to use a judge

ModeWhat the judge seesOutput
1 · Score it aloneQuestion + answerA score, e.g. 1–5
2 · Compare to a referenceQuestion + reference + answerSame as the reference? True/False
3 · Compare two answersQuestion + answer A + answer BWhich is better: A or B. Also used for preference data and best-of-N
⚠️ Common trap: built-in criteria aren't standard Azure AI Studio, MLflow, LangChain and Ragas all ship criteria like "relevance" or "faithfulness", but each tool defines and scores them differently. "Relevance 4" in one tool isn't "relevance 4" in another.

🧪 Testing angle Treat the judge prompt like test code: version it, review changes, and keep the judge's model and sampling settings fixed. If any of them change, re-check the judge against a small human-labelled set before trusting its new scores.

Limits and biases of AI judges

Why a judge's score can't be taken at face value 📖 PDF p. 165–169

🎲

Inconsistency

Same input, different scores. Adding examples raised GPT-4's consistency from 65% to 77.5%, but quadrupled its cost. And consistent isn't the same as correct: a judge can make the same mistake every time.

🌫️

Criteria ambiguity

"Faithfulness" is scored 1–5 in MLflow, 0/1 in Ragas and YES/NO in LlamaIndex. These scores can't be compared.

🔄

The judge changes

Coherence went from 90% to 92%. Did the app improve, or did someone fix a typo in the judge prompt and make it more lenient?

💸

Cost and latency

Judging with the same model doubles API calls; three criteria makes it 4×. Judging before replying adds latency. Spot-checking (judging a sample) cuts cost but can miss failures.

⚠️ The book's rule "Do not trust any AI judge if you can't see the model and the prompt used for the judge."

🧲 Three common biases

BiasWhat happensMitigation
🪞 Self-biasJudges favour their own answers. GPT-4: ~10% higher win rate for itself; Claude-v1: ~25%Use a judge from a different model family
🥇 First-position biasFavours the first answer shown (humans tend to favour the last)Run each comparison twice with the order swapped
📏 Verbosity biasPrefers longer answers: GPT-4 and Claude-1 preferred ~100-word answers with factual errors over correct ~50-word onesPut length guidance in the rubric; stronger judges suffer less
📌 Remember Judges also share every AI risk: privacy (you send data to a provider) and IP (unknown training data). The book's conclusion: use AI judges, but always supplement them with exact evaluation, human evaluation, or both.
🧪 Testing angle These biases give you ready-made test cases for your judge: swap answer order (does the verdict flip?), pad a wrong answer with extra words (does its score rise?), and include answers written by the judge's own model family.
❓ Check yourself
Your judge prefers answer A in an A-vs-B comparison. What's the cheapest check for position bias?
Run it again with the order swapped (B shown first). If the verdict flips, position is influencing the judge.
Your judge became more consistent after you added examples. Does that mean it's more accurate?
No. Consistency means it gives the same answer each time; it can still be consistently wrong. Check accuracy against human labels.

Which model should be the judge?

Stronger, weaker, itself, or a specialist 📖 PDF p. 169–172

💪 Stronger judge

Makes sense (the examiner should know more). Pattern: a cheap model generates; a strong model checks a sample, e.g. 1%, or runs in the background and swaps in its own answer when needed. Catch: who judges the strongest model?

🪞 Self-evaluation

Sounds like cheating (self-bias), but useful as a sanity check, and asking a model to critique itself can make it revise: "10+3 = 30" → "Is this correct?" → "No, it's 13."

🐜 Weaker judge

Judging may be easier than creating: anyone can say whether a song is good. Stronger judges did correlate better with humans in one study, though.

🎯 Specialised judges

TypeInput → outputExamples
Reward model(prompt, answer) → quality scoreGoogle's Cappy: 360M parameters, score 0–1
Reference-based judge(answer, reference) → similarity or quality scoreBLEURT (odd range, about −2.5 to 1) · Prometheus: adds a rubric, scores 1–5
Preference model(prompt, answer 1, answer 2) → which is betterPandaLM (explains its choice) · JudgeLM
📌 Remember The book is excited about small, specialised judges: trained for one criterion and one scoring system, they can be more reliable than big general models for that judgement, and much cheaper.

Ranking models with comparative evaluation

Head-to-head matches instead of individual scores 📖 PDF p. 172–175

📝 Pointwise

Score each model on its own, then sort. Like scoring each dancer separately.

🥊 Comparative

Put models side by side and ask which is better. Like a dance-off. Usually easier for subjective quality: picking the better of two songs is easier than scoring each.

How a comparative leaderboard is built
Win rate
The share of A-vs-B matches that A won.
Rating algorithm
Turns match results into a score per model. Borrowed from chess and games. Chatbot Arena moved from Elo to Bradley–Terry because Elo was sensitive to the order of evaluators and prompts.
A correct ranking
One that predicts future matches: if A ranks above B, A should win more than half the time. There's no single ground truth.
⚠️ Common trap: preference isn't correctness Don't decide factual questions by vote. "Is there a link between phone radiation and brain tumours? Yes / No" should be answered by evidence, not popularity, and training on such votes can misalign a model. Voting works best when voters know the subject: AI as an assistant for tasks the user can do, not tasks they can't.
📌 Comparative ≠ A/B testing In A/B testing, each user sees one version. In comparative evaluation, a user sees several at once and picks.

The limits, and the future, of comparative evaluation

Scale, quality control, and "better" vs "good enough" 📖 PDF p. 176–180

📈

Scale

Pairs grow with the square of the number of models. In January 2024, LMSYS ran 244,000 comparisons for 57 models, only ~153 per pair across 1,596 pairs. Rankings assume transitivity (A>B and B>C means A>C), which may not hold for AI. New and private models are hard to slot in.

🎭

Quality control

Crowd voters may not fact-check, may reward rude answers, or pick at random. Of 33,000 published Arena prompts, 180 were just "hello" or "hi"; one brainteaser appeared 44 times. Easy prompts don't separate models.

⚖️

Better ≠ good enough

"B beats A" doesn't say whether either is good. If A resolves 70% of support tickets and B wins 51% of matches, how many tickets will B resolve? And is it worth B's extra cost?

📌 Why it still has a future
  • Comparing stays possible even when models outgrow human experts' ability to score them.
  • It measures what we care about: human preference.
  • It never saturates: new models keep arriving.
  • It's hard to game: no reference answers to train on.
Fixes in use: filter to hard prompts (LMSYS), trained private evaluators (Scale), comparisons built into products.
🧪 Testing angle Public leaderboards don't test your prompts, your documents (RAG) or your users. Use them to shortlist models, then run your own evaluation, and include cost in the decision.

✅ One-page cheat sheet

  1. 🚨 Evaluation is the biggest hurdle to shipping AI, and it's under-invested. Avoid vibe checks.
  2. 📉 Cross entropy and perplexity measure how well a model predicts text; lower = better. Perplexity ≈ number of options it was torn between.
  3. 🔍 Perplexity helps detect contamination (suspiciously low on a benchmark), deduplicate data and spot abnormal text. Post-trained models have higher perplexity.
  4. 🎯 Exact evaluation = unambiguous verdict. Subjective = depends on the judge.
  5. ▶️ Functional correctness (run it) is the ultimate metric where possible. pass@k = solved by any of k samples.
  6. 🔤 Exact match for short answers only; "contains" can accept wrong answers. Lexical scores (BLEU, ROUGE) measure word overlap, not correctness.
  7. 🧠 Semantic similarity compares embeddings with cosine similarity; only as good as the embedding model.
  8. 🧑‍⚖️ AI judges are fast, cheap and need no reference. GPT-4 agreed with humans 85% of the time.
  9. ✍️ Judge prompt = task + criteria + scoring system + examples. Labels beat numbers; small ranges beat big ones.
  10. ⚠️ Judges are inconsistent, non-standard and can drift. Biases: self, first-position, verbosity. Never trust a judge you can't inspect.
  11. 🐜 Judges can be stronger, weaker, the same model, or small specialists (reward, reference-based, preference models).
  12. 🥊 Comparative evaluation ranks models from head-to-head matches; doesn't scale easily and doesn't tell you "good enough".

  1. Pick a small LLM feature, e.g. summarising bug reports.
  2. Write 30 test cases: input plus a reference summary or a checklist of must-have facts.
  3. Score with three methods: exact-match checks for key fields (severity, component), word overlap against the reference, and embedding similarity.
  4. Find a case where word overlap is high but the summary is wrong, and one where overlap is low but the summary is fine. Those are the limits from topic 5.
  5. Bonus: write a judge prompt using topic 8's four parts, judge 10 summaries twice with the order swapped, and see whether any verdicts flip.
