The big picture

The whole chapter on one page. Come back here after each topic.

📌 The chapter in one sentence Finetuning changes a model's weights to fit your task. It's powerful but costly, so try prompting and RAG first. "Finetuning is for form, RAG is for facts." Most of the clever techniques (quantisation, PEFT, LoRA) exist to cut finetuning's huge memory needs.
🧪 Why a QA lead should read this You may never finetune yourself, but you'll test finetuned models: did the target task improve, did other tasks get worse, does a smaller or quantised version keep quality? This chapter tells you what can go wrong.

What finetuning is

Transfer learning by further training 📖 PDF p. 331–335

🧒 Plain English Prompting and RAG change what goes into a model. Finetuning changes the model itself by training it a bit more on your data. It's most often used to improve instruction following, especially sticking to a required style or format.
🎯 Analogy: transfer learning Knowing piano makes learning another instrument easier. A model that learned general language can learn legal Q&A from a few hundred examples instead of millions. Google's translator even learned Portuguese→Spanish without any Portuguese–Spanish examples, by transferring from Portuguese→English and English→Spanish.
Type of finetuningData it usesExample
Continued pre-trainingCheap raw text, no labelsRaw legal documents before legal Q&A; Vietnamese text before Vietnamese summarisation
InfillingFill-in-the-blank examplesText editing, code debugging
Supervised (SFT)(instruction, response) pairsTeach a format or behaviour
Preference(instruction, winner, loser)Align with what users prefer (Ch 2)
Long-contextLong sequences + architecture changesCode Llama: 4,096 → 16,384 tokens. Hard, and can hurt short inputs
📌 Remember InstructGPT's paper describes finetuning as unlocking abilities the model already has but that are hard to reach by prompting. App developers usually finetune an already post-trained model: the closer it is to your task, the less work.
2

Reasons to finetune, and reasons not to

Start with prompting; finetune only when it isn't enough 📖 PDF p. 335–338

✅ Reasons to finetune

• Better quality on your task (e.g. a rare SQL dialect, customer-specific queries)
• Reliable structured output (JSON, YAML)
• Bias mitigation: finetuning on text with female CEOs, or written by women or by African authors, reduced biases
• Make a small model excellent: Grammarly's finetuned Flan-T5 beat a GPT-3 text-editing variant while 60× smaller, using 82,000 examples
• Distillation: train a small model to imitate a big one (Ch 8)

❌ Reasons not to

• Better at one task, worse at others
• Needs data (slow and costly to label)
• Needs ML skills: optimisers, learning rates, overfitting
• You must host and serve it
• Maintenance: new base models may soon beat your finetuned one

🧩 The "other tasks got worse" problem A model handles product recommendations and general feedback well but is weak at changing orders. You finetune it on order changes: those improve, and the other two get worse. Fixes: finetune on all the query types, use separate models, or merge models (topic 11).
⚠️ A story practitioners keep telling the author Someone insists prompting doesn't work and they need to finetune. On inspection, the prompt experiments were minimal and unsystematic: unclear instructions, unrepresentative examples, poorly defined metrics. With a proper prompt process, the prompts turned out good enough.
🧪 Testing angle After any finetune, run the full regression suite, not just the target task's tests. The book calls the drop in other skills an "alignment tax". Your existing evaluation pipeline from prompting is exactly what makes finetuning safe.

  • Finetuning used to save tokens (examples baked in rather than in every prompt); prompt caching (Ch 9) now covers much of that. Finetuning still allows unlimited examples; prompts are limited by context length.

Trainable parameter
A weight that gets updated during finetuning. Unchanged ones are frozen.
Gradient
One extra number per trainable parameter, saying how to adjust it.
Optimiser state
Extra numbers the optimiser keeps per trainable parameter: SGD 0, momentum 1, Adam 2 (most common for transformers).
📌 The key insight More trainable parameters = more memory, because each one drags along a gradient and optimiser states. Reducing trainable parameters is the whole point of PEFT (topic 9).

Memory maths

Back-of-the-napkin estimates for hardware 📖 PDF p. 346–349

⚙️ Algorithm: memory to RUN a model (inference) 
N ← 13 billion parameters
M ← 2 bytes per parameter                # 16-bit format
weights ← N × M                          # = 26 GB
total   ← weights × 1.2                  # +20% for activations and attention keys/values ≈ 31.2 GB
# A 24 GB GPU won't fit it. A 70B model needs 140 GB just for its weights.
# Longer contexts or bigger batches need more than the 20% allowance.
⚙️ Algorithm: extra memory to TRAIN with Adam 
training ← weights + activations + gradients + optimizer_states
# Per trainable parameter: 1 gradient + 2 Adam states = 3 values, at 2 bytes each
all 13B trainable:   13 billion × 3 × 2 bytes = 78 GB extra
only 1B trainable:    1 billion × 3 × 2 bytes =  6 GB extra
13B: run it
≈31 GB
13B: train every parameter
26 GB weights + 78 GB extra ≈ 104 GB+

Before counting activations, which during training can be far larger than the weights.

📌 Gradient checkpointing Don't store activations; recompute them when needed. Saves memory, costs training time.
🧪 Testing angle The book notes you're not really doing AI until you've seen a "CUDA out of memory" error. For performance tests of self-hosted models, include long inputs and bigger batches: memory grows with both, and that's where out-of-memory failures appear.

Number formats

How many bits each value uses 📖 PDF p. 349–352

🧒 Plain English Every weight is stored as a number in a format. Fewer bits = less memory, but less range (how big or small a number can be) and/or less precision (how many digits survive).
FormatBitsNotes
FP64 (double)64Default in NumPy/pandas; rarely used in neural networks
FP32 (single)32The traditional standard for training
TF3219 (!)NVIDIA's format, named to sound compatible with FP32
FP16 (half)16More precision, less range
BF1616Google's format: more range, less precision
INT8 / INT48 / 4Integer formats, increasingly popular for serving
🧩 What happens when FP32 values are squeezed (from the book's table)

1234.567891235.0 (0.035% off)1232.0 (0.208% off)

⚠️ Common trap: loading the wrong format Llama 2's weights were released in BF16. Many teams loaded them in FP16 and found quality much worse than advertised. Always load a model in the format it was made for.
🧪 Testing angle "Same model, different format" is a real source of regressions. When a team changes how a model is loaded or served, re-run the quality suite and compare against the reference format.

Quantisation

Fewer bits per value: cheaper, smaller, often faster 📖 PDF p. 352–356

🧒 Plain English Quantisation = storing values with fewer bits. A 10B model needs 40 GB in 32-bit and 20 GB in 16-bit. It's cheap, easy and works across tasks and architectures. (Strictly, the word means converting to integers; the book uses it for any precision reduction.)

❓ What to quantise

Usually the weights (more stable) rather than activations.

⏰ When

Post-training quantisation (PTQ), after training, is by far the most common: a few lines of code in PyTorch or Hugging Face.

32-bit
traditional
16-bit
common for serving
8 / 4-bit
LLM.int8 · QLoRA
~1.58-bit

Bar length ≈ bits per value. Apple serves on-device models at about 3.5 bits per weight (a mix of 2- and 4-bit); NVIDIA's Blackwell GPUs support 4-bit floats. Microsoft's BitNet b1.58 (1.58 bits) roughly matched 16-bit Llama 2 at sizes up to 3.9B.

✅ Benefits

Less memory, bigger batches, often faster maths (16 bits can be processed in roughly half the time of 32).

⚠️ Costs

Many small rounding changes can add up to a big quality drop; out-of-range values become infinity; format conversion can eat the speed gain.

Quantisation-aware training (QAT)
Simulate low precision while training so the model works well when quantised later. Doesn't speed training up.
Low-precision training
Actually train in fewer bits. Character.AI trained entirely in INT8. Harder: training is sensitive to rounding.
Mixed precision
Sensitive parts in higher precision, the rest lower; often set automatically (AMP).
🧪 Testing angle A quantised model is effectively a new model: run your evaluation suite on it, compare with the full-precision baseline per slice, and decide with a threshold (e.g. "no more than 1% drop on critical intents").

Parameter-efficient finetuning (PEFT)

Train a tiny fraction of the parameters 📖 PDF p. 356–362

🧩 Why full finetuning is out of reach (7B model, 16-bit, Adam) Weights 14 GB + gradients and optimiser states 7B × 3 × 2 bytes = 42 GB → 56 GB, before activations. Consumer GPUs have about 12–24 GB (high-end 48 GB). One workaround: CPU offloading (DeepSpeed) moves the overflow to CPU memory.

🧊 Partial finetuning

Freeze most layers, train the last ones. Saves memory but is parameter-inefficient: BERT needed ~25% of its parameters trained to match full finetuning.

🔌 Adapters (the first PEFT)

Insert small new modules and train only those. Got within 0.4% of full finetuning with only 3% of the parameters. Downside: extra layers add inference latency.

➕ Adapter-based (additive)

Add small trainable modules: LoRA (by far the most popular), BitFit, IA3, LongLoRA.

🔡 Soft prompts

Trainable "tokens" fed in with the input: vectors, not readable words, tuned by training. Variants (prefix-tuning, P-tuning, prompt tuning) differ in where they're inserted. A middle ground between prompting and finetuning.

📌 Remember PEFT is also sample-efficient: a few thousand examples can be enough, versus tens of thousands to millions for full finetuning. In the author's count of GitHub issues on Hugging Face's PEFT library, LoRA dominates.

LoRA and QLoRA

Small trainable add-ons with no extra latency 📖 PDF p. 362–371

🧒 Plain English LoRA (low-rank adaptation) leaves the big weight matrix W frozen and trains two thin matrices A and B whose product has the same shape as W. Afterwards, A×B can be merged back into W, so serving is no slower.

r is the "rank": how thin A and B are. α controls how strongly A×B counts
🧩 Why it saves so much (the book's example) A 9 × 9 matrix has 81 numbers; a 9 × 1 matrix times a 1 × 9 matrix has only 18. For GPT-3, LoRA matched or beat full finetuning on several tasks while training only ~4.7 million parameters, 0.0027% of the model.
📌 Why can so little training work? Research suggests pre-trained LLMs have a low "intrinsic dimension": pre-training compresses what they know, and bigger, better-trained models compress more, so a small adjustment goes a long way.

⚙️ LoRA settings

  • Which matrices: usually the attention ones (query, key, value, output). On a fixed budget for GPT-3, all four at rank 2 did best; if only two, query and value. Adding the feedforward layers often helps more (Databricks).
  • Rank r: 4–64 is usually enough; higher didn't help in the original paper, though one practitioner found 256 best for his tasks.
  • α: the ratio α : r usually between 1:8 and 8:1; experiment.

📦 Serving many LoRA models

🧩 100 customers, one finetuned model each (W = 4096 × 4096, rank 8)
Merge each into W
100 full matrices = 1.68B parameters
Keep adapters separate

Separate: one W (16.8M) + 100 small A,B pairs (65,536 each) ≈ 23.3M parameters, and switching customer just means loading a tiny adapter (at a small latency cost). Apple used several LoRA adapters on one 3B on-device model for different iPhone features.

🗜️ QLoRA

Stores the frozen weights in 4 bits (a format called NF4) and uses "paged" optimisers that spill to CPU memory. Result: a 65B model finetuned on a single 48 GB GPU. Its Guanaco 65B scored Elo 1022 vs ChatGPT's 966 in GPT-4-judged comparisons. Downside: quantising back and forth slows training.

⚠️ LoRA's catch

Usually not quite as strong as full finetuning, and harder to set up for less popular models. Frameworks (Hugging Face PEFT, Axolotl, unsloth, LitGPT) support popular ones out of the box.

🧪 Testing angle With multi-LoRA serving, each customer or feature has its own adapter version. Version and test adapters like separate releases, and check that a request never gets served with another customer's adapter.

Model merging and multi-task finetuning

Combining models instead of retraining one 📖 PDF p. 371–381

🧒 Plain English Model merging combines several (often finetuned) models into one. Goals: better performance (one model answers the first 60% of questions, another the last 60%, together maybe 80%), or one smaller model doing several jobs, e.g. on a phone. Often doable without GPUs.
Way to teach several tasksProblem
All tasks at onceHarder to learn several skills together; more data and training
One task after anotherCatastrophic forgetting: learning task B erases task A
Each task separately, then mergeLess forgetting; each task learned well

🗳️ Ensemble (not merging)

Run several models and combine their outputs (e.g. majority vote). Better results, but several calls per request.

🧬 Merging

Combine their parameters into one model: one call per request. Many top models on Hugging Face's leaderboard are merged models.

🧪 Three ways to merge

➕ Summing

Average or weighted-average the weights ("model soups"). Works best on models finetuned from the same base. Task vectors = finetuned weights minus base weights; you can add them to combine skills or subtract them to remove a behaviour (like a bias). SLERP blends two along a sphere's shortest path. TIES/DARE first prune tiny changes: keeping only the top 20% of a task vector performed about as well as keeping all of it.

🥞 Layer stacking

"Frankenmerging": take layers from different models and stack them. Goliath-120B used 72 of the 80 layers from each of two Llama 2-70B models. Usually needs more finetuning. Can build mixture-of-experts models, or upscale: SOLAR 10.7B was built from one 32-layer 7B model → 32 × 2 − 16 = 48 layers.

🔗 Concatenation

Join parameters side by side (two LoRA adapters of rank r₁ and r₂ → rank r₁ + r₂). Not recommended: no memory saving.

📌 Remember Merging is also a route to federated learning: copies of a model learn on different devices' private data, then get merged. Many merging techniques are experimental and may date quickly.

Practical finetuning tactics

Base model, method, framework, hyperparameters 📖 PDF p. 381–385

📈 Progression path (OpenAI)

1 · Test the code on the cheapest, fastest model. 2 · Test the data on a middling model (does loss fall?). 3 · Push the best model. 4 · Train all sizes and pick the best price/performance.

⚗️ Distillation path

1 · Small dataset + strongest affordable model. 2 · Use it to generate more data. 3 · Train a cheaper model on that data.

📌 Choosing a method and framework Start with LoRA; try full finetuning later. Full finetuning usually needs thousands of examples or more; with a few hundred, it may not beat LoRA. Need many finetuned variants? LoRA serves them more cheaply. Finetuning APIs are quick but limit models and knobs; frameworks (LLaMA-Factory, unsloth, PEFT, Axolotl, LitGPT) give control; multiple machines need DeepSpeed, PyTorch Distributed or ColossalAI.

🎛️ Key hyperparameters

KnobWhat it doesHow to read the signs
Learning rateStep size for each update (typically 1e-7 to 1e-3)Loss jumps around → too big. Stable but very slow → too small. Schedules can start big and shrink.
Batch sizeExamples per updateUnder ~8 can be unstable; bigger needs more memory. Gradient accumulation fakes a bigger batch.
EpochsPasses over the dataMillions of examples: 1–2; thousands: 4–10. Training loss ↓ but validation loss ↑ → overfitting, use fewer.
Prompt loss weightHow much the model learns from prompts vs responsesDefault ~10%: learn mostly from responses
🧩 A cautionary tale from the author In college she let a model train overnight, and it crashed after eight hours because it tried to save to a folder that didn't exist. That's why the progression path tests the code on a cheap model first.
🧪 Testing angle Validation loss rising while training loss falls is the training version of "the tests we tuned against pass, but the hold-out set fails". Same lesson as protecting your hold-out test set (LLM Evaluation Ch 1).

✅ One-page cheat sheet

  1. 🔧 Finetuning = further training to change weights; mostly for format and instruction following. A form of transfer learning.
  2. ⚖️ Reasons: quality on your task, structure, bias fixes, small specialised models, distillation. Against: other tasks degrade, data, skills, serving, maintenance.
  3. 🏦 General models often beat domain models (GPT-4 vs BloombergGPT). Prompt properly first.
  4. 📚 Finetuning is for form, RAG is for facts. Information failures → RAG; behaviour failures → finetune. Base + RAG beat finetuning on current events.
  5. 🔁 Training = forward pass → loss → gradients → optimiser. More trainable parameters → more memory.
  6. 🧮 Inference ≈ params × bytes × 1.2 (13B at 16-bit ≈ 31 GB). Training with Adam adds 3 values per trainable parameter (13B → +78 GB).
  7. 🔢 Formats: FP32, FP16, BF16, TF32, INT8, INT4. Range vs precision. Load models in their intended format.
  8. 🗜️ Quantisation cuts memory (32→16 bit halves it); post-training quantisation is standard; test quality after.
  9. 🔌 PEFT trains a tiny fraction: adapters (within 0.4% using 3% of params), soft prompts.
  10. 🎯 LoRA: frozen W + trainable A×B, mergeable, so no extra latency. Rank 4–64. Multi-LoRA serving is cheap. QLoRA: 4-bit base, 65B on one 48 GB GPU.
  11. 🧬 Merging: summing (averages, task vectors, SLERP, TIES/DARE), layer stacking, concatenation. Avoids catastrophic forgetting.
  12. 🎛️ Start with LoRA; test code on cheap models; watch learning rate, batch size, epochs, validation loss.

Try it (optional, Week 7 is mainly Chapter 10)

Practise the reasoning without training anything

  1. Pick an open model you know the size of. Calculate the memory to run it at 16-bit and 4-bit, and to fully finetune it with Adam. Which GPU sizes would fit?
  2. Look at your failing test cases from earlier labs. Label each as an information or behaviour failure. Would RAG or finetuning help more?
  3. If you can run a model locally (e.g. via Ollama), compare a full-precision and a quantised version on your 30 golden cases. Any quality drop?
