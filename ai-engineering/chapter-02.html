The big picture

The whole chapter on one page. Come back here after each topic.

📌 The chapter in one sentence A model's behaviour comes from four choices: what data it learned from, how it's built and how big it is, how it was taught to behave after training, and how it picks each next word. That last step, sampling, is why the same question can get different answers.
🧪 Why a tester should care most about this chapter The book's author calls sampling "one of the most underrated concepts in AI". It explains flaky outputs (inconsistency) and made-up facts (hallucination), the two things you'll spend the most time testing.

Training data: a model is only as good as what it read

Where the data comes from and why quality beats quantity 📖 PDF p. 74–75

🧒 Plain English A model can only do what its training data showed it. No Vietnamese in the data means no English-to-Vietnamese translation. Model makers mostly use whatever data is available, not exactly the data they'd want.
🕸️

Common Crawl

A non-profit crawl of the web: about 2–3 billion pages a month in 2022–23. Used, in some form, by most models that reveal their data (GPT-3, Gemini).

🧹

C4

Google's "cleaned" subset of Common Crawl. Cleaner, but still not clean.

🗑️

The problem

Clickbait, misinformation, propaganda, conspiracy theories, racism. In plain terms: plenty of fake news.

🧩 Quality beats quantity A team trained a small 1.3-billion-parameter model on just 7 billion tokens of high-quality code. It beat much larger models on several coding benchmarks.
🧪 Testing angle The model has absorbed the internet's mistakes and biases. Include tests for confidently wrong facts and biased answers, not just "does it respond".
❓ Check yourself
Why do model makers train on messy web data instead of perfect data?
Because it's available in huge amounts. Perfect, task-specific data is expensive and slow to collect, so they "use what we have, not what we want".

Multilingual models: English rules the internet

Why models are worse, slower and pricier in many languages 📖 PDF p. 75–79

🧒 Plain English Almost half of Common Crawl is English. Languages spoken by hundreds of millions of people barely appear, so models handle them much worse. Languages with little training data are called low-resource.

📉 Lower quality

GPT-4 scored worst on a big benchmark (MMLU) in Telugu, Marathi and Punjabi, among the least-represented languages. It solved math problems in English over 3× as often as in Armenian or Farsi.

💸 Slower and pricier

Same meaning, more tokens. Median length: English 7 tokens, Hindi 32, Burmese 72. Burmese is ~10× slower and ~10× more expensive.

🛡️ Different safety

One study: ChatGPT refused 6 of 7 misinformation requests in English but complied 7 of 7 times in Chinese.

⚠️ Common trap: "just translate to English and back" You need a model good enough to translate the low-resource language in the first place, and translation loses information. Vietnamese pronouns encode the relationship between speakers; in English they all collapse into "I" and "you".
🧪 Testing angle Treat each language as its own test slice, with its own quality, safety and cost/latency thresholds. A feature that passes in English can fail, or cost 10× more, in another language.
❓ Check yourself
Why does the same answer cost more in Hindi than in English?
APIs charge (and take time) per token, and Hindi needs many more tokens to say the same thing (median 32 vs 7 in the book's data).

Domain-specific models

When general knowledge isn't enough 📖 PDF p. 80–81

🧒 Plain English General models know a bit of everything that's on the web. Tasks whose data isn't on the web (protein structures, X-rays, factory plans) need specially collected data and often a specialised model.
🧬

AlphaFold

DeepMind. Trained on ~100,000 known protein structures.

💊

BioNeMo

NVIDIA. Biomolecular data for drug discovery.

🩺

Med-PaLM 2

Google. An LLM combined with medical data for medical questions.

🧪 Testing angle When you test a domain feature (legal, medical, finance), don't assume general benchmark scores carry over. Build domain test cases with expert-checked answers.

The transformer and attention

The design behind almost every language model today 📖 PDF p. 82–88

🧒 Plain English Before transformers, models (called seq2seq) read the input one word at a time and squeezed it all into one summary before answering. Transformers fixed two problems: they let the model look back at any input word while answering (attention), and they read the whole input at once instead of word by word.
🎯 The book's analogy Old seq2seq = answering questions about a book using only its summary. Transformer with attention = answering while able to flip to any page.

Reading the input is fast (parallel); writing the answer is still one token at a time

🔍 Attention: query, key, value

❓ Query (Q)

"What am I looking for right now?" The person searching the book.

🔑 Key (K)

One per earlier token: like a page number, used to decide relevance.

📄 Value (V)

One per earlier token: the page's content, what actually gets used.

⚙️ Algorithm: attention for one new token (simplified, my own numbers) 
input  q                              # query for the token being written
input  keys, values                   # one key and one value per earlier token
scores ← [ dot(q, k) for k in keys ]  # how relevant is each earlier token?  e.g. [2, 1, 0]
weights ← softmax(scores)              # turn into shares that add up to 1:    [0.67, 0.24, 0.09]
output ← sum(w × v for w, v in weights, values)
                                         # mostly the first token's content, a little of the others
# Real models: scores are also divided by √(dimension), and this runs in many "heads" at once.
Multi-head attention
Several attentions in parallel, each free to focus on different words. Llama 2-7B splits its 4,096-number vectors into 32 heads of 128.
Transformer block
One attention module + one MLP (feedforward) module. A model stacks many blocks; the count is its number of layers.
Embedding module
Before the blocks: turns each token and its position into numbers.
Output layer
After the blocks: turns the final numbers into a probability for every token (topic 10).
Activation function
A simple non-linear step between layers. ReLU just turns negative numbers into 0. Fancier ones didn't work better.
📌 Remember Every earlier token needs a stored key and value. Longer context = more to compute and store, which is why long context windows are hard and expensive (Chapters 7 and 9).
🧪 Testing angle Prefill is fast, decode is slow. That's why time to first token and time per output token (Chapter 1) are separate metrics, and why long answers take longer. Measure both in your performance tests.
❓ Check yourself
What two problems with seq2seq did the transformer solve?
It answered using only a final summary of the input (fixed by attention, which can look at any input token), and it processed input one token at a time (fixed by reading all input tokens in parallel).
Why is generating a long answer still slow with transformers?
Output is still produced one token at a time (decode), because each token depends on the ones before it.

Other architectures

Who might replace the transformer 📖 PDF p. 89–91

🧒 Plain English The transformer has dominated since 2017, which is unusually long. Replacing it is hard because it's been heavily optimised. The main pressure point is long inputs: attention's cost grows with the square of the length.

RWKVAn RNN that can still be trained in parallelNo hard context limit in theory (but long context isn't automatically good)

📌 Remember Even if the architecture changes, the book expects the application techniques (prompting, RAG, evaluation) to stay largely the same.

Model size: three numbers that matter

Parameters, training tokens, FLOPs 📖 PDF p. 91–95

🧠

Parameters

How much the model can learn. "Llama-13B" = 13 billion parameters.

📚

Training tokens

How much it did learn from. Llama 1: 1.4T · Llama 2: 2T · Llama 3: 15T.

💰

FLOPs

How much compute (and money) training took. GPT-3: 3.14 × 10²³.

🧩 Worked numbers from the book
  • Memory: 7B parameters × 2 bytes each = at least 14 GB of GPU memory just to run it.
  • Time: GPT-3 on 256 H100 GPUs at full speed ≈ 236 days.
  • Cost: at 70% utilisation and $2 per GPU-hour, over $4 million.

🧩 Sparse models and mixture of experts

🧒 Plain English A mixture-of-experts (MoE) model has several groups of parameters ("experts") but uses only a few for each token. So it can be big on paper but cheap to run.
Mixtral 8x7B: total
46.7B parameters
Active per token
12.9B

Costs and speed behave like a 12.9B model, because only 2 of the 8 experts work on each token.

Epoch
One full pass through the training data. 1T tokens × 2 epochs = 2T training tokens.
FLOPs vs FLOP/s
FLOPs = total work a task needs. FLOP/s = how fast a machine can work. Easy to mix up; watch the "/s".
Utilisation
Share of a machine's peak speed you actually get. 50% is OK; over 70% is great.
⚠️ Common trap Bigger isn't automatically better: a huge model trained on one sentence is useless. And newer small models can beat older big ones (Llama 3-8B beats Llama 2-70B on MMLU).

Scaling law, and the limits of scaling

How big to build, and what might stop growth 📖 PDF p. 95–101

🧒 Plain English Teams start from a compute budget and ask: what model size and data size give the best model for that money? The Chinchilla scaling law answers: about 20 training tokens per parameter, and grow both together.
🧩 Example A 3B-parameter model should be trained on about 60B tokens. Double the model to 6B and you should double the tokens to 120B.

🦙 Quality isn't everything

Llama's makers deliberately chose smaller models than the budget allowed: easier and cheaper to run, so more people adopted them.

🏔️ The last mile again

Going from 3% to 2% error can need 10× more data, compute or energy.

🔄 Inverse scaling

Sometimes bigger is worse, e.g. on some memorisation tasks, but no real-world failure won the top prize in a contest that looked for one.

Parameter
Learned by the model during training.
Hyperparameter
Set by people: number of layers, learning rate, batch size… Big models can only be trained once, so teams test settings on small models and extrapolate (e.g. from 40M to 6.7B).
Emergent abilities
Abilities that only show up at large scale, which makes small-model predictions less reliable.

🚧 Two bottlenecks

📉

Running out of data

Datasets grow faster than the internet. More web text is now AI-generated. Sites are blocking scrapers: about 45% of C4 is now restricted. Proprietary data (books, contracts, medical records) becomes a competitive advantage.

⚡

Electricity

Data centres use about 1–2% of world electricity, estimated to reach 4–20% by 2030.

⚠️ Common trap: anything online may be training data Assume anything published online is, or will be, in some model's training data, including text written on purpose to influence future models (a route for prompt injection, Chapter 5). Deleted posts may still be "remembered".

Post-training and supervised finetuning (SFT)

Turning a text-completer into an assistant 📖 PDF p. 102–107

🧒 Plain English After pre-training, a model has two problems: it completes text instead of answering, and it can be rude, biased or wrong (it learned from the raw internet). Post-training fixes both, in two steps: supervised finetuning, then preference finetuning.
🎯 Analogy (from the book) Pre-training is like reading to gain knowledge; post-training is learning how to use it. A friend of the author put it this way: a pre-trained model talks like a web page, not a human.
🧩 Why SFT is needed Type "How to make pizza" into a raw pre-trained model. Valid continuations include "…for a family of six?", or more questions, or the actual recipe. Only the recipe is a helpful answer. SFT teaches the model to pick that kind of response.
Demonstration data
Examples in the form (prompt, ideal response), written by people. The model copies the behaviour, so this is also called behaviour cloning.
Labelers
The people writing those responses. For InstructGPT, ~90% had a college degree and over a third a master's.
📌 Numbers to remember
  • One good (prompt, response) pair can take up to 30 minutes. At $10 each, InstructGPT's 13,000 pairs ≈ $130,000, before design and quality control.
  • Post-training used only 2% of InstructGPT's compute (pre-training 98%). It mostly unlocks abilities the model already has.
  • Volunteer-written data is cheaper but can be skewed: in one project, 90% of volunteers identified as male.
🧪 Testing angle The people who write demonstration data shape the model's behaviour. If they're not representative of your users, expect blind spots. Test with prompts from real user groups, not just your team.

Preference finetuning, reward models and RLHF

Teaching which answers people prefer 📖 PDF p. 107–112

🧒 Plain English SFT teaches how to hold a conversation, not which conversations to have. Should the model help with something harmful? How should it handle a controversial topic? Preference finetuning nudges it towards answers people prefer. The classic method is RLHF (reinforcement learning from human feedback).

RLHF in two parts: train a scorer, then train the model to please the scorer

❌ Scoring each answer alone

Called pointwise. Inconsistent: one person gives 5/10, another 7/10, even the same person changes their mind.

✅ Comparing two answers

Easier and more consistent. Still slow: 3–5 minutes each (fact-checking both), about $3.50 per comparison vs $25 to write an answer.

📌 Remember
  • Labelers agreed with each other only about 73% of the time. Human preference isn't one fixed thing.
  • Ranking three answers A > B > C gives three comparison pairs: A>B, A>C, B>C.
  • DPO is a simpler alternative (Meta moved from RLHF in Llama 2 to DPO in Llama 3). RLAIF uses AI feedback instead of humans.
  • Some companies skip the RL step: they generate several answers and keep the one the reward model scores highest (best of N, topic 12).
🧪 Testing angle Two ideas you'll reuse in evaluation (Chapters 3–4): comparing two outputs is more reliable than scoring one, and a scoring model can judge outputs automatically. Also, 73% agreement means your own human reviewers will disagree too, so measure agreement.
❓ Check yourself
Why compare two answers instead of scoring each one from 1 to 10?
Independent scores vary a lot between people and even for the same person. Choosing the better of two is easier and gives more consistent data.
What does the reward model do in RLHF?
It scores (prompt, answer) pairs. The assistant is then trained to produce answers that get high scores.

Sampling and temperature

How the model picks each next token 📖 PDF p. 112–117

🧒 Plain English For every next token, the model gives each token in its vocabulary a score. Those scores become probabilities, and one token is picked at random, weighted by those probabilities. That random pick is called sampling.

From raw scores to the chosen token

🎯 Greedy

Always pick the most likely token. Fine for classification (spam / not spam), but makes text boring and repetitive.

🎲 Sampling

If "green" is 50% likely and "red" 30%, then green is picked 50% of the time and red 30%.

🌡️ Temperature: the creativity dial

The book's example: a model with only two tokens, A and B, with logits [1, 2]. How often is B (the more likely one) picked?

T = 0.5
B 88% · A 12%
T = 1 (default)
B 73% · A 27%
T = 2
B 62% · A 38%

The T = 2 row is my own calculation using the same method.

⚙️ Algorithm: sampling with temperature (worked with the numbers above) 
input  logits = [1, 2]                # raw scores for A and B
input  T = 0.5                        # temperature
if T == 0: return argmax(logits)       # "temperature 0" just means: always take the top token
adjusted ← [x / T for x in logits]    # [2, 4]  (low T stretches the gap)
exps ← [e^x for x in adjusted]         # [7.39, 54.6]
probs ← [v / sum(exps) for v in exps]  # [0.12, 0.88]  softmax
return random_choice([A, B], weights = probs)
📌 Remember
  • Low temperature = more predictable, more boring. High temperature = more creative, less coherent.
  • Providers usually allow 0–2. About 0.7 is common for creative tasks; 0 for consistency.
  • Logprobs are useful for classification and evaluation, but many providers expose them only partly or not at all.
🧪 Testing angle Temperature is a test setting. Record it with every result, keep it fixed when comparing versions, and run each case several times at the temperature production actually uses. A test that passes at 0 can fail at 0.7.
❓ Check yourself
What happens to the less likely token's chance when you raise the temperature?
It goes up. Higher temperature flattens the probabilities, so rarer tokens get picked more often.
Why is "temperature 0" not really dividing by zero?
In practice the model skips the maths and just picks the highest-scoring token (argmax).

Top-k, top-p and stopping

Limiting which tokens can be picked, and when to stop 📖 PDF p. 118–119

🔟 Top-k

Only consider the k highest-scoring tokens (often 50–500). Saves computation; smaller k = more predictable.

🥧 Top-p ("nucleus")

Only consider the smallest group of top tokens whose probabilities add up to p (often 0.9–0.95). The group size changes with the situation.

⬇️ Min-p

Only consider tokens above a minimum probability.

⚙️ Algorithm: top-p (my own numbers; same outcome as the book's example) 
probs ← { yes: 0.60, maybe: 0.35, no: 0.04, other: 0.01 }
p ← 0.9
keep ← [];  total ← 0
for token in tokens sorted by probability, highest first:
    keep.append(token);  total ← total + probs[token]
    if total ≥ p: stop                # yes (0.60) + maybe (0.35) = 0.95 ≥ 0.9
return sample(keep)                    # only "yes" or "maybe" can be chosen
# with p = 0.99 the loop also keeps "no" (0.60 + 0.35 + 0.04 = 0.99)
🧩 Why top-p adapts "Answer yes or no" should only ever consider 2 tokens. "What's the meaning of life?" should consider many. Top-k always uses the same k; top-p adjusts to the situation.

🛑 Stopping conditions

Stop after a maximum number of tokens, or at a stop token (like the end-of-sequence token). Shorter outputs keep latency and cost down.

⚠️ Common trap: truncated JSON If the token limit cuts the answer off, a JSON reply can lose its closing brackets and fail to parse. Test long inputs near the max-token limit.

Test time compute: generate several, keep the best

Spend more at answer time for better answers 📖 PDF p. 120–123

🧒 Plain English Instead of one answer per question, generate several and choose the best one. This is called test time compute ("test time" here just means "when the model is used"). Simplest form: best of N.

Five ways to choose among several generated answers
🧩 How a sentence's probability is computed (from the book) p("I love food") = p(I) × p(love | I) × p(food | I, love) = 0.2 × 0.1 × 0.3 = 0.006. Longer sentences multiply more numbers below 1, so they always look less likely. Using the average logprob per token removes that bias.

🚀 Verifiers are powerful

OpenAI found a verifier gave about the same boost as making the model 30× bigger: a 100M model with a verifier matched a 3B model without one.

📉 But not forever

In one OpenAI test, more samples helped up to 400, then got worse (more chances to fool the verifier). Another study saw gains up to 10,000. Nobody does that in production: it's too expensive.

⏱️ Beat latency

One team generates several answers in parallel and shows the first one that's complete and valid.

🗳️ Majority vote

Google sampled 32 answers per question and took the most common one when testing Gemini on MMLU.

🧩 Fragile models benefit most (from the book) A product-label reader managed to read a given image only half the time; the other half it claimed the image was too blurry. Trying three times per image got the correct information for most images.
🧪 Testing angle Two generations cost about twice as much as one. If your product uses best-of-N or majority voting, test cost and latency as well as quality, and check which selection rule is in use. And remember the Gemini lesson from Chapter 1: compare scores only when the number of samples is the same.

Structured outputs: getting reliable JSON, SQL and labels

Five ways to make output follow a format 📖 PDF p. 123–128

🧾 The task needs structure

Semantic parsing: turning plain language into something machines run, like text-to-SQL ("average monthly revenue over 6 months"), regexes, or valid class labels.

🔗 Another program reads it

The text itself is free-form (an email), but the app downstream needs it as, say, JSON with "title" and "body". Essential for agents passing outputs to tools.

⚠️ Common trap: "JSON mode" ≠ correct JSON A provider's JSON mode usually guarantees valid JSON syntax only, not the right keys or values. It can still be cut off by the token limit. The author has seen valid-JSON rates anywhere from 0% to the high 90s.

The probabilistic nature: inconsistency and hallucination

The two problems you'll test most 📖 PDF p. 129–135

🧒 Plain English If a model thinks "Vietnamese cuisine" is 70% likely to be the best answer and "Italian" 30%, it will answer Vietnamese about 7 times in 10 and Italian about 3 times. It's probabilistic, not deterministic (always the same). Anything with a probability above zero, however unlikely, can come out.
📌 From the field In three months of support requests at one AI company, one in five was about inconsistency. Industry leaders agree hallucination is the biggest blocker for many enterprise uses.

Hypothesis 1, "self-delusion" or snowballing hallucination

1️⃣ Self-delusion

The model can't tell what it was given from what it wrote. One odd first sentence snowballs. In the book's example, a vision model decided a shampoo bottle was milk, then listed milk as an ingredient. A wrong start can even make it fail questions it would otherwise get right.

2️⃣ Knowledge mismatch

During SFT, the model copies answers written by people who know things the model doesn't. So it learns to answer confidently without the knowledge, which is effectively being taught to make things up.

📌 What helps (partly) Ask the model to cite the sources it relied on · train it to separate given text from its own text · reward functions that punish making things up · prompts like "if you're unsure, say you don't know" · shorter answers (fewer tokens, fewer chances to invent). Note: in the InstructGPT paper, RLHF actually made hallucination worse, even though people preferred the RLHF model overall.
🧪 Testing angle
  • Run every test case several times. One pass tells you almost nothing about a probabilistic system.
  • Add near-duplicate inputs (casing, spacing, word order) to test the second kind of inconsistency.
  • Add "bait" questions about things that don't exist or aren't in the provided context, and check the model says it doesn't know.
  • Detecting and measuring hallucination properly is covered in Chapter 4.

✅ One-page cheat sheet

  1. 📚 Models learn mostly from messy web data (Common Crawl, C4). Quality can beat quantity.
  2. 🌍 English is ~46% of the web; many big languages are tiny. Expect worse quality, more tokens, higher cost outside English. Test per language.
  3. 🧬 Specialist domains need specialist data.
  4. 🔍 Transformers use attention (query, key, value) to look back at any earlier token. Input is read in parallel (prefill); output is written one token at a time (decode).
  5. 🐍 Challengers like Mamba and Jamba target cheaper long inputs.
  6. 📏 Size = parameters (capacity) + training tokens (what it learned) + FLOPs (cost). MoE models are big but run like small ones.
  7. ⚖️ Chinchilla: ~20 tokens per parameter. Data and electricity may limit future growth.
  8. 🎓 Post-training = SFT (learn to answer) + preference finetuning (learn what people prefer).
  9. ⚖️ RLHF: compare answers → train a reward model → train the model to score well. People agree only ~73%.
  10. 🎲 Sampling picks each token by probability. Temperature: low = predictable, high = creative.
  11. 🥧 Top-k keeps the top k tokens; top-p keeps the top tokens adding up to p. Token limits can cut JSON off.
  12. 🔁 Best of N / verifiers / majority vote improve quality at extra cost.
  13. 🧾 Structured output: prompt → post-process → regenerate → constrained sampling → finetune. JSON mode ≠ correct content.
  14. 👻 Probabilistic models are inconsistent and hallucinate. Test with repeated runs, near-duplicate inputs and bait questions.
