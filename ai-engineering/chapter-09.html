The big picture

The whole chapter on one page. Come back here after each topic.

📌 The chapter in one sentence A model that's too slow or too expensive is useless, however good it is. To fix that, find the bottleneck (compute or memory bandwidth), measure the right things (TTFT, TPOT, throughput, goodput, utilisation), then optimise at the model level (compression, faster decoding, efficient attention, kernels) and the service level (batching, splitting prefill and decode, prompt caching, parallelism).

Inference, inference servers and three levels of optimisation

Training builds the model; inference uses it 📖 PDF p. 429–431, 450

🧒 Plain English Training = building a model. Inference = using it: give it an input, get an output. Unless you train or finetune, inference is all you'll deal with. The program that runs the model on the hardware is the inference server; around it sits the inference service, which receives, routes and maybe preprocesses requests. OpenAI's and Google's model APIs are inference services: if you use them, they do the optimising. If you host a model yourself, it's your job.

🎯 The book's analogy: archery Model-level optimisation = crafting better arrows. Hardware-level = training a stronger archer. Service-level = improving the whole shooting process: the bow and the conditions. In production you usually combine levels. The book covers model and service levels; hardware design is out of scope.
🧩 Why it matters (the book's example) A model that predicts tomorrow's stock price but takes two days to compute is worthless. And a model that's too expensive won't pay back its cost.
⚠️ Same model, different answers Ideally optimisation doesn't change quality, but many techniques do. A Cerebras experiment found the same Llama models scored differently on benchmarks depending on which provider served them. "Llama 3 70B" from provider A may not behave exactly like "Llama 3 70B" from provider B.
🧪 Testing angle If you switch hosting provider, or your team turns on a new optimisation, re-run your evaluation suite. Treat it like a new model version, even if the model name is unchanged.

The two bottlenecks: compute and memory bandwidth

Prefill is compute-bound, decode is bandwidth-bound 📖 PDF p. 431–434

🧒 Plain English Optimising means finding what slows you down. Two usual suspects: compute-bound = the chip can't do the maths fast enough (like cracking a password); memory bandwidth-bound = the chip is waiting for data to arrive (like moving data from CPU memory to the GPU). People often shorten the second to bandwidth-bound or, confusingly, memory-bound.

🧮 Prefill: compute-bound

The model reads all your input tokens at once, in parallel. The limit is how many operations the chip can do per second. (Prefill also fills the KV cache, topic 10.)

🐢 Decode: bandwidth-bound

The model writes one output token at a time. Each step loads big weight matrices into the chip, so the limit is how fast memory can deliver them.

Operations done per byte of memory read. High = compute-bound, low = bandwidth-bound.
Roofline chart
A chart (from the 2009 "Roofline" paper, shown by tools like NVIDIA Nsight) that tells you which bound a workload hits. It's named for its roof shape.

📌 Remember Image generators like Stable Diffusion are usually compute-bound; language models are usually bandwidth-bound. Compute-bound work speeds up with more or faster chips (higher FLOP/s); bandwidth-bound work speeds up with higher-bandwidth chips. Because the two phases differ so much, production systems often run them on separate machines (topic 13).
🧪 Testing angle Long prompts stress prefill (slower first token); long answers stress decode (slower total time). Design performance tests with both: long-input/short-output and short-input/long-output cases.
❓ Check yourself
Why is decoding bandwidth-bound rather than compute-bound?
Each new token needs the whole model's weights moved from memory to the compute units, but only a small amount of maths is done with them, so the chip spends most of its time waiting for data.
A teammate says "we're memory-bound". What should you ask?
Do they mean bandwidth (data moves too slowly) or capacity (it doesn't fit, OOM)? The term is used both ways.

Online vs batch APIs, and streaming

Pay for speed, or wait and save 📖 PDF p. 434–436

⚡ Online API📦 Batch API
Optimises forLow latencyLow cost / high throughput
TurnaroundSecondsHours
PriceNormalGemini and OpenAI: about 50% off (as of writing)
Good forChatbots, code completionSynthetic data, periodic reports, onboarding a customer's documents, re-processing data for a new model, newsletters, reindexing a knowledge base
🧒 Streaming By default an API returns the full answer at once. Streaming mode sends each token as soon as it's generated, so users see something sooner. The downside: you can't score (check) the answer before users see it; you can only remove or update it afterwards.
⚠️ "Batch" means something else in classic ML In traditional ML, batch inference means precomputing predictions before requests arrive (e.g. recommendations for every user overnight). With foundation models you can't predict open-ended prompts, so a batch API just means "slower, cheaper processing of requests you send".
🧪 Testing angle Streaming changes what your output guardrails can do. Test what happens when a bad answer is detected mid-stream: is it retracted, and what does the user see? Also, batch APIs are a cheap way to run large evaluation suites overnight.

Latency metrics: TTFT, TPOT and percentiles

The numbers your users feel 📖 PDF p. 436–438

🧒 Plain English Latency = time from sending a query to receiving the complete answer. For token-by-token generation it splits into two parts: TTFT (time to first token) = how long until the first token appears; it's the prefill step and grows with input length. TPOT (time per output token) = how long each later token takes; it's the decode step. Variants: TBT (time between tokens, LinkedIn's term) and ITL (inter-token latency, NVIDIA's). 
sequenceDiagram
  participant U as 👩 User
  participant M as 🤖 Model
  U->>M: send query
  Note over M: prefill = TTFT
  M-->>U: token 1
  Note over M: TPOT
  M-->>U: token 2
  Note over M: TPOT
  M-->>U: token 3 … last token
  Note over U,M: Total latency = TTFT + TPOT × number of output tokens
Where TTFT and TPOT sit in a streamed answer
🧩 Numbers from the book At 100 ms per token, a 1,000-token answer takes 100 s. A very fast reader manages about 120 ms per token, so a TPOT around 120 ms (6–8 tokens a second) is enough for most streaming apps. Anyscale found 100 input tokens affect latency about as much as one output token.
⚠️ Trap 1: averages lie Ten TTFTs: 100, 102, 100, 100, 99, 104, 110, 90, 3,000, 95 ms. The average is 390 ms, but nine of ten requests took about 100 ms. Use percentiles: p50 (median) plus p90, p95, p99, and investigate the outliers (a network error? a huge prompt?). It also helps to plot TTFT against input length.
⚠️ Trap 2: the model's first token isn't the user's first token An agent might write a hidden plan, call tools, then write the visible answer. The model's TTFT is at step 1; the user's is at step 3. Some teams use time to publish to mean "time until the first token the user sees".
🎯 Analogy A restaurant: TTFT is how long until your starter arrives; TPOT is the gap between later courses. Two restaurants with the same total time can feel very different. Which users prefer is a question for user studies; you can trade one against the other by moving machines between prefill and decode.
🧪 Testing angle Write SLOs as percentiles, separately for TTFT and TPOT, e.g. "p95 TTFT ≤ 500 ms and p95 TPOT ≤ 100 ms". For agents, measure time to publish from the user's side, not just model-side TTFT.
❓ Check yourself
TTFT = 0.5 s, TPOT = 50 ms, the answer has 200 tokens. Total latency?
0.5 + 0.05 × 200 = 10.5 seconds.
Your dashboard shows average TTFT doubled overnight, but p50 is unchanged. What's likely going on?
A few very slow outliers (long prompts, network errors, overloaded nodes). Check p95/p99 and the slowest individual requests.

Throughput, cost and goodput

How much work, at what price, within the SLO 📖 PDF p. 438–440

🧒 Plain English Throughput = how many output tokens per second (TPS) the service produces across all users. Count input and output throughput separately, since prefill and decode behave differently. It can also be measured in completed requests per minute (RPM), since LLM requests take seconds. Higher throughput usually means lower cost.
⚙️ The book's cost calculation, step by step 
# Decode cost
machine cost  = $2 per hour
throughput    = 100 output tokens/s  = 360,000 tokens/hour
cost per 1M output tokens = $2 ÷ 0.36  ≈ $5.556
1,000 requests × 200 output tokens = 200,000 tokens  → $1.11

# Prefill cost
prefill speed = 100 requests/minute = 6,000 requests/hour
1,000 requests = 1/6 hour × $2  → $0.33

# Total for 1,000 requests
$1.11 + $0.33 = $1.44
🧒 Goodput Batching and similar tricks can double or triple throughput (LinkedIn's experience) by making each request slower. So raw throughput can hide a bad user experience. Goodput counts only the requests per second that meet the SLO (service-level objective).
Throughput
100 requests/min
Goodput
30/min

The book's example: SLO = TTFT ≤ 200 ms and TPOT ≤ 100 ms. The service completes 100 requests a minute, but only 30 meet both targets, so goodput is 30 per minute.

⚠️ Tokens aren't equal across models Different models have different tokenizers, so "tokens per second" isn't directly comparable between models. Compare cost per request instead.
🧪 Testing angle Goodput is the load-test metric to report: "at 50 concurrent users, 92% of requests met the SLO". It ties performance to user experience. Note that providers may throttle you when you send many concurrent requests, so test at realistic concurrency.

Utilisation: why "GPU 100% busy" means little, and MFU and MBU

Busy isn't the same as efficient 📖 PDF p. 440–443

🧒 Plain English nvidia-smi's GPU utilisation is the share of time the GPU is doing anything. A chip able to do 100 operations a second but doing just 1 can still show 100%. Two better measures: MFU (model FLOP/s utilisation) = actual throughput ÷ the throughput the chip could reach at its advertised peak FLOP/s; MBU (model bandwidth utilisation) = memory bandwidth used ÷ the chip's peak bandwidth.
⚙️ Computing MBU (the book's example) 
bandwidth used = parameters × bytes per parameter × tokens per second
               = 7B × 2 bytes (FP16) × 100 tokens/s
               = 1.4 TB/s                       # 7×10⁹ × 2 × 100 = 1.4×10¹²
MBU            = bandwidth used ÷ chip's peak bandwidth
               = 1.4 TB/s ÷ 2 TB/s (A100-80GB)
               = 70%
➕ A spotted typo The book prints the middle step as 700 GB/s, but 7B × 2 × 100 is 1.4 TB/s, and the book's final answer (70% of 2 TB/s) only works with 1.4 TB/s. Good practice for a tester: re-run the arithmetic in any spec.
Model (PaLM paper, 2022)SizeChipsTraining MFU
GPT-3175BV10021.3%
Gopher280B4,096 TPU v332.5%
Megatron-Turing NLG530B2,240 A10030.2%
PaLM540B6,144 TPU v446.2%
📌 Remember Compute-bound work shows higher MFU and lower MBU; bandwidth-bound work the reverse. Prefill has higher MFU than decode; training has higher MFU than inference. For training, above 50% MFU is considered good. Fewer bytes per parameter (quantisation) means less bandwidth used, which is why quantisation helps so much. With more concurrent users, MBU drops as the workload shifts towards compute-bound (a Databricks Llama 2-70B test).
⚠️ Utilisation isn't the goal What you want is jobs done faster and cheaper. Higher utilisation means nothing if cost and latency both go up. Also beware "peak FLOP/s hacking": chip makers may quote peaks measured in special conditions you'll never hit.

AI accelerators: GPUs, FLOP/s, memory and power

The hardware that makes inference fast or slow 📖 PDF p. 443–449

🧠 CPU

A few powerful cores (up to ~64 on high-end consumer machines). Great at sequential work: the operating system, I/O, complex step-by-step logic.

🎮 GPU

Thousands of small cores for work that splits into many independent pieces, like graphics and matrix multiplication, which is over 90% of a neural network's floating-point work.

🧩 History in two lines Too little compute contributed to the first AI winter in the 1970s. AlexNet (2012) took off partly because it trained on GPUs: a couple of GPUs were within reach of PhD students; thousands of CPUs weren't. Today NVIDIA dominates, with AMD GPUs, Google TPUs, Intel Gaudi, Groq LPUs, Cerebras and others competing. Inference can make up up to 90% of a deployed system's ML costs, so inference-specific chips (lower precision, faster memory) are a big theme: Apple Neural Engine, AWS Inferentia, Meta MTIA, Edge TPU, Jetson.
🧒 Computational capability: FLOP/s FLOP/s = floating-point operations per second (often written FLOPS). Lower precision = more operations per second. Real apps rarely reach the advertised peak.

The memory hierarchy: the closer to the cores, the faster and smaller.

⚡ On-chip SRAMCaches (L1, L2, sometimes L3), registers, shared memory. Over 10 TB/s, but tiny: typically 40 MB or less.
🚀 GPU HBM (high-bandwidth memory)The GPU's own 3D-stacked memory. About 256 GB/s to over 1.5 TB/s; a GPU has around 24–80 GB.
🐢 CPU DRAM (host memory)Slowest: about 25–50 GB/s. Laptops 16–64 GB; workstations can have 1 TB or more.

Frameworks like PyTorch don't give fine control over this hierarchy, which is why people learn GPU languages such as CUDA, Triton and ROCm.

🧩 Power An A100 has 54 billion transistors; an H100, 80 billion. One H100 running flat out for a year uses about 7,000 kWh, against about 10,000 kWh for an average US household. Electricity, not chips, often limits data centre growth. Specs list maximum power draw or TDP (thermal design power); max draw is roughly 1.1–1.5× TDP.
📌 Choosing an accelerator: three questions Can it run my workload? How long will it take? How much will it cost? FLOP/s, memory size and memory bandwidth answer the first two. Compute-bound workload → more FLOP/s. Bandwidth-bound → more bandwidth and memory.

Model compression: quantisation, distillation, pruning

Smaller models run faster 📖 PDF p. 450–451

🧒 Plain English Model-level optimisation changes the model itself, so it can change behaviour. Transformers are expensive for three reasons: their size, one-token-at-a-time decoding and the attention mechanism. Compression tackles size.
TechniqueWhat it doesIn practice
🔢 Quantisation (Ch 7)Store weights in fewer bits: 32 → 16 bits halves memoryBy far the most popular (weight-only): easy, works out of the box, very effective. But we're near the limit: you can't go below 1 bit
🎓 Distillation (Ch 8)Train a small model to copy a big oneCommon: a small model can match a big one on your task
✂️ PruningRemove whole nodes, or set the least useful weights to zero (making the model sparse)Less common: needs deep architecture knowledge, smaller gains, and not all hardware benefits from sparsity. Research showed over 90% of non-zero weights removable in some networks without losing accuracy
🎯 Analogy Quantisation = saving photos as smaller JPEGs. Distillation = an apprentice learning to do the master's job. Pruning = cutting the branches of a tree that bear no fruit.
🧪 Testing angle Compressed models need a quality regression check against the original on your own evaluation set, focusing on rare cases where small errors show up first (numbers, other languages, long reasoning).

Beating one-token-at-a-time: speculative, reference and parallel decoding

Guess ahead, copy, or generate several tokens at once 📖 PDF p. 452–457

🧒 Why it matters Output tokens are slow and costly: across providers an output token costs about 2–4× an input token. Shaving even a little off decoding noticeably improves user experience.

⚡ Speculative decoding

🧒 Plain English A small, fast draft model guesses the next few tokens; the big target model (the one you actually want) checks them all in one go and keeps the ones it agrees with.
⚙️ Speculative decoding loop 
repeat until the answer ends:
    draft ← draft model writes K tokens            # cheap and fast
    target model checks all K tokens in parallel     # checking is parallel, like prefill
    j ← how many draft tokens it accepts, left to right
    keep those j tokens
    target model adds 1 token of its own            # so each loop gives 1 to K+1 tokens

📌 Why it works (three insights) 1) Checking tokens is faster than generating them, because checking is parallel. 2) Many tokens are easy, so a weak model guesses them right. 3) Decoding is bandwidth-bound, so there are idle FLOPs to spend on checking for free (if MFU is already maxed out, it helps less). Acceptance is higher for structured text like code. Bigger K = fewer checks but lower acceptance. Ideally the draft model shares the target's tokenizer.
🧩 Results DeepMind trained a 4B draft for Chinchilla-70B: 1.8 ms vs 14.1 ms per token, cutting latency by more than half with no quality loss. It's simple (about 50 lines of PyTorch) and built into vLLM, TensorRT-LLM and llama.cpp.

📋 Inference with reference

Answers often repeat the input: quoting a document, or returning code with small fixes. So take draft tokens by copying from the input instead of from a draft model. No extra model needed; about 2× faster where outputs overlap the context (retrieval, coding, multi-turn chat).

🔀 Parallel decoding

Generate several future tokens at once: after "the cat sits", you can guess "the" comes two words later without knowing the next word. Lookahead decoding uses the same decoder and repairs failed tokens (Jacobi decoding). Medusa adds extra trained heads, each predicting a further position, then picks the best combination with tree attention. NVIDIA reported up to 1.9× for Llama 3.1. Powerful but harder to implement.

🧪 Testing angle Speculative decoding should be lossless (the target model decides every token), so outputs shouldn't change. That's testable: with the same seed and settings, compare outputs with it on and off, and report the latency gain.
❓ Check yourself
K = 4. All draft tokens are accepted. How many tokens does that loop produce?
5: the 4 accepted draft tokens plus 1 from the target model.
Which technique suits a "fix the bug in this file" coding assistant best, and why?
Inference with reference: most of the output copies the input code, so tokens can be copied rather than generated, without an extra model.

Attention optimisation and the KV cache

Remember past work; make attention cheaper 📖 PDF p. 457–461

🧒 Plain English To write each new token, attention needs the key and value vectors (from Chapter 2) of every earlier token. Rather than recompute them every step, store them in the KV cache and compute only the newest token's. It's used only at inference; in training all tokens are known up front.

🎯 Analogy Writing minutes of a long meeting: you don't re-listen to the whole recording before every new sentence; you keep notes and add to them. The notes pile grows with the meeting's length, and that pile is the KV cache.
⚙️ KV cache size (unoptimised) 
size = 2 × B × S × L × H × M
       # 2 = keys and values · B = batch size · S = sequence length
       # L = layers · H = model dimension · M = bytes per value

Llama 2 13B: L = 40, H = 5,120; B = 32, S = 2,048, FP16 (M = 2)
size = 2 × 32 × 2,048 × 40 × 5,120 × 2 ≈ 54 GB
⚠️ Why long context is so hard Attention work grows with the square of the sequence length (O(n²)); the KV cache grows linearly with length and with batch size. For a 500B+ model with batch 512 and context 2,048, Google calculated a 3 TB cache: three times the model's weights.

Three families of fixes:

FamilyExamplesNote
🏗️ Redesign attentionLocal windowed attention (attend only to nearby tokens: 10,000 tokens with a 1,000 window = 10× smaller cache), often mixed with global attention · multi-query (heads share keys and values) · grouped-query (groups of heads share) · cross-layer (neighbouring layers share)Changes the architecture, so only during training or finetuning
🗄️ Manage the KV cachePagedAttention (vLLM): split the cache into non-contiguous blocks to avoid fragmentation · KV quantisation · adaptive compression · selective cachingLets you serve bigger batches
⚙️ Write attention kernelsFlashAttention: fuses several attention operations into one fast stepHardware-specific (topic 11)
🧩 Character.AI Average conversations have 180 messages of history, so KV cache size was their main throughput limit. Multi-query attention + interleaved local/global attention + cross-layer attention cut the cache by over 20×, and memory stopped being the bottleneck.
🧪 Testing angle Long conversations are where memory runs out. Include long multi-turn sessions and large batches in load tests and watch for OOM errors, rising TTFT and dropped requests as context grows.

Kernels and compilers

Code tuned for one chip 📖 PDF p. 461–464

🧒 Plain English A kernel is code optimised for a specific accelerator, for heavy, repeated operations like matrix multiplication, attention and convolution. Kernels are written in low-level languages: CUDA (NVIDIA), Triton (OpenAI), ROCm (AMD). Writing them needs deep knowledge of the memory hierarchy, so it used to be a "dark art"; many companies treat their kernels as trade secrets.

📏 Vectorisation

Process several neighbouring data elements at once instead of one by one.

🔀 Parallelisation

Split an array into independent chunks for different cores or threads.

🧱 Loop tiling

Reorder data access to suit the hardware's memory layout and cache. A good CPU pattern may be bad on a GPU.

🔗 Operator fusion

Merge several operations into one pass to avoid re-reading memory, e.g. two loops over the same array become one. Needs model-specific knowledge.

🧒 Compilers and "lowering" Converting a model's code into something a particular chip can run is called lowering; the tool that does it is a compiler. Where it can, it swaps in specialised kernels. Examples: Apache TVM, MLIR, torch.compile, XLA/OpenXLA, TensorRT's compiler. New hardware needs new kernels: FlashAttention was built for A100s, FlashAttention-3 for H100s.

Batching: static, dynamic and continuous

Put requests on the same bus 📖 PDF p. 464–466

🧒 Plain English Service-level techniques manage resources and don't change the model, so they shouldn't change quality. The easiest cost saver is batching: process requests that arrive around the same time together. The book's analogy: everyone driving their own car vs taking a bus. A bus moves more people, but each trip may take longer.

Splitting prefill from decode, and prompt caching

Two LLM-specific service tricks 📖 PDF p. 466–468

✂️ Decoupling prefill and decode

🧒 Plain English Prefill wants compute, decode wants bandwidth. On one machine they fight: a new request's prefill can steal compute from other requests' decoding and slow their TPOT. So run them on different machines (papers: DistServe, Inference Without Interference). Passing the intermediate state between them costs little on fast links like NVLink.

📜 Long inputs, TTFT matters

Prefill : decode machines ≈ 2:1 to 4:1

💬 Short inputs, TPOT matters

Prefill : decode machines ≈ 1:2 to 1:1

🗃️ Prompt caching (context cache, prefix cache)

🧒 Plain English Many prompts share the same beginning: the system prompt, a long document everyone asks about, or earlier turns of a conversation. A prompt cache processes that shared part once and reuses it.

Overlapping prompt segments are reused
🧩 The savings A 1,000-token system prompt × 1 million API calls a day = about 1 billion repeated input tokens a day you no longer process. As of writing, Gemini gave cached tokens a 75% discount (plus a storage fee of $1 per million tokens per hour); Anthropic promised up to 90% cost and 75% latency savings.

⚠️ Not free Like the KV cache, the prompt cache takes memory. Building it yourself takes serious engineering; using an API that offers it is much easier.
🧪 Testing angle ➕ Prompt caches usually match on an exact prefix, so a timestamp or user name at the start of a system prompt can silently break caching. Check the provider's cache-hit fields in responses, and keep the stable parts of prompts first. Also verify cached and uncached calls give equivalent answers.

Which kind of parallelism for inference?
🎯 Analogy Replicas = opening more identical checkout lanes. Tensor = several cashiers scanning one huge trolley together. Pipeline = an assembly line where each worker does one step and passes the item on: good total output, but each item spends longer travelling.
🧩 The bin-packing puzzle (replicas) Models of 8B, 13B, 34B and 70B parameters (8-bit), GPUs with 24, 40, 48 and 80 GB. Do you put three 13B models on a 40 GB GPU, or keep it for one 34B? With more models, replicas and chip types, this gets complicated fast.

📄 Context parallelism

Split the input sequence: the first half on machine 1, the second half on machine 2.

🔧 Sequence parallelism

Split the operators: attention on machine 1, feedforward on machine 2. Both are for long inputs and less common.

📌 The book's "most impactful" list Across use cases: quantisation (works for most models), tensor parallelism (lower latency and bigger models), replica parallelism (easy) and attention optimisation (big speed-ups for transformers). Pick by workload: KV cache work matters most for long contexts, prompt caching for long shared prefixes and multi-turn chat, and more replicas when latency matters more than cost.
❓ Check yourself
Your chatbot has strict latency targets and a model too big for one GPU. Tensor or pipeline parallelism?
Tensor parallelism: it splits each operation so it also cuts latency. Pipeline parallelism adds latency between stages.
Which levels' techniques can change answer quality: model or service?
Model-level ones (quantisation, pruning, architecture changes) can. Service-level ones (batching, caching, parallelism) shouldn't, though it's still worth checking.

✅ One-page cheat sheet

  1. 🖥️ Inference = using a model. The inference server runs it; the service routes requests. Optimise at model, hardware and service levels.
  2. 🧮 Prefill (read input in parallel) is compute-bound; decode (one token at a time) is memory bandwidth-bound.
  3. 📦 Batch APIs: about 50% cheaper, hours to return. Streaming shows tokens sooner but can't be checked first.
  4. ⏱️ Latency = TTFT + TPOT × output tokens. Use percentiles (p50, p90, p95, p99), never just averages. Agents: measure time to publish.
  5. 💰 Throughput drives cost. Goodput = requests per second that meet the SLO. Compare models by cost per request.
  6. 📊 nvidia-smi utilisation ≠ efficiency. MFU (compute) and MBU (bandwidth); MBU = params × bytes × tokens/s ÷ peak bandwidth.
  7. ⚡ Accelerators: judge by FLOP/s, memory size, bandwidth (and power). Memory: SRAM (fast, tiny) → HBM → CPU DRAM (slow).
  8. 🔢 Compression: quantisation (most popular), distillation, pruning. Model-level changes can change quality.
  9. 🏎️ Faster decoding: speculative decoding (draft + verify, lossless), inference with reference (copy from input), parallel decoding (Lookahead, Medusa).
  10. 🗄️ KV cache = 2 × B × S × L × H × M; it limits long context. Fixes: local/multi-query/grouped-query/cross-layer attention, PagedAttention, FlashAttention.
  11. ⚙️ Kernels: vectorise, parallelise, tile, fuse. Compilers lower models to hardware (torch.compile, XLA, TensorRT).
  12. 🚌 Continuous batching beats static and dynamic for LLMs. Split prefill/decode across machines. Prompt caching reuses shared prefixes (up to 90% cheaper).
  13. 🧩 Parallelism: replicas (easy), tensor (fits big models, lowers latency), pipeline (adds latency), context and sequence (long inputs).

Try it: a latency-testing mini lab (optional)

Measure a real model API the way this chapter describes

  1. Write a small script that calls a model API in streaming mode and records the time to the first token and the gaps between tokens.
  2. Send 50 requests: half with a short prompt, half with a long one. Compute p50, p95 and p99 of TTFT and TPOT. Compare the average with the p50.
  3. Plot TTFT against input length. Does it rise as prefill predicts?
  4. Set an SLO (e.g. TTFT ≤ 1 s, TPOT ≤ 100 ms) and compute your goodput.
  5. If your provider offers prompt caching, repeat with a long, fixed system prompt and compare TTFT and cost with and without caching.
