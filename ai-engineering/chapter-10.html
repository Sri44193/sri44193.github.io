Step 1: Enhance context

Give the model the information it needs 📖 PDF p. 474–475

🧒 Plain English The first upgrade is usually letting the system build context for each query: retrieve text, images or table data (RAG, Chapter 6) and call tools such as web search, news or weather APIs. The book calls context construction "feature engineering for foundation models": it supplies what the model needs to answer well.
⚠️ Providers differ Most model APIs let you upload files and use tools, but with limits: how many documents and which types, retrieval settings like chunk size, which tools, and whether tools run in parallel or support long jobs. A dedicated RAG system may take as many documents as your vector database holds; a generic API may take only a few.
🧪 Testing angle Test context building separately from generation: for a set of questions, is the right document retrieved? Then check generation against that context (Chapter 4's factual consistency). Include tests at the provider's limits: too many files, an unsupported file type.

Step 2a: Input guardrails

Stop private data leaking out and bad prompts getting in 📖 PDF p. 475–477

🧒 Plain English Guardrails are checks placed wherever there's risk. Input guardrails protect against two things: (1) prompt attacks (Chapter 5) and (2) leaking private information to an external model API. Risks can be reduced but never fully removed.

💧 How leaks happen

An employee pastes a secret or a customer's data into a prompt (the book cites a Samsung leak via ChatGPT) · a developer puts internal policies in the system prompt · a tool pulls private data from a database into the context.

🔎 What to detect

Personal information (ID numbers, phone numbers, bank accounts) · human faces · keywords tied to intellectual property or privileged information. You choose the classes; many detectors use AI.

⚙️ Mask, send, unmask (the reverse PII map) 
query    ← "Call me on 07700 900123 about my refund"
if policy == block: reject the query                  # option 1: block it entirely
# option 2: remove the sensitive part
masked   ← "Call me on [PHONE NUMBER] about my refund"
pii_map  ← { "[PHONE NUMBER]": "07700 900123" }      # kept inside your system
answer   ← external_model(masked)                    # the API never sees the number
for placeholder, value in pii_map:
    answer ← answer.replace(placeholder, value)      # unmask before showing the user
🧪 Testing angle Build a PII test set: phone numbers in many formats, IDs, bank details, addresses, names in other scripts, PII hidden inside code or JSON. Measure what the masker misses (false negatives) and what it over-masks (false positives), and check that unmasking puts the right value back in the right place.

Step 2b: Output guardrails, retries and trade-offs

Catch bad outputs and decide what to do about them 📖 PDF p. 477–480

🧒 Plain English Output guardrails do two jobs: catch failures, and set the policy for each failure type. The easiest failure to catch is an empty response when one isn't expected.

📉 Quality failures (Ch 4)

Wrong format (e.g. invalid JSON) · hallucinated, factually inconsistent answers · simply bad answers (a poor essay).

🔐 Security failures (Ch 5)

Toxic content · private or sensitive data · triggering remote tool or code execution · brand risk: misrepresenting your company or competitors.

Three common failure policies
⚠️ The trade-offs Reliability vs latency: some teams skip guardrails because they add latency (early readers told the author this gave them nightmares). Streaming: partial answers are hard to judge, so unsafe text can reach users before it's blocked. Too safe: also track the false refusal rate, since blocking legitimate requests frustrates users.
📌 Who provides guardrails Model providers build some in (balancing safety against flexibility). Third-party APIs reduce what you build; self-hosting means less input-leak risk. Off-the-shelf tools: Meta's Purple Llama, NVIDIA NeMo Guardrails, Azure PyRIT and AI content filters, the Perspective API, OpenAI's moderation API. Many cover inputs and outputs, and some gateways include them. Scorers (often small AI models) sit with the model APIs or inside the output guardrails.
🧪 Testing angle For each failure type, write a test that forces it (e.g. a mocked model returning invalid JSON or an empty string) and assert the policy: did it retry, how many times, did it hand over to a human, what did the user see? Report both miss rate and false refusal rate.
❓ Check yourself
Your SLO is tight and invalid JSON happens 5% of the time. Retry after failure, or parallel calls?
Parallel calls keep latency down (no waiting for the first failure), at the price of more API calls. Retry-after-failure is cheaper but doubles latency for the 5%.
Why is a guardrail with zero harmful outputs not automatically a good one?
It may block many legitimate requests. Measure the false refusal rate too.

Step 3a: The router

Send each query to the best solution 📖 PDF p. 480–482

🧒 Plain English Instead of one model for everything, a router sends each query where it fits best. Benefits: specialised models can beat a general one (troubleshooting vs billing), and cheap models can handle simple queries. A router is usually an intent classifier: it predicts what the user wants.

The book's customer-support routing example

🧭 Next-action predictor

For agents: code interpreter or search API next? For memory: use the attached document about Melbourne, or search the web?

⚡ Keep routers small

Often adapted small models (GPT-2, BERT, Llama 7B) or tiny classifiers trained from scratch, so several can run without adding much latency or cost.

📏 Context limits

A 1,000-token query bound for a 4K-context model fetches an 8,000-token web result: either truncate the context or reroute to a model with a bigger window.

📌 The common pattern Routing usually happens before retrieval (is it in scope? does it need retrieval?), though it can also come after (should a human take over?). The most common flow: routing → retrieval → generation → scoring.
🧪 Testing angle A router is a classifier, so test it like one: a labelled set of queries per intent, a confusion matrix, and special attention to costly mistakes (a billing dispute sent to a bot, a harmless question refused as out of scope). Include ambiguous one-word queries.

Step 3b: The model gateway

One door to every model 📖 PDF p. 482–484

🧒 Plain English A model gateway is a layer between your apps and all the models (commercial APIs and self-hosted ones) that offers one unified interface. If a provider's API changes, you update the gateway, not every app.
⚙️ A gateway in its simplest form (pseudocode) 
endpoint POST /model (provider, model_name, input, max_tokens):
    check caller is allowed to use model_name        # access control
    check caller's usage budget                      # cost management
    try:
        reply ← adapter[provider].generate(model_name, input, max_tokens)
    except rate limit or outage:
        wait and retry, or switch to a fallback model     # fallback policy
    log request, response, latency, tokens            # one place for logs and analytics
    return { "response": reply }                     # same shape for every provider

🔑 Access control

People get gateway access, not the organisation's API keys, which can easily leak. Fine-grained rules decide which user or app can use which model.

💰 Cost management

Monitor and limit API usage to prevent abuse.

🛟 Fallbacks

API failures are "unfortunately common": reroute to another model, retry after a wait, or fail gracefully.

➕ Extras

Load balancing, logging, analytics, sometimes caching and guardrails.

Off-the-shelf gateways: Portkey AI Gateway, MLflow AI Gateway, Wealthsimple LLM Gateway, TrueFoundry, Kong, Cloudflare. A similar "tool gateway" could front many tools, but wasn't common as of writing.

🎯 Analogy A hotel reception desk: guests don't get master keys to every room. Reception checks who you are, gives the right key, keeps a log, and sends you to another room if yours is out of service.
🧪 Testing angle Chaos-test the gateway: make the primary provider return 429 (rate limit) and 500 errors, or time out. Does it fall back? Do answers from the fallback model still pass your evaluation suite? Are an unauthorised user's calls rejected and budgets enforced?

Step 4: Caches, exact and semantic

Don't compute the same answer twice 📖 PDF p. 484–487

🧒 Plain English Chapter 9's KV and prompt caches live inside the model service. This step adds system caches, in two kinds: exact (reuse only for identical requests) and semantic (reuse for requests that mean the same thing).
🎯 Exact cache🧠 Semantic cache
Reused whenThe request is identical (e.g. the summary of product #123; a repeated vector search)The request is similar enough ("capital of Vietnam?" vs "capital city of Vietnam?")
StorageIn memory, or PostgreSQL, Redis, tiered storageNeeds a vector database of query embeddings
RiskLow, apart from leaks (see trap)Higher: depends on good embeddings, working vector search and a well-chosen threshold. A wrong match returns a wrong answer; the search itself costs time and compute
VerdictEspecially useful for multi-step or slow work (chain-of-thought, retrieval, SQL, web search)Value is "more dubious"; worth it only with a high hit rate, after evaluating cost and risk
⚙️ Semantic cache lookup 
e      ← embed(query)                          # embedding model
match  ← vector_search(cache, e)               # most similar cached query
if similarity(match) > threshold:            # threshold needs trial and error
    return match.answer                         # cache hit
answer ← run the full pipeline(query)
store (e, query, answer) in cache
return answer
📌 What to cache, and for how long Use an eviction policy: LRU (least recently used), LFU (least frequently used) or FIFO. Don't cache user-specific queries ("status of my order?") or time-sensitive ones ("weather?"). Many teams train a classifier to decide whether a query should be cached.
⚠️ The cache data leak (the book's example) User X asks "What's the return policy for electronics?" The answer depends on X's membership, so the system fetches X's details and includes them. It wrongly treats the question as generic and caches the answer. User Y asks the same question and gets X's information.
🧪 Testing angle Write a two-user cache test: user A asks a question that pulls personal data, user B asks the same thing; assert B never sees A's data. For semantic caches, build near-miss pairs that look alike but differ in meaning ("cancel my order" vs "don't cancel my order") and check they don't hit the same entry.

Step 5: Agent patterns and write actions

Loops and real-world actions 📖 PDF p. 487–489

🧒 Plain English Until now each query flows once, straight through. Agent patterns (Chapter 6) add loops, parallel steps and branches: e.g. after generating, the system decides the task isn't done, retrieves more, and feeds the draft plus new context back into a model. Write actions let outputs change the world: send an email, place an order, start a bank transfer.
⚠️ More power, more risk Write actions make a system far more capable but far riskier: grant them "with the utmost care". And every added component adds failure modes, making the system harder to debug. That's why observability comes next.
🧪 Testing angle For every write action, test the guard as much as the action: human approval for risky actions, limits (amount, recipients), idempotency (a retry mustn't send two emails or two payments) and a dry-run mode for test environments. For loops, test that they terminate (a maximum number of steps).

Monitoring and observability

Designed in, not bolted on 📖 PDF p. 489–491

🧒 Plain English Monitoring has the same goal as evaluation: reduce risks (failures, attacks, drift) and find opportunities (improvements, savings). The book uses monitoring for tracking a system's information, and observability for the whole process of instrumenting, tracking and debugging it.

⏱️ MTTD

Mean time to detection: when something goes wrong, how long until you notice?

🔧 MTTR

Mean time to response: after detection, how long until it's resolved?

💥 CFR

Change failure rate: % of changes or deployments that need a fix or rollback. Don't know yours? Your platform needs to be more observable.

📟 Monitoring🔬 Observability
Watch the outputs to spot when something's wrong inside. No promise they'll tell you what.Instrument the system so its internal state can be worked out from its logs and metrics, without shipping new code to debug it.
📌 Evaluation and monitoring work as a pair A high CFR means your evaluation pipeline should catch bad changes before deployment. Evaluation metrics should map onto monitoring metrics (good in evaluation → good in production), and issues found in monitoring should feed back into evaluation as new test cases.
🧪 Testing angle MTTD, MTTR and CFR are perfect QA lead KPIs. Every production incident becomes a regression test, which over time lowers CFR.

Metrics: design them around failures

A metric's job is to tell you something's wrong 📖 PDF p. 491–493

🧒 Plain English Metrics aren't the goal; nobody cares about a relevance score unless it serves a purpose. First list the failures you want to catch, then design metrics that catch them. Don't want hallucinations? Track whether outputs can be inferred from the context. Worried about cost? Track tokens per request and cache hit rate.
📐 FormatEasiest. E.g. % invalid JSON, and of those, how many are easy to fix (missing bracket) vs hard (missing keys).
✍️ QualityFactual consistency, conciseness, creativity, positivity; often scored by AI judges.
🛡️ SafetyToxicity, PII in inputs and outputs, how often guardrails fire, refusal rate, abnormal queries (edge cases or attacks).
💬 User signalsGenerations stopped halfway, turns per conversation, tokens per input and output, output token distribution over time.
⏱️ Latency and 💰 costTTFT, TPOT, total latency (per user), query count, input/output tokens, TPS, requests per second against rate limits.
📌 Make metrics useful Each component has its own metrics (retrieval: context relevance and precision; vector DB: storage and query time). Check how metrics correlate with your business north star (daily active users, session duration, subscriptions). Mix spot checks (samples, fast) with exhaustive checks (every request). And make every metric breakable down by user, release, prompt/chain version and type, and time.
🧪 Testing angle For each item in your risk list, write down the metric that would reveal it and the alert threshold. If a known failure has no metric, it has no MTTD: you'll learn about it from customers.

A typical debugging path. Fast detection needs fast metrics; fast response needs logs that aren't delayed
📌 The logging rule: log everything Configuration (API endpoint, model name, sampling settings such as temperature, top-p, top-k and stop conditions, prompt template) · the user query, the final prompt sent, the output and intermediate outputs · tool calls and their outputs · component start, end and crash. Tag every log with IDs showing where it came from. Use AI-powered tools to analyse the volume, but also read production data by hand daily: Shankar et al. (2024) found developers' idea of good and bad outputs changes as they see more data.
🧒 Traces Logs are separate events; a trace links them into one request's story from query to response (the book shows LangSmith). When a query fails, you should be able to point at the exact step: bad processing, irrelevant retrieved context, or a wrong generation.

Drift: three things that change without telling you

📝 System prompt

A shared template was updated; a colleague fixed a typo. Simple logic can catch this.

🧑 User behaviour

Users adapt, e.g. learning to ask for shorter answers, so response length slowly drops. Metrics show it; finding the cause takes investigation.

🤖 The model behind the API

Same API name, new model underneath, not always announced. GPT-4 and GPT-3.5 scored differently between March and June 2023; Voiceflow saw a 10% drop moving from gpt-3.5-turbo-0301 to -1106.

🧪 Testing angle ➕ Cheap drift alarms: hash the final system prompt and alert when it changes; run a small canary evaluation set against the production API daily and alert when scores move. Pin model versions where the provider allows it.

AI pipeline orchestration

Wiring the components into one pipeline 📖 PDF p. 496–498

🧒 Plain English An orchestrator defines how components work together, in two steps: components definition (which models, data sources, tools, evaluation and monitoring tools; a gateway makes adding models easier) and chaining (function composition: the steps from query to finished task). It passes data between steps, checks formats match, and should alert you when a step fails. It's different from general workflow tools like Airflow or Metaflow.

Why user feedback matters more for AI

Explicit vs implicit, and the data flywheel 📖 PDF p. 498–500

🧒 Plain English Feedback always helped evaluate and guide software. For AI it is also proprietary training data, a competitive advantage that powers the data flywheel (Chapter 8): launch early, collect feedback, improve, attract more users. (Open-source apps struggle here: people self-host and you never see usage.) Feedback is user data, so respect privacy and tell users how it's used.
👍 Explicit feedback🕵️ Implicit feedback
WhatUsers answer a direct request: thumbs, stars, "Did we solve your problem?"Inferred from actions: buying a recommended product means a good recommendation
ProsEasy to interpret, well understoodPlentiful; limited only by imagination
ConsSparse (extra effort), and biased: unhappy users complain moreNoisy and app-specific: sharing a chat might mean "great" or "look at this mistake"
🧩 The book's hotel example An assistant suggests three Sydney hotels (~$400, ~$200 and ~$300 a night). "Book the one near the galleries" reveals an interest in art. "Is there nothing under $200?" reveals price sensitivity and that the assistant hasn't understood the user yet.
📌 Three uses of conversational feedback Evaluation (monitoring metrics) · development (training or guiding future models) · personalisation (adapting to each user). It's been studied for years (reinforcement learning from language feedback, Alexa, Spotify voice, Yahoo! Voice), but needs data analysis and user studies to interpret.

Reading conversational signals

What users' words and actions tell you 📖 PDF p. 500–504

⏹️ Early termination

Stopping generation, leaving the app, telling a voice assistant to stop, or leaving an agent hanging: probably going badly.

✏️ Error correction

"No, …", "I meant …", rephrasing (detectable by heuristics or ML). Pointed fixes: "Bill is the suspect, not the victim." Agent nudges: "Also check their GitHub page."

🤨 Confirmation requests

"Are you sure?", "Check again", "Show me the sources": maybe not wrong, but missing detail or not trusted.

📝 User edits

A user fixing generated code is a very strong signal, and free preference data: original = losing response, edit = winning response.

😠 Complaints and sentiment

"Wrong", "too long", "Uggh". Track sentiment across a conversation: angry at the start but happy at the end suggests it got resolved.

🙅 Model refusals

"Sorry, I don't know that" or "As a language model, I can't…": the user is probably unhappy.

Repetitive or rude: about 1%. Knowing why users are unhappy tells you what to change (e.g. "too long" → prompt for concise answers).

🔄 Regeneration

May mean "not satisfied", or just "show me options" (common for creative work). A stronger signal with pay-per-use billing. Some apps then ask "better or worse?", which yields preference data.

🗂️ Organising chats

Delete = probably bad (or embarrassing). Rename = good chat, bad auto-title. Share and bookmark are signals too.

📏 Length and diversity

Long chats: good for an AI companion, bad for customer support. Long and repetitive (low distinct tokens or topics) = the user may be stuck in a loop.

🧪 Testing angle Turn these into dashboards: % of generations stopped early, % of turns starting with "No" or "I meant", regeneration rate, edit rate, refusal rate. A spike after a release is an early regression alarm, often faster than any thumbs-down count.
❓ Check yourself
A user shares a conversation. Good or bad sign?
It's ambiguous: some people share great answers, others share glaring mistakes. Combine it with other signals (e.g. rephrasing afterwards) and study your users.

When to collect feedback. It should always be possible, and never intrusive
🧩 Examples from the book Inpainting (DALL-E): select part of an image and describe the fix; better results for users, precise feedback for developers. Side-by-side: ChatGPT shows two full answers; Gemini shows the start of each and you expand one (it's unclear which gives more reliable votes). Google Photos asks "same person?" when unsure. Apple's guidelines advise against asking for positive feedback (good results should be normal), but one product team said positive feedback shows which features users love.

How to collect: build it into the workflow

🎨 Midjourney

Four images per prompt. Upscale one = strongest positive signal; variations = weaker positive; regenerate = none are good enough (or just curiosity).

💻 GitHub Copilot

Suggestions appear in grey: Tab accepts, typing on ignores. Both are feedback at zero effort.

📧 Standalone chat apps

ChatGPT can't tell if the email it wrote was sent; Gmail can. Apps outside the user's workflow get weaker signals.

📌 Design rules Easy to give and easy to ignore · give users a reason to give good feedback · collect context with it (the last 5–10 turns), with consent: through terms of service or a "share my recent data" checkbox · explain how feedback is used (personalisation, statistics, training), and only promise privacy you really provide · don't ask the impossible: add an "I don't know" option · use clear icons and tooltips · decide whether feedback is private or public (people are more candid in private; when X made likes private, likes reportedly went up, but discoverability dropped).
⚠️ A confusing form gives you wrong data The author ran a workshop feedback form (on Luma) where the angry-face emoji meant 1 star but sat where 5 stars usually is. People writing glowing comments gave 1-star ratings by mistake.
🧪 Testing angle Feedback widgets are features: test them. Does the thumbs-down store the right response ID and context? Does "share my data" respect the user's choice? Usability-test rating scales on a few real users before launch to avoid a Luma-style mix-up.

Feedback limitations: biases and degenerate loops

Feedback isn't a free lunch 📖 PDF p. 514–516

BiasWhat happensWhat to do
😇 LeniencyPeople rate too kindly to avoid hassle (a low rating triggers "why?"). Uber, 2015: average driver rating 4.8; below 4.6 risked deactivationLook at the rating distribution; use descriptive options ("Great ride", "Pretty good", "Could've been better", "Don't match me again") instead of numbers
🎲 RandomnessUnmotivated users click anything, e.g. without reading two long answersDon't ask for heavy effort; treat votes as noisy
📍 PositionThe first option gets more clicks regardless of qualityRandomise positions, or model the true success rate per position
📏 PreferenceLonger answers win even when less accurate (length is easier to see than errors); recency bias favours the last answer seenInspect feedback for these patterns before trusting it
🧒 Degenerate feedback loops You only get feedback on what you show. When feedback trains the model, its own predictions shape the next round of feedback and amplify early biases. Also called exposure bias, popularity bias or filter bubbles.

A small early difference becomes a huge one
🧩 Two more loops from the book The cat haven: a few early users like cat photos, so the system makes more cats, which attracts cat lovers, who like more cats… The same mechanism can amplify racism, sexism or explicit content. The liar: training on user approval can teach a model to say what users want to hear: sycophancy (Sharma et al., 2023).
🧪 Testing angle Add sycophancy tests to your evaluation: ask a factual question while asserting a wrong answer ("I'm sure the capital of Australia is Sydney, right?") and check the model still corrects you. Re-run them after every feedback-based finetune.
❓ Check yourself
90% of your ratings are 5 stars. Does that mean users love the product?
Not necessarily: leniency bias. Look at the distribution, how it changes over time, and implicit signals (stopping early, rephrasing) to cross-check.
In side-by-side tests, users pick the left answer 65% of the time. What should you change?
Randomise which side each model's answer appears on (position bias), and correct past results for position.

✅ One-page cheat sheet

  1. 🏗️ Start with query → model → response; add parts as needed: context → guardrails → router and gateway → caches → agents and write actions. Each adds capability and failure modes.
  2. 📚 Context = feature engineering for foundation models. Providers differ in file limits, retrieval settings and tool support.
  3. 🛡️ Input guardrails: block or mask PII (reverse PII map to unmask) and stop prompt attacks. Output guardrails: catch quality and security failures; policies = retry, parallel calls, hand over to a human. Track the false refusal rate.
  4. 🔀 Router = small, fast intent classifier: specialised or cheaper models, out-of-scope stock replies, clarifying questions. Usual flow: routing → retrieval → generation → scoring.
  5. 🚪 Gateway = one interface to all models: access control, cost limits, fallbacks, logging.
  6. 🗃️ Exact cache (safe, simple) vs semantic cache (more hits, risk of wrong answers). Don't cache user-specific or time-sensitive queries; beware cross-user leaks.
  7. 🤖 Agent loops and write actions: very powerful, very risky; add with the utmost care.
  8. 👀 Observability is designed in. Measure MTTD, MTTR, CFR. Evaluation and monitoring feed each other.
  9. 📊 Design metrics from failure modes: format, quality, safety, user signals, latency, cost. Break them down by user, release, prompt version and time.
  10. 📜 Log everything, read production data daily, trace each request. Watch drift: system prompt, user behaviour, the model behind the API.
  11. 🔗 Orchestrators define components and chain them; consider starting without one. Run independent steps in parallel.
  12. 💬 Feedback = proprietary data for the flywheel. Explicit (clear, sparse) vs implicit (plentiful, noisy). Signals: early stops, corrections, edits, complaints, sentiment, refusals, regenerations, deletes, conversation length.
  13. 🎛️ Ask at the start, on failures, when unsure (and rarely on success); build feedback into the workflow (Midjourney, Copilot); collect context with consent; keep forms unambiguous.
  14. ⚠️ Biases: leniency, randomness, position, preference (length, recency). Beware degenerate feedback loops and sycophancy.
