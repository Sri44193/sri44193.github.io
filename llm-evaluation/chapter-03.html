The big picture

The whole chapter on one page. Come back here after each topic.

📌 The chapter in one sentence In production you're evaluating a pipeline, not a model call, so evaluation must work like a control system: every stage (intake, prompt, decoding, tools, retrieval, output, safety, budgets, monitoring, rollout) gets a check that produces a signal and triggers a defined action, preventing expensive failures instead of analysing them afterwards.
🧪 Why a QA lead should care Each control here is something you can test and own: validators, contract checks, claim gates, canary criteria. 1

The inference pipeline, and why it needs controls

Failures live in the seams between steps 📖 PDF p. 122–124

🧒 Plain English Inference-time evaluation = continuously checking, validating and correcting behaviour as each live request flows through the pipeline: intake and validation → prompt building → optional retrieval → optional tool calls → generation under a decoding policy → output validation. Training can't reveal what goes wrong here: incomplete or adversarial inputs, drifting prompts, stale retrieval, tool timeouts, new phrasing.

💬 User-facing thread

Ticket in → drafted reply out. What the user sees.

⚙️ Execution thread

Retrieval hits, tool calls, failures, retries, verification flags. What actually happened.

📌 The key rule A high-impact claim (like "your refund has been issued") belongs to the execution thread first. The reply may only say what the execution thread proved. Every control in this chapter must produce a measurable signal that triggers an action.
🎯 Analogy A waiter (the reply) may only tell you "your order is being cooked" if the kitchen ticket system (the execution thread) shows it was accepted. Sounding confident isn't evidence.

Input validation and intake policies

Stop bad inputs before any generation 📖 PDF p. 124–126

🧒 Plain English Many incidents start before the model sees the ticket: malformed input, missing metadata, too long, or adversarial. The input isn't just text: it includes locale, customer tier and whether identity verification is required. If required fields are missing, don't guess; in high-risk account_access cases, uncertainty is itself a reason to escalate. Intake must be deterministic: if validation fails, take a safe, auditable fallback path instead of generating.

3

Prompt governance: prompts as versioned product code

The highest-frequency lever for behaviour change 📖 PDF p. 126–128

🧒 Plain English A tiny prompt edit can change routing, refusals, verbosity and tool use. Without versions you can't tell what caused a change; without gates you ship "regressions disguised as tone improvements". A prompt isn't one string: it's a template with variables, a policy insert and an output contract.

🪪 1. Log identity

Every request logs PROMPT_ID, PROMPT_VERSION and a hash of the template (e.g. SHA-256). When a metric moves, check whether the hash moved.

🎚️ 2. Classify by risk

Each change type sets the regression scope it needs.

↩️ 3. Reviewable and reversible

Prompt diffs reviewed like code, and easy to roll back.

🟢 Wording / toneLow risk → narrow slice checks.
🟠 Examples, structureMedium → wider regression on affected intents.
🔴 Constraints, output contract, tool instructionsHigh risk → full regression across every safety-critical slice, triggered automatically.

A simplified prompt-change risk matrix (the book's Figure 3.3 idea).

🧪 Testing angle ➕ Put prompts in the repo, and add a CI rule: any diff touching the policy insert, the contract or tool instructions runs the full high-risk suite before merge.
4

Output contracts and the bounded reject–repair–fallback loop

Structure is a control layer, not a quality score 📖 PDF p. 128–130

🧒 Plain English Assistants often fail on structure: almost-valid JSON, a missing field, a category that doesn't exist. That breaks automation and fools judges (a "helpful" reply the system can't use). The policy: validate the contract → repair only if the fix is purely syntactic and safe → fall back if the meaning is unclear → cap retries, since they add latency and cost.

⚠️ What a passing contract does NOT prove That the category is right, the reply is safe, or the tool calls were appropriate. Those are separate controls with separate metrics. Keeping them apart speeds up debugging.
5

Decoding policy and stability

Less randomness where mistakes are expensive 📖 PDF p. 130–131

🧒 Plain English A decoding policy is the sampling settings (mainly temperature and top-p) that control how random answers are. Randomness can flip a refusal or verification wording in high-risk cases, so set decoding by risk tier.
Risk tierTemperatureTop-pWhy
🔴 High0.01.0Stable decisions and refusals
🟠 Medium0.20.9A little variety
🟢 Low0.40.95Variety can improve the experience
📌 Measure stability on decisions, not wording Run the same input several times and check decision agreement on key fields: category, refusal type, whether a verification-sensitive claim appears. Different wording is fine; different decisions are not. High-risk slices need high agreement.
➕ Where this connects AI Engineering Ch 2 explains temperature and top-p. Even temperature 0 isn't always perfectly deterministic in practice, which is why measuring agreement still matters.
6

Runtime evaluation: calibrated judges and human sampling

A risk-weighted sampling pyramid 📖 PDF p. 132–133

🧒 Plain English On live traffic you rarely have labels for everything. So layer the checks: cheap ones on everything, expensive ones on samples, stratified by slice and oversampling high-risk and incident-related traffic. Version the judge rubric and calibrate it, so score changes mean product changes, not grader drift.
👩 HumansSmallest sample, heavily weighted to account_access and verification-sensitive refunds.
⚖️ AI judgeSlice-stratified sample across top intents and the high-risk intent.
📏 Reference metricsLabelled subsets, e.g. routing accuracy.
✅ Deterministic validatorsEvery single request.

Top = most expensive, fewest requests. Bottom = cheapest, all traffic.

🧪 Testing angle This is a test strategy pyramid for production. Report each layer separately; a judge score without its sample size and slice mix is hard to trust.

Tool calling and evidence-bound claims

Claims must be backed by executed evidence 📖 PDF p. 133–135

🧒 Plain English The assistant can write a convincing refund reply without checking anything. Refund confirmation isn't a writing task; it's a claim that needs proof. Tool correctness is a chain of four obligations:

⚙️ The claim gate 
claims_processed ← reply contains "refund issued" or "refund has been processed"
if claims_processed and not trace.billing_verification_succeeded:
    block the response                 # don't just tune temperature
    send a safe fallback template
    open an incident → it becomes a new regression test
📌 Remember Map each claim class to the execution flag that must exist before it may appear (an evidence binding map). The gate checks the trace, never the model's own say-so. "Verification-required claim without evidence" is a hard-blocker metric that must be near zero.
🧪 Testing angle Mock the billing tool to fail, time out, or return "not verified", and assert the reply never contains confirmation language. ➕ Keyword checks miss paraphrases ("your money is on its way"), so add paraphrased claims to the test set and consider a classifier for claim detection.
8

Retrieval controls and groundedness

Evaluate retrieval separately from generation 📖 PDF p. 135–136

🧒 Plain English Retrieval is a pipeline stage with its own signals. If you don't measure it separately, the model gets blamed for index, ranking or freshness problems, and people "fix" them with prompt edits. Groundedness has three separate parts:

📚 Coverage

Was the relevant policy or knowledge retrieved at all?

🤝 Faithfulness

Are the reply's claims supported by what was retrieved?

🔗 Citation correctness

Do citations point to the right evidence?

📌 Remember Log doc IDs and ranks; watch for rank instability and missing coverage on critical slices. Retrieval failures cluster by intent (refund policies change, cancellation rules differ by region, account guidance follows security policy). When coverage drops, fix retrieval and expand the suite, not the prompt.

Safety controls as slice-based gates

A low overall rate can hide a dangerous slice 📖 PDF p. 136–137

🧒 Plain English Chapter 2's safe outcomes (refuse, safe redirect, escalate, comply after verification) become runtime hard blockers on high-risk slices. "Disable 2FA" → refuse or safe redirect, often with escalation. Refund confirmations → only after verification.
IntentSeverityControls that must hold
account_access🔴 HighNo bypass guidance; refuse or redirect; escalate when verification needed (hard blocker)
refund_request🟠 Medium–highConfirmation only with evidence flag (hard blocker)
escalation🟠 MediumRoutes to a human instead of unsafe self-help
bug_report, cancellation🟢 LowerPolicy-compliant, no invented actions

An illustrative safety gate stack by slice (my simplification of the book's Figure 3.9).

🧪 Testing angle A safety suite needs adversarial prompts, paraphrase clusters, tool-degraded conditions (what does it say when verification is down?) and escalation tests. Always report safety per slice.
10

Performance and cost as first-class budgets

Five control dials 📖 PDF p. 137–138

🧒 Plain English Users feel the tail (p95/p99), not the average. Retries, long generations and tool timeouts live in the tail. Define budgets so these become controlled quantities.

🔤 Token budget

Caps generation length.

🔁 Retry budget

Caps contract repairs and tool retries.

⏱️ Timeout budget

Caps tool call time.

⚖️ Judge budget

Caps expensive grading.

📉 Error budget

Caps reliability decline over time.

🧩 Why budgets help debugging p95 latency rises → you can see retries rose, because retries are counted in the contract loop. Cost per request rises → you can trace it to output length drift from decoding or preference tuning.

Monitoring, drift and incident response

Monitoring must lead to actions 📖 PDF p. 138–140

Drift typeSignal
🧑 TrafficNew intents, new phrasing
🛠️ ToolRising failure rate or latency
📚 RetrievalCoverage drops, rank instability
📜 PolicyBehaviour no longer matches updated policy

Possible actions: tighten a budget, increase escalation, roll back a canary, add a slice to the regression suite.

⚙️ A simple intent-mix drift alarm (the book's idea) 
p ← share of each intent in the baseline traffic        # e.g. refund 40%, bug 30%, …
q ← share of each intent in recent traffic
delta ← Σ over all intents of |p(intent) − q(intent)|
if delta > 0.20:
    alert: "offline suite may no longer represent traffic"
    inspect new traffic → update slices → add cases
🧩 Worked example (mine) Baseline: refund 40%, bug 30%, account 30%. This week: refund 30%, bug 30%, account 40%. delta = |40−30| + |30−30| + |30−40| = 20 points = 0.20: right at the threshold, so not flagged yet (it must be greater than 0.20).

Rollouts: shadow, canary and rollback

Evaluation as a deployment gate 📖 PDF p. 140–141

🧪 Offline suitesRegression and gate suites must pass first.
👻 ShadowThe candidate sees real traffic, but users never see its answers. Compare behaviour safely.
🐤 CanaryA small share of real users; limits the blast radius. Watched by hard blockers.
🚀 Full rampOnly when every gate holds.
📌 Canary gates for the assistant Roll back on: more high-risk safety violations · evidence-bound claim violations · tool failure spikes · tail latency regressions. Write rollback criteria and owners before the rollout, so nobody debates during an incident.
🧪 Testing angle Rehearse a rollback: trigger a fake canary breach in staging and time how long it takes to revert. That's a real MTTR measurement (AI Engineering Ch 10).

Where each control sits in the running assistant
❓ Check yourself
Routing accuracy dropped after a knowledge-base update. Should you edit the prompt?
First check retrieval coverage and rank stability for the affected slices. It's likely a retrieval problem; fix the index or ranking and add cases, rather than patching with prompt edits.
The reply says "refund issued" and a judge rates it 5/5. Is it OK?
Only if the trace shows billing verification succeeded. Otherwise the claim gate blocks it, whatever the judge says.
Why measure stability on decision fields rather than text similarity?
Wording can vary harmlessly; what matters is whether the category, refusal type or verification claim flips between runs.

✅ One-page cheat sheet

  1. 🧭 Evaluate the pipeline. Two threads: user-facing reply and execution trace; claims belong to the trace first.
  2. 📨 Intake: required fields, no guessing, deterministic tagged truncation (5,000 head + 2,500 tail over 8,000 chars), safe fallback.
  3. 📝 Prompts: log ID, version and hash; classify changes by risk; contract, constraint or tool edits trigger full high-risk regression.
  4. 📐 Contracts: validate → syntactic repair → fallback, with capped retries. Passing ≠ correct or safe.
  5. 🎚️ Decoding by risk: high 0.0 / medium 0.2 / low 0.4 temperature. Measure decision agreement.
  6. ⚖️ Runtime evaluation: validators on all, references on labelled, judge on stratified sample, humans on high-risk.
  7. 🔐 Evidence-bound claims: tool → args → execution → claim matches outcome. No flag, no claim; block, fall back, open an incident.
  8. 📚 Retrieval: coverage, faithfulness, citations, separately. Log doc IDs and ranks.
  9. 🛡️ Safety by slice with hard blockers; test paraphrases and degraded tools.
  10. 💰 Five budgets: tokens, retries, timeouts, judges, errors. Watch the tail.
  11. 📈 Drift: traffic, tool, retrieval, policy; each alert → action; incidents become tests.
  12. 🚀 Rollout: offline → shadow → canary → full, with rollback criteria and owners set in advance.

Try it: a mini lab

Add three runtime controls to an LLM feature

  1. Write an intake validator with required fields and tagged truncation; boundary-test it.
  2. Wrap a model call in the contract loop: validate, one repair, then fallback. Count how often each path happens over 50 calls.
  3. Run 10 high-risk prompts 5 times each at temperature 0 and 0.7. Compute decision agreement on one key field.
  4. Write a claim gate test: mock the verification tool to fail and assert no confirmation wording (include 3 paraphrases).
  5. Write a one-page canary plan: gates, thresholds, rollback owner.
