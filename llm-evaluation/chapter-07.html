Chapter 7: Evaluating Routing and Reliability in Mixture of Experts LLMs

Models made of many specialist "experts" with a router that picks a few per token. Routing becomes a first-class test target: data separability, routing entropy, load balance, expert collapse, cold experts, token dropping, latency and cost.

The big picture

The whole chapter on one page. Come back here after each topic.

📌 The chapter in one sentence A mixture of experts (MoE) model only works if its router sends each token to the right few experts and keeps all experts usefully busy, so besides output accuracy you must test data separability, routing accuracy and calibration, load balance, collapse and dead experts, cold-expert readiness, token dropping, latency variance and cost, across training and inference.
🧪 Why a QA lead should care MoE models (Mixtral, DeepSeek, DBRX, Qwen-MoE…) can look fine on average benchmarks while some experts are broken, idle or overloaded. These are system-level failures that only routing metrics reveal. The running example is again a medical system with experts for X-rays, pathology and clinical text.

How a mixture of experts works

Huge total capacity, small active cost 📖 PDF p. 304–312

🧒 Plain English In a normal ("dense") transformer every parameter works on every token. In an MoE, the feed-forward part of some layers is replaced by many experts (small independent networks), and a router (gating network) picks only a few (often 1–4 out of 8 to hundreds) for each token. So total parameters can be enormous while the compute per token stays manageable: conditional computation.

🎯 Analogy A hospital triage desk (the router) sends each patient to two of many specialists (experts). Attention is the shared waiting room everyone passes through. If triage sends everyone to the same two doctors, the others never practise, and the hospital is really a two-doctor clinic with a big payroll.
Top-k routing
Only the k highest-scoring experts run for a token. Softmax routers can instead give soft weights.
Token-choice vs expert-choice
Tokens pick experts (risk: many tokens pick the same one) vs experts pick tokens (better load control, but coverage changes).
Capacity
The maximum tokens an expert can take per pass; overflow is rerouted or dropped (topic 13).
Multi-head attention
Several attention "heads", each learning a different kind of relationship between tokens, combined afterwards.
📌 Remember Experts can live on different devices, so tokens are sent across hardware and the results are gathered back. Evaluating an MoE means checking that experts and router work together: inputs go to the right experts, experts are used evenly, and specialisation actually emerges.

3

Data quality, coverage and separability

Experts can only specialise if the data can be told apart 📖 PDF p. 312–318

🧒 Plain English The router learns its boundaries from patterns in the data. If input types overlap heavily, it can't decide which expert should take what, experts can't specialise, and the MoE behaves like a poorly optimised dense model that still carries all the routing overhead. In a dense model, overlap mostly hurts generalisation; in an MoE it breaks the whole premise.

💎 Quality

Accuracy · annotation correctness · completeness · consistency · noise level · label reliability. Bad labels teach experts wrong patterns and the router wrong routes.

🗺️ Coverage

Domains (science, chat, legal) · tasks (summarise, QA, reason) · rare cases · edge cases · enough data for each expert's region.

⚖️ Skew

One dominant domain → a few experts get most inputs → others stay untrained → expert collapse.

🧩 Where MoE is used (from the book) Language (domains, styles, language families) · multimodal (an expert per modality) · recommendations (user segments, product categories) · autonomous driving (weather, object types, scenarios) · medical diagnosis: an expert for chest X-rays, one for pathology slides, one for clinical text; the router must send each input by modality.

Data readiness: simulate the experts before training

Diversity, separability, balance 📖 PDF p. 318–326

⚙️ Expert assignment simulation (the book's method) 
sample ← a slice of the training data
for each of 2–3 different embedding models:      # one model's biases can fake (or hide) separation
    vectors  ← embed(sample)
    clusters ← k-means(vectors, k = number of planned experts)   # e.g. 8, or a small multiple
    inspect cluster sizes
if most samples land in 1–2 clusters and several clusters are tiny:
    expect overload, starvation or unstable routing
    → rebalance, resample or collect more data before training

📊 Distribution and imbalance

Histograms of domains, classes and labels.

🫧 Clusters

k-means, hierarchical; clear clusters ≈ possible expert regions.

🗺️ Embedding views

Dimensionality reduction; compare several embedding models before concluding.

🧾 Profiling

Missing values, duplicates, structural consistency; enough examples per expert region.

Tools named: Cleanlab, Great Expectations, Hugging Face Datasets, DataPrep, FiftyOne, CleanVision, Label Studio (annotation agreement), scikit-learn, TensorBoard Embedding Projector, FAISS.

📌 Data KPIs specific to MoE Label correctness · missing data · consistency · duplication · domain, class and rare-case coverage · embedding space coverage · expert utilisation balance · routing entropy · data drift. Operational links: error rate per input segment, latency stability (overloaded experts slow everything), cost efficiency.
5

Pretraining validation and router learning

Similar inputs together, different inputs apart 📖 PDF p. 327–331

🧒 Routing entropy Entropy measures how spread out routing is. Too low: nearly everything goes to a few experts (poor separability, collapse). Too high: routing looks random, not meaningful. You want a healthy middle that matches real specialisation.
⚙️ ➕ Worked entropy example (4 experts) 
entropy = − Σ p(e) × log₂ p(e)
even split  [0.25, 0.25, 0.25, 0.25] → 2.00 bits  # maximum for 4 experts
collapsed   [0.97, 0.01, 0.01, 0.01] → ≈ 0.24 bits # one expert does almost everything

🎯 Specialisation coherence

Not just "expert 2 gets X-rays": measure per-expert, per-condition sensitivity, specificity, F1, AUROC (one may be better at pneumothorax, another at lung disease).

🫧 Separability

Intra- vs inter-cluster distances in embedding space.

🔬 Probing

Simple classifiers predicting disease, anatomy or modality from embeddings.

🚫 Misrouting rate

A pathology slide sent to the radiology expert. Checked against modality or diagnosis labels.

📏 Stability and drift

Assignments compared across checkpoints; representation drift (too much = unstable, too little = not learning).

👯 Redundancy

Experts with near-identical parameters or outputs waste capacity.

⚠️ A router can be confidently wrong Router probabilities are optimised for task performance, not honest uncertainty. Build a calibration curve: group routing confidence into bins and check the chosen expert's accuracy in each bin. Track overconfident misrouting separately; re-check after deployment, because new devices or populations can break calibration while confidence stays high.
6

Instruction and alignment tuning across experts

Obey the task without breaking specialisation 📖 PDF p. 331–336

🚦 Instruction routing accuracy

Share of instructions ("write a radiology impression") sent to the clinically right expert. The triage-desk test.

📋 Adherence and safety

Expert instruction adherence · clinical safety compliance (no unsupported claims or missed findings) · terminology correctness · completeness.

🎚️ Routing confidence margin

Top probability minus second. Small margins = ambiguous routing.

⚔️ Instruction conflict rate

Instructions that clash with an expert's specialty (radiology expert asked about pathology).

⚠️ Forgetting has a routing dimension in MoE In a dense model, forgetting spreads across shared parameters. In an MoE, if one expert forgets its specialty, no other expert automatically compensates. Measure the expert reassignment rate (did inputs move to different experts after tuning?) together with the expert forgetting rate. Router keeps using a degraded expert → hidden forgetting. Router routes around it → unstable specialisation. Either way it's a compound failure.
📌 Also Specialisation preserved before vs after tuning · instruction-level diagnostic accuracy · calibration · inter-expert agreement on similar instructions · bias across groups and devices · balanced instruction load · robustness to rephrased instructions · router sensitivity to instruction meaning.

Generalisation, load balance, collapse and dead experts

Is all the capacity actually used? 📖 PDF p. 339–343

🌍 Generalisation

External validation accuracy · generalisation gap · subgroup consistency · variance across institutions.

⚖️ Load balance

Utilisation per expert · load imbalance ratio = busiest ÷ least busy expert · activation frequency.

🫠 Collapse

Few experts get almost everything. Detected by low utilisation entropy and a high routing concentration index (share to the top few).

💀 Dead experts

Share of experts with ~zero assignments: wasted capacity.

Input validation and routing decisions at inference

Bad inputs get misrouted 📖 PDF p. 343–346

🧱 Structural validation

Resolution, modality metadata, file integrity, encoding, required fields. Input rejection rate: moderate is healthy; very high points upstream.

🧠 Semantic validation

Does a "chest X-ray" actually show a thorax? Mislabelled inputs → misrouting.

🚦 Routing decision accuracy

Routing vs ground-truth modality or diagnosis labels; misrouting rate is critical.

❓ Out-of-distribution

Flag unfamiliar inputs (new scanners, rare presentations) before routing.

🧪 Routing error attribution When a diagnosis is wrong, ask: was it misrouted, or did the right expert get it wrong? The routing error attribution rate (share of errors caused by misrouting) decides whether you fix the router or the expert.
📌 Also Routing confidence margin · routing stability under brightness, resolution or phrasing changes · utilisation shifts over time windows · input completeness · routing latency · calibration at inference · routing accuracy by segment · expert fallback rate (rerouting due to capacity or uncertainty) · cold-input routing rate · drift detection · expert overload · routing trace completeness for audits.

Routing stability and cold experts

Rare but valid, or broken? 📖 PDF p. 346–349

🧒 Plain English A cold expert is rarely activated, often because it handles rare diseases or unusual scans. Rarely used doesn't mean useless. The danger is that after long dormancy it no longer reflects current data and performs badly when its moment comes.

📏 Stability

Routing confidence variance for similar inputs over time · assignment persistence (the same domain keeps going to the same expert).

❄️ Cold-expert checks

Cold routing correctness · dormancy duration · cold calibration · reactivation success · knowledge retention vs just after fine-tuning.

📈 Long-term trends

Gradual concentration on fewer experts = early collapse. Rare-case routing success. Stability under distribution shift.

🏥 System impact

Cross-expert interference · clinical safety incidents caused by routing instability.

📌 The expert readiness score A composite of activation frequency, accuracy, confidence stability and knowledge retention. Low use + good accuracy + good calibration + correct rare-case routing → monitor and preserve. Low use + poor accuracy, calibration or reactivation → intervene. Don't "fix" a healthy rare specialist.
🧪 Testing angle ➕ Keep a small rare-case canary set per cold expert and run it on a schedule, so you measure readiness before a real rare patient arrives.
11

Latency variance, throughput and cost

Routing makes timing uneven 📖 PDF p. 349–355

🧒 Plain English Different tokens go to different experts on different devices, so response time varies with expert workload. Watch mean latency but especially p95/p99 and the variance: overloaded experts create long tails.
⚠️ Split routing latency in two Routing computation (scoring and selecting experts) vs routing communication (moving tokens to the devices hosting those experts). In large distributed MoEs the all-to-all token dispatch often costs more than computing the routing. Measure them together and you'll blame the wrong thing.

⏱️ Latency

Per expert processing time · variance across experts · queue wait after routing (overload signal).

📈 Throughput

Studies per hour · distribution across experts · stability as volume rises · scaling efficiency.

💰 Cost

Cost per inference and its variance · cost per expert activation · cost efficiency ratio (performance ÷ cost) · cost per successful inference · energy.

🔥 Contention

Experts competing for the same processors or memory bandwidth · utilisation too low (wasted) or too concentrated (overload).

📌 Also Clinical workflow compliance (share meeting time limits) · cost predictability over time · latency–cost correlation (necessary complexity or waste?) · expert-level cost vs diagnostic contribution.

12

Output quality consistency across experts

Quality shouldn't depend on which expert you got 📖 PDF p. 355–357

🧒 Plain English Specialists should raise quality, not make it a lottery. Check inter-expert agreement on clearly defined shared-domain cases (identical inputs, paraphrased instructions, augmented images, cases several specialists can judge), and accept appropriate disagreement on cases only one expert truly knows.

📊 Accuracy variance

Large gaps between experts on their own validation sets = uneven training.

🎯 Confidence consistency

"80% confident" should mean the same from every expert.

📋 Completeness and errors

All findings reported; no expert with a much higher error rate.

🔤 Semantic consistency

Standard terminology across experts; also rare-case, longitudinal and cross-institution consistency.

Token dropping, and the consolidated KPI table

A quiet MoE failure mode 📖 PDF p. 357–363

🧒 Plain English Each expert has a capacity. If too many tokens choose the same expert, extras are dropped, rerouted or sent down a fallback path. A dropped token gets a weaker representation, which can cause degraded reasoning, factual errors, repetition, broken formatting. It gets worse in long contexts and under heavy batching.

📉 Measure drops directly

Token drop rate overall, by sequence length, by token position, by task type, and under high-batch serving.

🔗 Correlate with quality

Factual accuracy, reasoning consistency, hallucination, latency, completion quality.

🗺️ Look for patterns

Certain languages, domains, prompt styles or long tasks dropping more = strong on average, failing in deployment.

❓ Check yourself
Routing entropy is near its maximum for every input type. Good news?
Not necessarily: very high entropy can mean routing is close to random rather than specialised. Check specialisation coherence and misrouting rate.
Expert 6 handles rare skin cancers and is used in 0.2% of requests. Retrain it?
Only if its readiness score is poor. If accuracy, calibration and rare-case routing are good, it's a rare-but-valid expert: preserve and monitor it.
Quality drops on long documents only under heavy load. What MoE-specific cause should you check?
Token dropping from expert capacity overflow: measure drop rate by sequence length, position and batch size.

✅ One-page cheat sheet

  1. 🧠 MoE = many experts + a router choosing top-k per token: huge capacity, small active compute.
  2. 🏷️ "MoE" models differ hugely (expert count, active experts, shared experts); add system metrics to benchmarks.
  3. 🫧 Experts need separable data; overlap turns an MoE into an expensive dense model. Skew → collapse.
  4. 🧪 Before training: k-means with k = experts on several embedding models; check cluster sizes.
  5. 📏 Routing entropy (not too low, not random), specialisation coherence per condition, misrouting, router calibration.
  6. 🔁 Alignment can cause forgetting with a routing twist: reassignment rate + forgetting rate together.
  7. 🎯 Specialisation depth = cross-expert accuracy differential (a strong diagonal).
  8. 🫠 Collapse: low utilisation entropy, high concentration, dead experts. Audit training cause vs distribution cause.
  9. 🚦 Inference: validate inputs, routing accuracy, OOD, margins, routing error attribution, trace completeness.
  10. ❄️ Cold experts: dormancy, reactivation, retention, readiness score; preserve rare-but-valid experts.
  11. ⏱️ Latency variance and tails; split routing compute vs communication; cost per successful inference.
  12. 🤝 Consistent quality across experts; agreement on shared cases, appropriate disagreement on specialist cases.
  13. 🕳️ Token dropping: measure by length, position, task and batch; correlate with quality.

Try it: a mini lab

Practise MoE metrics with a spreadsheet

  1. Invent routing counts for 8 experts over 10,000 tokens (one balanced set, one collapsed set). Compute utilisation shares, entropy and the load imbalance ratio.
  2. Build a 3×3 cross-expert accuracy matrix like topic 7 and judge the specialisation.
  3. Take 100 sentences from 4 topics, embed them with any free embedding model, run k-means with k = 4 and look at cluster sizes (the readiness simulation).
  4. If you can use an open MoE model locally, log which experts fire for prompts in different languages.
