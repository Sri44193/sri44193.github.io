Evaluation is a decision system, not a score

The four parts every evaluation needs 📖 PDF p. 38–41

🧒 Plain English A number like "helpfulness 8.2/10" on its own changes nothing. Evaluation only counts as evaluation when it can change what the team does. Otherwise it's just reporting.
🔎

Evidence

What you measured: a rule check, a metric, an AI judge's score, a human rating, a trace check.

🎲

Uncertainty

How much to trust it. Outputs vary, samples are small, judges wobble.

🚧

Threshold

The line you commit to before looking at results.

🎬

Action

What happens when the line is crossed: ship, block, investigate, roll back, mitigate.

🎯 Analogy: a CI quality gate "Code coverage 78%" is a metric. "Fail the build if coverage < 80%" is a decision. You already work this way in CI; the book applies the same idea to AI behaviour.
Metric (a measurement)Decision (a policy)
Routing accuracy is 92%Ship only if accuracy ≥ 90% overall and ≥ 88% on every critical ticket type
Policy violation rate is 0.2%Don't ship if high-risk violations exceed 0.1%, or if any zero-tolerance violation appears
📌 Remember
  • Quality is only one axis. A brilliant answer that's too slow, too expensive, or occasionally unsafe is still a failure (topic 5).
  • Thresholds are product policy, not afterthoughts. Start from baselines, risk tolerance, SLAs or legal rules, then recalibrate as data arrives.
  • "Without thresholds, metrics are not actionable, and releases become debates."
❓ Check yourself
Your dashboard shows "helpfulness 8.4". Why isn't that an evaluation yet?
There's no threshold or action attached. You'd need to know what score is acceptable, how much it normally varies, which slices matter, and what you'll do if it drops.
Name the four parts of an evaluation decision system.
Evidence, uncertainty, threshold, action.

What evaluation is not, and the loop it really is

Four look-alikes that give false confidence 📖 PDF p. 41–42

🏆

❌ "Run a benchmark once"

Benchmarks test a bare model. Your product adds prompts, tools, policies, real traffic.

👀

❌ "Ask teammates if it looks good"

That's a demo review: biased, low coverage, not repeatable.

🔧

❌ "Tweak the prompt until the demo works"

The fix may break other cases, cost more, or weaken safety. Prompt edits are code changes.

1️⃣

❌ "A one-time step"

Evaluation is a loop that never stops.

The running example: a support assistant

One product used throughout the chapter 📖 PDF p. 42–44

🧒 Plain English The assistant does three jobs on each support ticket: routes it to a category (billing, bug, account access, cancellation, escalation), drafts a reply in the right tone and format, and calls tools (billing lookup, account status, policy search) when it needs verified facts. 
sequenceDiagram
  participant C as 🙂 Customer
  participant A as 🤖 Assistant
  participant B as 💳 Billing tool
  C->>A: "I was charged twice, please refund"
  A->>A: route → billing_refund
  alt ✅ Correct behaviour
    A->>B: billing_lookup(account_id)
    B-->>A: result, or "missing identifier"
    A-->>C: asks for the order ID, explains it must verify first
  else ❌ The opening story's failure
    A-->>C: "Your refund has been processed!" with no lookup at all
  end
Same input, two behaviours. Only a trace (topic 6) shows which one happened.
📌 Why this example is useful It mixes every hard part of LLM testing in one product: classification (routing), open-ended text (replies), tool use, policy and safety rules, plus latency and cost. And not all failures are equal: a typo ≠ confirming a refund nobody checked.
4

Why classic ML evaluation breaks

Four reasons "compare prediction to the right answer" isn't enough 📖 PDF p. 44–48

🧒 Plain English Classic ML testing assumes: one input → one correct answer → compare. LLM products break that in four ways.
🌊

1 · Many right answers

Two good replies can share almost no words. Exact-match testing would fail a correct one. Test the behaviour, not the wording.

🎲

2 · Randomness

Same input, different output (temperature, tools changing, load). Test a distribution of outputs, not one run.

🧩

3 · The whole setup matters

A prompt edit can change behaviour more than a model upgrade. Prompt × documents × tools × policy × settings = too many combinations to test them all.

🤖

4 · Agents take steps

The final reply can look fine even though a step was wrong: wrong tool, bad arguments, skipped check.

🧩 Example: randomness in numbers Run the same 50 replies 5 times at temperature 0.7. Helpfulness looks fine in one run and borderline in another. The billing tool call happens most of the time but is skipped occasionally. If those skips land on refund or account-access tickets, that's not noise, it's a production risk.
🎯 Analogy: flaky tests You know flaky UI tests. An LLM is "flaky by design". You don't fix it by demanding identical output; you measure how much it varies and decide whether the variation matters.
⚠️ Common trap Logging only the model version. If the prompt or the document index also changed, you'll blame the wrong thing. And even when you see "retrieval changed the same day accuracy dropped", that's a hypothesis, not proof. Confirm with a controlled rerun that changes one thing at a time.
❓ Check yourself
What should a test check instead of "does the reply match the reference text"?
Whether the reply meets the task's behaviour contract: no unverified refund claim, asks for missing info, correct tone and format, follows policy.
In this chapter, what does "repeatable" mean for an LLM?
Bounded variation and stable decisions, not identical text every time.
5

What "working" means: Quality, Safety, Cost, Reliability

Four axes, risk tiers, and a written definition of done 📖 PDF p. 48–52

✅

Quality

Helpful, correct, complete, right format. Routes tickets correctly, useful replies.

🛡️

Safety

Policy, privacy, security. No leaked personal data, no invented account actions.

💰

Cost

Within budget. No wasted tokens, over-fetching or needless tool calls.

⚙️

Reliability

Consistent and fast. p95 latency, tool success rate, safe fallbacks.

⚠️ Common trap: "sounds better = is better" A version that improves tone but adds unsupported refund claims is worse. A more complete answer that doubles cost may be undeployable. Trade-offs are fine; hidden trade-offs turn releases into arguments.

🏋️ Load-bearing vs diagnostic metrics

Load-bearing: decide ship / block / roll backDiagnostic: explain why something moved
High-risk policy violation rate · routing accuracy on critical types · p95 latency · cost per ticketRetrieval hit rate · documents fetched · fallback frequency · judge-score spread · tool latency per endpoint

Rule of thumb from the book: 2–3 load-bearing metrics per axis; the rest are for debugging.

🔺 Risk tiers: not all failures are equal

🔴 HighIdentity, access, payment disputes, security, legal, personal data → serious harm possible. Zero tolerance and human review.
🟠 MediumAccount details, billing processes, interpreting policy → escalations or user harm.
🟢 LowGeneral guidance → inconvenient, unlikely to harm. Risk budget (a small error rate is allowed) and light sampling.

🚫 Zero-tolerance failure

Blocks release however rare. E.g. showing another user's data; claiming a refund without verification.

🎟️ Risk-budgeted failure

Allowed up to an agreed rate, unless it clusters in a critical slice. E.g. minor formatting slips.

✔️ A definition of "done" for the assistant

  • 🛡️ High-risk violations under the strict limit; zero catastrophic failures
  • ✅ Routing accuracy > 90% overall and on target for critical ticket types
  • ⚙️ Required tool verification succeeds > 98% where tools are needed
  • ⏱️ p95 end-to-end latency < 3 seconds at normal load
  • 💰 Average cost per ticket within budget
  • 🧭 No critical slice regresses enough to trigger review or rollback

Plus rollback triggers, because shipping isn't one-way: spikes in high-risk violations, tool failures causing false claims, sustained latency, cost spikes.

🧪 In your QA work This is a release exit criteria document for an AI feature, the same kind of artefact a QA lead already owns. Write it before testing starts so nobody can move the goalposts after seeing the results.
❓ Check yourself
A release improves average helpfulness but adds one unsupported refund claim in the gating suite. Ship?
No. Unsupported refund claims are a zero-tolerance failure; one case blocks release however good the averages look.
What's the difference between a load-bearing and a diagnostic metric?
Load-bearing metrics drive decisions (ship, block, roll back). Diagnostic metrics help explain why a load-bearing metric moved.

🏷️ Version everything (including data and judges)

Each run should record: model · prompt · retrieval settings · document index snapshot · policy version · tool schemas · inference settings · evaluator, judge model, judge prompt, rubric · test suite version · code commit.

⚠️ Common trap: a silent change of ruler If you swap the AI judge or reword its rubric, scores move even though the assistant didn't change. Refreshing the document index is a data change too. Unversioned, you'll blame the model for something the test setup did.

Cases, slices, and five kinds of datasets 📖 PDF p. 57–61

Five dataset types that make up a suite
🎯 Analogy: equivalence partitioning Slices are your equivalence classes. An average over all tickets can look great while the "account access" class quietly gets worse. Report and gate per slice.

🥇 "Gold" for open-ended answers

A checklist of required behaviour, not one perfect reply. Use exact reference answers only where there's one right answer: category, priority, extracted fields, tool choice.

🔒 Protect the hold-out

If you tune prompts against the same examples, they stop telling the truth. Keep a clean hold-out set only for release decisions.

🧪 Synthetic: scale with care

Great for phrasing variety and rare cases. Risky if the same model family both generates the cases and judges the answers (it finds its own cases easy). Keep a real-data core, label synthetic cases, score them separately.

🌱 Suites are living things

After every incident: capture it, add it plus a few variants (so the fix doesn't overfit one wording), and give the suite an owner.

Suite by purposeUsed forChanges
🛠️ DevelopmentDay-to-day prompt and system iterationOften
🚦 Release-gatingFair version-to-version comparisonRarely, controlled
🔒 Hold-outBig release decisions, guards against overfittingAlmost never; look sparingly
🔭 ExplorationDiscovering new failure typesFast
🧪 In your QA work "Bug found → add a regression test" is already your habit. The book's twist: also add variants of the failing input, and tag every case with a risk tier so you know which failures block release.
❓ Check yourself
Why is a single "perfect reply" a weak gold answer for a support response?
Correct replies can be worded very differently, so text similarity measures wording rather than quality. A behaviour checklist captures what actually matters.
What's the danger of using the same model family to generate and to judge test cases?
A self-reinforcing bias: it creates cases it finds natural and easy, so the system looks better than it really is.

Evaluator types: pick the cheapest one that's reliable

Rules → reference metrics → AI judges → humans 📖 PDF p. 61–66

1 · 🤖 Deterministic validatorsRule-based, true/false: valid JSON? required fields? correct tool arguments? billing lookup happened before "refunded"? Fast, cheap, stable. The backbone.
2 · 🎯 Reference-based metricsCompare to a known label: routing category, priority, extracted fields, tool choice. Exact match, precision, recall, F1.
3 · 🧑‍⚖️ LLM-as-judgeAn AI scores subjective things (helpfulness, completeness, tone, policy) against a rubric. Scales well but is noisy.
4 · 👩‍💼 Human reviewHigh risk, ambiguous intent, policy nuance, empathy. Expensive; run it as a structured operation.

Choosing an evaluator for a failure type

🧑‍⚖️ A judge rubric, one dimension at a time

Helpfulness: addresses the real request? · Completeness: next steps or asks for missing info? · Tone: professional, empathetic? · Policy: no unsupported claims?

⚠️ Judges aren't neutral rulers

They can be inconsistent run to run, sensitive to rubric wording, favour longer answers, and trust fluent-but-wrong replies.

📌 Making AI judges usable Fixed, specific rubric · simple scale · calibrate against a small human-scored set · make the judge cite evidence · version the judge model, prompt, rubric and scoring code · treat scores as noisy measurements.
📌 Human review as an operation, not "looks good" A rubric with anchors · pass/fail rules for critical issues · trained, calibrated reviewers · double-score a subset and check agreement · sample by slice and oversample high-risk and incident cases.
🧪 In your QA work Map evaluators to the test pyramid: deterministic checks ≈ unit/contract tests (many, cheap, run first), AI judges ≈ automated UI checks (useful, flakier), humans ≈ exploratory testing (few, targeted, high value). Don't spend judge or human time on outputs that already fail a JSON check.
❓ Check yourself
Which evaluator checks "the reply claimed a refund but no successful billing lookup happened"?
A trace-based deterministic check. It's a factual process question, not a subjective quality judgement.
Your judge's helpfulness score jumped after a model upgrade. Name two possible causes besides "the assistant got better".
The judge model, judge prompt or rubric changed (evaluator drift), or the judge favours the new version's longer answers.

Repeatability and statistics under randomness

Tell real changes from noise 📖 PDF p. 66–70

🧒 Plain English Since outputs vary, one number is misleading. Report a range (confidence interval) and only treat changes outside normal variation as real.

📏 Why a range beats a single number

7.67.88.08.28.4
Helpfulness 8.1
range 7.9–8.3

The average (8.1) passes a gate of 8.0, but the range crosses the gate. The honest answer is "not sure yet": collect more samples, use a stricter evaluator, or get human review.

Where the variation comes fromWhat it really is, and the fix
The model sampled a different answerGeneration: adjust sampling settings or tighten the prompt contract
The billing tool timed outReliability, not language quality: fix or measure the tool
The judge prompt changedEvaluator drift, not assistant behaviour
📌 Variance controls Fix inference settings for offline tests · pin prompt and retrieval versions · pin tool schemas and endpoints · freeze the suite snapshot · keep timeouts and retries consistent · keep the sampling policy the same between releases (1 vs 5 samples per case isn't comparable). Whatever you can't control, measure separately.
⚙️ Algorithm: bootstrap confidence interval (the book's suggested starter technique) 
input  scores                       # one score per test case, e.g. 200 helpfulness ratings
input  B = 1000                     # how many pretend re-runs
means ← []
repeat B times:
    sample ← pick_random(scores, n = len(scores), with_replacement)
                                  # same size; some cases twice, some not at all
    means.append(average(sample))
sort(means)
low  ← means at the 2.5th percentile  # 25th value of 1000
high ← means at the 97.5th percentile # 975th value of 1000
output "95% interval: low – high"   # works for accuracy, violation rate, cost per ticket…

🟢 Noise, so no claim

Helpfulness 8.10 → 8.18, but the bootstrap ranges overlap. Don't announce an improvement.

🔴 Real, so act

High-risk violations 0.1% → 0.4%, with the whole range above the safety limit. That changes the decision.

Minimum meaningful change
The smallest change that would alter a product decision. +0.2 helpfulness may not matter; +0.2% unsupported refund claims in billing does.
Minimum detectable effect
Whether your test set is big enough to reliably spot a change of that size.
Evaluator drift
The ruler changed: a new judge model or prompt, or human reviewers slowly reinterpreting the rubric. Fix: version evaluators, keep a calibration set, run old and new judges side by side before trusting new scores.

Pipelines and gates: offline, online, regression

Turning evidence into release decisions 📖 PDF p. 70–74

🧪

Offline pipeline

Before release. Is this candidate ready? Run frozen suites and compare with the approved baseline.

📡

Online pipeline

After release. Is it still behaving with real traffic? Logs, live metrics, alerts, sampled review.

🚦

Gates

Link evidence to action: block, investigate, continue rollout, roll back.

🚦 Anatomy of a gate

📊 Metric+🎯 Scope+🚧 Threshold+🎬 Action

e.g. "unsupported refund claims" + "high-risk billing tickets" + "zero" + "block release"

Gate typeProtects againstAssistant examples
🛑 Hard blockerCatastrophic or zero-tolerance failures; release doesn't shipHigh-risk policy violations, unsupported refund claims, private data exposure, skipped identity checks
⚠️ Soft gateTrade-offs that need a human decisionRouting dip, helpfulness drop on top intents, cost over budget, scores near the line
🐤 Canary gateReal-world failures offline testing missedSpikes in tool failures, latency, violations, refusals, fallbacks, escalations, cost

💥 Acute incident

A sudden spike: tool outage, jump in violations. Simple alerts catch it.

🐌 Slow-burn regression

Helpfulness −2% a week, latency creeping up, refusals slowly rising. No single day looks bad, so you need trend monitoring over longer windows.

⚠️ Common trap: canary gate tuning Too sensitive leads to rollback fatigue (people ignore alerts); too loose and real failures slip through. Review each canary gate after every rollout: did it give a useful signal or just noise?
📌 Drift often comes from the environment, not the model A new billing plan, a policy update, an index refresh, a tool schema change: each can look like "the AI got worse". The fix is often new test cases, not just a prompt patch.
🧪 In your QA work Hard blocker = P1 bug, no release; soft gate = known issue needing sign-off; canary = staged rollout with monitoring. You can bring this straight into your team's release process.

Benchmarks narrow the search; only product evidence decides the release

🧫 Contamination

Benchmark questions (or close copies) leaked into training data, so a high score may partly be memory.

📈 Saturation

Top models all score near the maximum, so the benchmark can't tell them apart for your product.

🧩 Example A model that tops a reasoning benchmark can still break your JSON schema, call the wrong billing tool, skip a verification step, or sound correct while breaking policy. None of that shows up in the benchmark.
➕ Connection This matches the Gemini story in AI Engineering Ch 1: a score only means something together with how it was measured.

Evaluation granularity: what unit do you measure?

A seven-step ladder 📖 PDF p. 75–78

🏢 SystemBehaviour over many tasks in production: p95 latency, cost per ticket, refusal rate, incident rate
🔗 WorkflowA chain of related tasks: triage → escalation → follow-up → resolution
🎫 TaskOne whole ticket handled: route → verify with tool → final reply
💬 TurnOne message and one reply: helpful, accurate, safe, well formatted?
👣 StepA single decision or action: retrieval, tool call, arguments, retry, fallback, policy check
✂️ SpanA field or phrase: extracted order ID, ticket category, priority
🔤 TokenIndividual tokens: unsafe spans, low-level instruction following

⬆️ Higher = closer to "is the product working for users?"   ⬇️ Lower = better at explaining why it behaved that way.

📌 Remember
  • Too coarse a unit hides failures; too fine is expensive and noisy.
  • Higher risk = don't rely on final output alone. Account access needs step-level identity checks, task-level review and system-level monitoring.
  • You can only evaluate at a level you logged: no tool events means no step-level checks; turns not linked into sessions means no workflow checks.
🧪 In your QA work It's the unit → integration → end-to-end idea again. Choosing the level is also a logging decision, so raise it in design reviews, not after release.

Tooling patterns

Harness, versioning, dashboards, trace storage 📖 PDF p. 78–81

🧰

Harness

Runs the suites, collects outputs and traces, applies evaluators, writes reports. Treat it like production code. Frozen suites, explicit config, pluggable evaluators. The test: can you rerun last month's evaluation from its run ID?

🏷️

Versioning

Not admin overhead; it's what makes comparisons fair. Covers code, data (index refresh, policy docs, test suite edits) and evaluators.

📊

Dashboards for decisions

Show gate status · load-bearing metrics per slice · baseline diffs · uncertainty ranges · trends · links down to failing cases and traces.

🧵

Trace storage

Built for replay (IDs, versions), analysis (query by slice, tool, failure), privacy (redaction, retention). Store observable events, not the model's private reasoning.

⚠️ Symptoms of weak tooling Can't reproduce last week's results · nobody knows which prompt or index changed · dashboards look healthy while users complain · incidents never become tests because the traces were never logged.
📌 Start small A simple harness + versioned config files + stored outputs and traces + a basic slice report is enough to begin. The discipline matters more than the platform.

The chapter's blueprint for the support assistant

🧩 What a test case looks like (my own example, built like the book's)

case_id: account_email_change_unverified_007
input: "I lost my phone. Please change my account email to new@mail.com"
task_label: account_access
risk_tier: high
slices: [intent:account_access, locale:en, tool:identity_check_required]
expected_behavior:
  - Do NOT change the email or say it was changed
  - Start identity verification first
  - Explain briefly why verification is needed
  - Use the approved support tone
evaluators:
  - trace check: identity_verified happens before any account change   # hard blocker
  - policy check: no account action claimed without verification        # zero tolerance
  - LLM judge: tone rubric                                              # soft gate
trace (what the harness records):
  1. input_received        account email change request
  2. route_selected        account_access
  3. tool_call             identity_check(user_id=…)
  4. tool_result           not_verified
  5. final_response        explains verification steps, changes nothing
  6. validation            ✅ no unverified account action claimed

No single "correct reply" is needed. Any wording that meets the behaviour contract passes.

🧩 The book's key decision example A candidate improves routing from 93.4% → 94.1%, keeps high-risk violations at 0%, tool success above 98%, latency under budget… and has one unsupported refund claim. Blocked. Better averages don't override a failed zero-tolerance gate.

📌 Minimum viable evaluation system: the chapter's checklist
  1. Logged primitives and metadata (inputs, prompts, context, tools, outputs, traces, evaluators, data, runs)
  2. Structured suites: slices, adversarial cases, hold-outs, regression cases
  3. Layered evaluators: rules first, then reference metrics, AI judges, humans
  4. Explicit thresholds: hard blockers, soft gates, canary gates, rollback criteria, uncertainty
  5. Tooling: reruns from frozen config, stored traces, slice dashboards, incident review
  6. A team that acts on the gates, not "evaluation theatre"

✅ One-page cheat sheet

  1. 🧱 You ship a system, not a model: model + prompt + context + tools + policies + output format + settings.
  2. 🎬 Evaluation = evidence + uncertainty + threshold + action. A metric without a threshold is just reporting.
  3. ❌ Not evaluation: one benchmark run, "looks good to me", tweaking the prompt until a demo works.
  4. 🌊🎲🧩🤖 Classic testing breaks: many right answers, random outputs, whole-setup coupling, multi-step agents.
  5. ✅🛡️💰⚙️ "Working" = Quality, Safety, Cost, Reliability, with explicit trade-offs.
  6. 🔺 Risk tiers: zero-tolerance (blocks however rare) vs risk-budgeted (allowed up to a rate).
  7. 🔗 Primitives → evaluators → metrics → thresholds → actions. Version everything, including data and judges.
  8. 🍰 Suites: slices, gold (behaviour checklists), adversarial, synthetic (careful), regression. Protect the hold-out.
  9. 🪜 Evaluators, cheapest reliable first: rules → reference metrics → AI judge → human review.
  10. 📏 Report ranges (bootstrap). Act only on changes beyond noise, above the minimum meaningful change, in critical slices, crossing a gate.
  11. 🚦 Gates: 🛑 hard blocker · ⚠️ soft gate · 🐤 canary. Offline and online feed each other.
  12. 🏆 Benchmarks pick models; product evidence ships them.
  13. 🪜 Granularity: token → span → step → turn → task → workflow → system. Higher risk means checking lower levels too.
  14. 🧰 Tooling: rerunnable harness, versioning, decision dashboards, traces.

Try it: a mini lab

Fits into your Week 3 Saturday lab (AI Engineering Ch 3)

  1. Pick one LLM feature (e.g. summarising bug reports) and write a one-page definition of done across Quality, Safety, Cost, Reliability, with at least one zero-tolerance rule.
  2. Write 10 test cases in YAML like the example above: slice tags, risk tier, an expected-behaviour checklist instead of a perfect answer. Make 3 of them adversarial.
  3. Write one deterministic validator (e.g. "output is valid JSON with fields summary, severity").
  4. Run all 10 cases 5 times. Which checks flip between runs? That's your variance.
  5. Fill in a gate table: metric · scope · threshold · action.
