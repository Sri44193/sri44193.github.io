NER evaluation: more than "did it find the entity?"

Span, token, entity and label metrics 📖 PDF p. 414–419

🧒 Plain English Named-entity recognition (NER) finds pieces of text and labels them: product, order ID, price, date… A model can spot that a price exists yet grab the wrong span, give it the wrong label, or break on messy input. So report several metrics, each tied to a threshold, an action and a gate.
Exact-span match
Predicted start and end exactly equal the annotated ones.
Partial-span overlap
Credit for overlapping but imperfect spans.
Token-level P/R/F1
Are individual tokens tagged correctly?
Entity-level P/R/F1
Are whole entities found and labelled correctly?
Boundary correctness
Start and end positions right.
Label consistency
Same kind of thing, same label, every time (label P/R/F1, confusion matrix).
End-to-end document pass rate
Share of documents where all mandatory fields are right and pass validation without manual correction.
⚠️ Boundary errors differ in severity Dropping "₹" when the currency is obvious = minor (normalise it). Truncating a product name, cutting an invoice number short or misreading a price = severe (wrong billing, inventory mismatches, disputes). Make thresholds and gates severity-aware: strict confidence, human review or rejection for high-risk fields.

3

Span accuracy and label consistency

Token F1 can look good while the field is wrong 📖 PDF p. 421–424

🧩 Why token F1 misleads (the book's example) Gold product: "Apple iPhone 15 Pro Max"; predicted: "iPhone 15 Pro". Most tokens are right, so token F1 looks decent, but the field is wrong. Downstream systems need complete fields, so entity-level exact-span F1 and field-level correctness matter more.
🧒 BIO tagging Each token is B (beginning of an entity), I (inside) or O (outside). "B-PRODUCT I-PRODUCT O B-PRICE" = a two-token product, a non-entity, then the start of a price. Tags are converted into spans and compared with the ground truth.
🧒 Label consistency "Order ID", "Order Number" and "Purchase Ref." should all map to the same label if they're the same business field. 
example production gates (from the book):
  exact-span F1, mandatory fields        > 0.90
  field-level accuracy, price + order ID > 0.95
  schema-valid output                    > 0.98
  price, tax or invoice ID below confidence threshold → automatic human review

A worked example: scoring one invoice

Each error type points to a different fix 📖 PDF p. 424–425

FieldGoldPredictedResult
PRODUCTApple iPhone 15 Pro MaxiPhone 15 Pro❌ Incomplete span
ORDER_IDORD-78421ORD-78421 as ORDER_NUMBER❌ Right span, wrong label
PRICE₹79,90079,900❌ Missing currency symbol
DELIVERY_DATE12 Feb 202612 Feb 2026✅ Exact match
SELLER(none)Apple Store❌ False positive
⚙️ Entity-level metrics for this example 
true positives  (TP) = 1   # delivery date
false positives (FP) = 4   # 4 predictions that don't exactly match a gold entity
false negatives (FN) = 3   # product, order ID, price not correctly found
precision = TP ÷ (TP + FP) = 1 ÷ 5 = 0.20
recall    = TP ÷ (TP + FN) = 1 ÷ 4 = 0.25
F1        = 2 × P × R ÷ (P + R) = 0.10 ÷ 0.45 ≈ 0.22
📌 Why this beats "accuracy" Each error links to an action: normalise (currency), validate (formats), improve the prompt (full product names), redesign the schema (ORDER_ID vs ORDER_NUMBER), fine-tune, or route to human review. Every run should log gold, predicted, exact-match status, boundary error type, label confusion, schema validity, confidence and the gate decision.
5

Fine-tuning, and the template-leakage trap

Only fine-tune when gates fail 📖 PDF p. 425–426

🧒 Plain English Fine-tune only when prebuilt models fail defined gates (exact-span F1, field accuracy, schema validity, robustness, manual-review rate). It helps with domain terms, long product names, vendor-specific invoice formats and abbreviations.
⚠️ Leakage through templates If invoices from the same vendor or layout (or near-duplicates) are in both training and test sets, the model looks ready but has only memorised formats. Split hold-outs by vendor, template, time period or source, remove near-duplicates across splits, and keep a blind test set used only after all prompt, model and fine-tuning decisions are made.
➕ Where this connects The same leakage levels (exact, near-duplicate, paraphrase) from Chapter 2 of this book apply here at the template level.

Label confusion, and when it's the schema's fault

Similar fields get mixed up 📖 PDF p. 428–429

Gold labelPredicted asExampleImpact
UNIT_PRICETOTAL_PRICE"₹999 per item" vs "₹4,995"Wrong pricing and margins
TOTAL_PRICEDISCOUNT_AMOUNT"Discount ₹500" taken as totalBilling and reconciliation errors
SELLER_NAMESHIPPING_PROVIDER"BlueDart" as sellerWrong seller attribution
ORDER_IDINVOICE_ID"INV-44920" as order IDFailed order matching
PRODUCT_NAMEPRODUCT_CATEGORY"Footwear" instead of "Nike Air Max 270"Inventory and catalogue errors
⚠️ Audit the schema before blaming the model If the schema has TOTAL_PRICE, ORDER_VALUE and PAYABLE_AMOUNT with no clear definitions, or SELLER/VENDOR/MERCHANT used inconsistently, confusion reflects the labels, not the model. Each label needs a clear definition, mutually exclusive boundaries, positive and negative examples, and rules for ambiguous cases.
📌 Pick the fix from the diagnosis Formatting inconsistent → prompt. Labels overlap → schema redesign. Structured fields (prices, SKUs, dates, IDs) → post-processing and validation. Persistent domain-specific errors → fine-tune. Each fix has a measurable rerun target.
8

Robustness to noisy and adversarial text

Measure the drop, per field 📖 PDF p. 430–432

📄 Document noise

Scanning or conversion corruption → partial product names.

🔢 Numeric corruption

Missing decimals, misplaced commas, wrong currency, misread digits → wrong prices or tax.

🗂️ Layout variation

Unusual field order, nested tables, columns → total vs line price confusion.

❓ Semantic ambiguity

Similar field names → seller vs shipping provider.

💉 Adversarial manipulation

Embedded instructions, manipulated totals, misleading wording.

🔤 Homoglyphs

Look-alike characters: "O" vs "0" in order IDs.

⚙️ Clean-to-noisy F1 drop 
drop = entity F1 on clean text − entity F1 on noisy text
example: 0.91 − 0.76 = 0.15
per-field thresholds (from the book):
  low-risk descriptive fields       drop ≤ 0.10
  price, tax, order ID, invoice no.  drop < 0.03, plus review on validation failure
🧒 Noise adaptation If thresholds fail, fine-tune on augmented data: formatting variation, character corruption, missing delimiters, reordered fields, synthetic OCR errors, adversarial examples. Report clean and noisy scores, per-field drop, OCR-induced error rate, change in label confusion, and the share of noisy documents that still pass the gate.

OCR and document understanding: modular or unified

Evaluate by task, not by model ranking 📖 PDF p. 433–437

🧱 Modular pipeline

OCR → layout parsing → key information extraction → validation, each evaluated separately. Better control, debugging and error isolation.

🧠 Unified multimodal model

Recognition, layout, extraction and reasoning together. Good for complex visual documents, but must also be tested for grounding, field correctness and reasoning reliability.

TaskTypical metricsBest for
Text recognitionCER, WER, transcription accuracyPrinted invoices, receipts, scans
Scene textDetection and recognition accuracy, VQA accuracyPackaging, labels, signage
Document VQAExact match, answer F1, grounding accuracyForms, invoices, PDFs
Key information extractionEntity P/R/F1, field accuracy, schema validityEnterprise document extraction
Layout understandingLayout detection, table structure, cell accuracy, reading orderComplex PDFs, tables, columns
Multimodal reasoningAnswer accuracy, reasoning consistency, citation/groundingComplex questions over documents
HandwritingCER, WER, field accuracyForms, notes, prescriptions

End-to-endField accuracy, workflow completion, manual review, downstream errorsHigh-volume automation

Record the exact model name, version, date and configuration in formal evaluations; capabilities change by version.

11

Transcription accuracy and layout grounding

Reading the text isn't enough; it must land in the right field 📖 PDF p. 438–440

🔤 Transcription

CER (character error rate) · WER (word error rate) · exact match · normalised field-level accuracy.

📐 Layout grounding

Bounding-box IoU · field-to-region accuracy · reading-order accuracy · table-structure and cell accuracy.

⚙️ ➕ CER in one example 
CER = (substitutions + deletions + insertions) ÷ characters in the reference
reference "ORD-78421"  (9 characters)
OCR       "ORD-7B421"  (8 read as B → 1 substitution)
CER = 1 ÷ 9 ≈ 11%   # tiny for prose, fatal for an order ID
⚠️ Layout decides meaning The same number can be a unit price, tax, discount or total. Common failures: values misaligned to the wrong field, misread tables, unit and total price mixed up. Fine-tuning should show lower CER/WER, better field-to-region accuracy, fewer table errors and a higher document pass rate on unseen vendors and layouts.
12

Image quality, latency and automation success

Graceful degradation, production speed, fewer manual fixes 📖 PDF p. 440–443

✅ Semantic-preserving

Mild skew, compression, shadow: answers should stay the same.

📉 Information-destroying

Severe blur, low resolution, cropping: expect graceful degradation, not invariance.

Test controlled levels (clean, mild blur, severe blur, low resolution, skew, compression, shadow, crop) and report the drop for transcription, layout grounding and extraction separately.

⏱️ Production gates

p95 time per page · documents per hour · cost per document · GPU/CPU use · queue wait · human-review backlog. Account for page count, resolution, OCR and layout time, context length, batch size, hardware.

🏁 Automation success

Document accuracy = all required fields correct, validated and accepted downstream. Automation success = documents completed with no manual correction.

📌 Release rule Move from experiment to production only when automation success, manual-review rate, downstream error rate, latency and cost all meet predefined thresholds.

❓ Check yourself
Gold has 4 entities. The model predicts 3, of which 2 match exactly. Precision, recall, F1?
Precision 2/3 ≈ 0.67, recall 2/4 = 0.50, F1 = 2×0.67×0.50 ÷ 1.17 ≈ 0.57.
The model keeps labelling TOTAL_PRICE as ORDER_VALUE. Fine-tune first?
No: audit the schema first. If labels overlap or are poorly defined, redesign the schema and guidelines; fine-tuning won't fix ambiguous labels.
Your test set shows F1 0.96, but all test invoices come from vendors also in training. Ready to ship?
Not proven: possible template leakage. Re-test on a hold-out split by vendor/template/time and a blind test set.

✅ One-page cheat sheet

  1. 🏷️ NER metrics: exact-span, partial overlap, token and entity P/R/F1, boundaries, label consistency, document pass rate.
  2. ⚖️ Severity-aware gates: minor boundary slips normalised; price, ID, tax errors → strict thresholds or review.
  3. 🧰 NER types: retrieval-augmented, label-conditioned (GLiNER), prompted LLMs, multilingual, domain, high-throughput, on-prem, hybrid.
  4. 🔍 Token F1 can hide incomplete fields; use entity-level exact-span F1 and field accuracy.
  5. 🧮 Worked example: P = 0.20, R = 0.25, F1 ≈ 0.22; each error maps to a fix.
  6. 🧪 Fine-tune only after failing gates; split by vendor/template/time; blind test set.
  7. ✂️ Boundary types: left/right truncation, over-extended, split, merged, wrong span with right label.
  8. 🔀 Label confusion: unit vs total price, seller vs shipper, order vs invoice ID; audit the schema first.
  9. 🌪️ Clean-to-noisy F1 drop per field (≤ 0.10 low-risk, < 0.03 critical); homoglyphs and injected text too.
  10. 🌊 OCR errors propagate into NER and then into billing, inventory and analytics.
  11. 📷 OCR: CER/WER, bounding-box IoU, field-to-region, reading order, table cells.
  12. 🖼️ Preserve answers under harmless changes; degrade gracefully when information is destroyed.
  13. 🏁 Ship only when automation success, review rate, downstream errors, latency and cost all pass.
  14. 📉 Real TrOCR + GLiNER on FUNSD scored F1 = 0: use region OCR and layout-aware models.

Try it: a mini lab

Score an extraction model on your own receipts

  1. Take 10 receipts or order emails. Write the gold JSON for product, order ID, price, date, seller.
  2. Ask an LLM to extract the same fields. Score entity-level P/R/F1 and classify every error by boundary type or label confusion.
  3. Corrupt the text (swap O/0, drop decimals, reorder lines) and compute the clean-to-noisy F1 drop per field.
  4. Photograph two receipts and run OCR; compute CER on the order ID and total.
  5. Write gates: which fields need exact match, which can be normalised, which go to review.
