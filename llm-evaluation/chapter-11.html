Text2SQL is a system, not a model

Valid SQL can still be the wrong answer 📖 PDF p. 498–502

🧒 Plain English Text2SQL turns a question ("total revenue last quarter?") into an SQL query. It predates LLMs (semantic parsing, grammars, schema linking). Today it's usually a general or code LLM adapted with fine-tuning, schema retrieval, constrained decoding and execution checks, not a brand-new kind of model. Tools named: Defog, Numbers Station, MotherDuck; open frameworks SQLCoder, DIN-SQL, RAT-SQL, PICARD, RESDSQL.

2

Four implementation patterns

Where reliability is expected to come from 📖 PDF p. 502–503

🎯 Fine-tuned ("native")

Trained on question–SQL pairs; the model carries more of the schema reasoning.

🧰 RAG / orchestration ("non-native")

A general LLM plus schema retrieval, prompt building, validators and repair.

📏 Constrained decoding

Output restricted by SQL grammar, schema rules or a parser (e.g. PICARD).

▶️ Execution-verified

Query run in a sandbox before acceptance.

📌 Remember In orchestrated systems, test retrieval, grounding, validation and repair hardest. In fine-tuned systems, test the model's learned schema reasoning, execution correctness, semantic stability and generalisation. Both still need runtime validation.

🧩 Execution-grounded evaluation (the book's example) A query uses order_date instead of invoice_date for revenue reporting. Syntax: fine. Result: wrong. Catch it by comparing results, row counts and aggregations against a trusted reference query.

Text2SQL at inference time

The most common failure: valid but semantically wrong 📖 PDF p. 508–512

🧩 The book's example "Show total revenue from active customers last quarter" → the SQL sums all invoices with no active-customer filter. It runs, returns a number, and is wrong.
AreaSignals
Schema retrievalRetrieval accuracy, context completeness and latency, grounding precision
GenerationSyntax, semantic correctness, hallucination, prompt-injection resistance, schema contamination, ambiguity handling
ExecutionSuccess rate, null-result frequency, row-count sanity, semantic equivalence with business intent
RepairRepair success, fallback effectiveness, retry stability
SafetyPermissions, unrestricted scans, dangerous joins, query cost, sensitive data exposure
OperationsLatency, throughput, token cost, concurrency
🧪 Testing angle ➕ Keep a golden question set with trusted reference SQL and expected result snapshots on a fixed test database. Compare results, not SQL text: two different queries can both be right. Add paraphrases, ambiguous questions, questions about restricted tables, and one that would scan a huge table.

Text2Cypher: queries over graphs

Nodes, edges, paths and direction 📖 PDF p. 512–520

🧒 Plain English Cypher is the query language of graph databases like Neo4j. Beyond tables it must handle nodes, edges, paths, relationship direction and multi-hop traversals, so it's more exposed to path explosion, relationship ambiguity and runaway traversal cost.
🧩 ➕ Why direction matters "Who does Asha manage?" vs "Who manages Asha?" use the same MANAGES relationship in opposite directions. Both queries are valid Cypher; one answers the wrong question.
Neo4j fine-tuned experimentApprox. size
Gemma 2 Text2Cypher9B
Llama 3.1 Text2Cypher8B
Phi-3 Medium / Small / Mini14B / 7B / 3.8B

Also GPT-4o and Gemini 1.5 Flash fine-tuned variants. These are fine-tuned general models, not graph-native foundation models: decoder-only transformers stay dominant because they're easier to tune and deploy. Recipe: base model → fine-tune → schema grounding → graph schema retrieval → Cypher validation and repair → execution checks.

🏋️ Training-time

Node-label grounding · relationship mapping · edge-direction correctness · syntax validity · multi-hop traversal accuracy · semantic equivalence · hallucinated nodes, relationships, properties · execution success · unseen schemas · restricted traversals.

🚀 Inference-time

Schema retrieval · relationship interpretation stability · path validity · runtime exceptions, null results · hallucinated edges · schema drift · unauthorised traversals, unrestricted scans · traversal cost control (depth, recursion, query plan, timeouts) · latency and tail · retries and fallback.

Guardrail SLMs

Small, fast models that police bigger ones 📖 PDF p. 520–523

🧒 Plain English A guardrail SLM isn't a chatbot. It sits around the main LLM and checks prompts, outputs, tool calls, retrieved content and actions against policies, fast enough to run on every request. Example: Google's ShieldGemma (ShieldGemma 1 on Gemma 2 at 2B/9B/27B; ShieldGemma 2 at 4B on Gemma 3).

🛡️ Jobs

Harmful content · toxicity · jailbreak and prompt-injection detection · unsafe instructions · PII · policy validation · output moderation · tool-use governance · escalation.

Evaluating ShieldGemma for hate-speech policy

Both mistakes are costly 📖 PDF p. 523–527

🧒 The setup A policy forbids hate speech targeting race, gender, ethnicity, religion, nationality, sexual orientation, disability or caste. Before a prompt reaches the main LLM, the guard must answer "Yes" (violates) or "No", then give step-by-step reasoning. It must tell endorsement apart from discussion, education, reporting, condemnation, satire and quotation, and resist adversarial phrasing.

🚫 False positive

Blocks a legitimate discussion (e.g. a history lesson about discrimination). Hurts users and free discussion.

✅ False negative

Lets real hate speech through. Legal, compliance, reputational and safety risk.

📌 Calibration decides the action High-confidence violation → block. Low-confidence or borderline → human review, not automatic blocking. So measure confidence calibration, threshold sensitivity, escalation precision and recall, and agreement between confidence bands and human reviewers.
🧒 What to measure Training: classification accuracy across paraphrases, dialects and indirect hate · refusal correctness · FP and FN rates · adversarial robustness · contextual understanding · policy-grounded reasoning quality (rationales that cite the policy correctly, no invented reasons). Inference: latency, throughput, stability, jailbreak resistance, sarcasm and coded language, policy drift, escalation accuracy, human-review agreement, safety drift over time.
🧪 Testing angle ➕ Build contrast pairs: an attack and a near-identical legitimate sentence (quoting a slur to condemn it, news reporting, a classroom question). A good guard blocks one and allows the other. Report precision and recall per protected category, not just overall.

Guardrails for images

Govern visual content before it's shown or stored 📖 PDF p. 527–530

🧒 Plain English Image moderation must reason about objects, actions, symbols, embedded text, scene composition and synthetic manipulation, not just words. Categories: violence and gore, explicit sexual imagery, dangerous activities, graphic harm, unsafe visual instructions, harmful synthetic imagery. Same Yes/No + reasoning format, grounded strictly in the policy text, with room to explain ambiguity.

📏 KPIs

Harm-category accuracy · unsafe-image precision and recall · FP and FN rates · synthetic-manipulation sensitivity · reasoning consistency · escalation · latency · containment.

💉 Adversarial images

Hidden text injection · blurred harmful content · perturbations · stylised unsafe content · manipulated context · synthetic transformations designed to evade the classifier.

➕ Where this connects Chapters 4–5 of this book (embedded instructions and injection in images) and AI Engineering Ch 10 (guardrails in the architecture).

Embeddings, explained simply

Meaning as coordinates 📖 PDF p. 530–536

🧒 Plain English Text is split into tokens; each token gets an ID (e.g. "Today" → 2035), which is just a lookup key with no meaning. The embedding is the vector that ID maps to (e.g. [0.12, −0.44, 0.91, …], hundreds or thousands of numbers). Similar meanings land near each other ("dog" near "puppy", "banana" far from "planet"). In transformers, attention then makes them contextual: the same word's vector changes with its sentence (unlike older static Word2Vec or GloVe).

From words to vectors

📝 Text embeddings

Documents, tickets, policies, chat history → semantic search, RAG, clustering, deduplication. Example: EmbeddingGemma (~300M parameters).

🖼️ Image embeddings

Image search, product matching, visual recommendations, anomaly detection.

🔗 Multimodal embeddings

Text and images in one shared space: search a product photo with words, or words with a photo.

📌 Remember Embeddings aren't judged by generated text: they're judged by retrieval behaviour, ranking consistency, vector-space stability and downstream reliability.

Evaluating text embeddings

Recall@K, MRR, hard negatives, drift 📖 PDF p. 536–539

⚙️ ➕ Recall@K and MRR on three queries 
rank of the first relevant document for each query:
  query A → rank 1     query B → rank 3     query C → not in top 5
Recall@3 (hit rate) = queries with a relevant doc in the top 3 ÷ all = 2 ÷ 3 ≈ 0.67
MRR = average of 1/rank = (1/1 + 1/3 + 0) ÷ 3 ≈ 0.44

Evaluating image and multimodal embeddings

Robust visuals; balanced modalities 📖 PDF p. 539–544

🖼️ Image: training

Top-K image retrieval · mAP · contrastive loss stability · cluster purity · augmentation robustness (crop, blur, resize) · embedding variance. Tight within-class, well separated between classes. Must survive lighting, rotation, compression, occlusion, noise.

🖼️ Image: inference

Recall@K · latency per image · drift detection · cross-resolution stability · false match rate · indexing throughput · adversarial robustness.

🔗 Multimodal: training

Cross-modal recall@K · alignment similarity · contrastive alignment loss · caption–image matching · cross-modal cluster consistency · embedding collapse detection.

🔗 Multimodal: inference

Image→text and text→image accuracy · cross-modal drift · latency · robustness to visual changes · ranking stability across modalities.

⚠️ Modality imbalance Text supervision is usually denser and cleaner, so text can dominate: results match the description while ignoring what the image shows. Measure modality dominance, collapse and cross-modal balance; check both inputs really affect the ranking. Over time, new product types, visual styles or generated images cause multimodal drift.
❓ Check yourself
A Text2SQL query runs without errors and returns a plausible number. Why isn't that enough?
It may be semantically wrong (missing a filter, wrong date column, wrong join). Compare results against a trusted reference query and check row counts and aggregations.
Your guard blocks 99% of hate speech but also 15% of legitimate history lessons. What do you change?
That's a high false-positive rate. Add contrast-pair tests, recalibrate thresholds, and route low-confidence or borderline cases to human review instead of auto-blocking.
Five queries have first-relevant ranks 1, 2, 1, 4, 10. What's MRR?
(1 + 0.5 + 1 + 0.25 + 0.1) ÷ 5 = 2.85 ÷ 5 = 0.57.

📌 The book's closing message Reliable AI doesn't come from bigger models alone, but from continuous evaluation, monitoring, validation and disciplined system design. As systems gain tools, memory, retrieval and self-correction, evaluation becomes an ongoing governance process, not a one-off test phase. That is exactly the job of an AI-focused QA lead.

✅ One-page cheat sheet

  1. 🗂️ Text2SQL is a pipeline: retrieval → enrichment → planning → generation → repair → execution → access control.
  2. 🧭 Fine-tuned vs orchestrated vs constrained vs execution-verified: test where the reliability is meant to come from.
  3. ⚖️ Retrieval recall and precision: too little hallucinates schema, too much confuses and costs.
  4. ▶️ Execution-grounded checks against reference queries; valid-but-wrong is the top failure.
  5. 🛡️ SQL governance: permissions, restricted tables, unrestricted scans, query cost, injection, schema drift.
  6. 🕸️ Text2Cypher adds nodes, edges, direction, multi-hop paths and traversal cost control.
  7. 🚧 Guardrail SLMs (ShieldGemma) police inputs, outputs and tools; measure FP and FN, refusal correctness, robustness, escalation.
  8. 🎚️ Calibration: high-confidence → block; borderline → human review.
  9. 🖼️ Image guards: visual evidence, embedded text, synthetic images; rationale must match what's visible.
  10. 📍 Embeddings = meaning as vectors; judged by retrieval, not text.
  11. 📏 Recall@K, Precision@K, MRR, hard negatives, embedding drift.
  12. 🔗 Image: mAP, cluster purity, robustness, false matches. Multimodal: cross-modal recall, modality imbalance, collapse, drift.

Try it: a mini lab

Three small specialised-system tests

  1. Text2SQL: make a tiny SQLite database (customers, invoices). Write 10 questions with reference SQL. Ask an LLM for SQL and compare results, not text. Include one "active customers only" question.
  2. Guardrail: write 10 contrast pairs (harmful vs legitimate discussion of the same topic). Run them through any moderation model; compute FP and FN.
  3. Embeddings: embed 20 FAQ answers and 10 user questions with any free embedding model. Compute recall@3 and MRR. Add a hard negative ("reset password" vs "close account") and see if ranking holds.
