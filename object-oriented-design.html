Module 1 · Object-oriented analysis and design

Design comes before code

Design looks at the lower-level parts of a system: components and their responsibilities. Architecture looks at the whole system: frameworks, data storage, and how components interact. The course compares them to a building's interior designer and its architect.

From requirements to technical design Requirements, conceptual and technical designs

  • Eliciting requirements means probing the client's vision, not just writing it down. For example, the house brief has a gym and three bedrooms but no kitchen: do they need one? How big should each room be? Are there building restrictions? Also ask about trade-offs the client hasn't considered.
  • Conceptual design: identify the major components, the connections between them and each one's responsibility, and leave out technical details (wiring, plumbing). The worked example is a course search page. Its first mockup lacks an input field, a search button and a results page, and drawing it reveals those gaps.
  • Technical design: describe how each responsibility is met. Keep splitting components until each is small enough to design in detail (e.g. the gym floor needs reinforcing for an Olympic lifter). Conflicts, such as basement columns versus open headroom, need a compromise agreed with the client.

Competing qualities Competing qualities and trade-offs

FunctionalWhat the system does. The key quality is correctness, e.g. the media app downloads a full movie.
Non-functional (runtime)How well it does it: performance, resource use, efficiency, e.g. download speed and a memory limit.
Non-functional (code)How well the code can evolve: reusability, flexibility, maintainability.
  • Typical trade-offs:
    • Performance vs maintainability: fast code is often less clear and less modular.
    • Security vs performance: security adds overhead.
    • Backward compatibility vs both: the extra code hurts performance and maintainability.
    Adding locks to a front door shows it: each lock adds security and costs convenience.
  • Context decides the balance. A house in a high-crime area needs more security. But window bars stop a fire escape, which a fire marshal's review would have caught. Use design reviews, prototypes and tests to catch unintended consequences.
  • Industry interviewees summed it up as quality versus time to market. The architect decides what is "good enough", which requirements can't be negotiated, and which can.

Module 2 · Object-oriented modeling

Thinking in objects

Represent the key concepts of a problem as objects with their own data and behaviour. In OO modeling even inanimate objects "know" their information: a chair knows its dimensions and a door knows how far it's open.

  • Object-oriented analysis (conceptual) finds the key objects. Nouns in the problem description are good candidates. Object-oriented design (technical) refines their attributes and behaviours.
  • The model starts with entity objects from the problem space. As the solution takes shape, you add control objects, which receive events and coordinate actions, and boundary objects, which connect to outside services.

How languages evolved toward objects Languages evolution · Ted's journey

The four design principles Abstraction · Encapsulation · Decomposition · Generalization

AbstractionSimplify a concept to its essential attributes and behaviours for a context. A student in an academic app has courses, grades and an ID, but not their favourite video game. Follow the rule of least astonishment. Maps to a class.
EncapsulationBundle data with the methods that use it, expose an interface, and restrict the rest. You get black-box thinking and an abstraction barrier. Example: a student can answer "in good standing?" without revealing their GPA.
DecompositionSplit a whole into parts with separate responsibilities, or combine parts into a whole. Ask whether the number of parts is fixed or dynamic, whether lifetimes are linked, and whether parts are shared.
GeneralizationFactor shared characteristics into a superclass (inheritance), or repeated code into a method. Follows D.R.Y. (Don't Repeat Yourself): Cat and Dog → Animal.

Decomposition examples: a refrigerator has one freezer (fixed number, same lifetime) but a changing number of shelves and food items. Food lives independently of the fridge. A person can be a daughter in one family and a spouse in another (a shared part), but a food item can't be in the fridge and the oven at once.

Module 2 · Expressing design in Java and UML

UML class diagrams

CRC cards are the sketch; a class diagram is the blueprint. It's close enough to code to convert either way. Keep CRC cards for prototyping, because class diagrams' parameter lists and return types are too detailed for early design.

Abstraction and encapsulation Class box · access modifiers

public class Student {
    private float gpa;
    private String degreeProgram;

    public float getGPA() { return gpa; }
    public void setGPA(float gpa) { this.gpa = gpa; }
    public String getDegreeProgram() { return degreeProgram; }
    public void setDegreeProgram(String program) {
        if (gpa > 2.7f) { this.degreeProgram = program; }   // a rule hidden behind the interface
    }
}

Decomposition: three relationships Association · aggregation · composition

public class Airliner {                         // aggregation: parts come from outside
    private ArrayList<CrewMember> crew = new ArrayList<>();
    public void add(CrewMember m) { crew.add(m); }
}
public class Human {                            // composition: part created and owned by the whole
    private Brain brain;
    public Human() { brain = new Brain(); }
}

Generalization: inheritance and interfaces extends · implements · polymorphism

  • Java allows single implementation inheritance only. Multiple inheritance (allowed in C++) creates data ambiguity when two parents define the same member. A class can implement any number of interfaces instead, and overlapping signatures need just one implementation.
  • An interface is a contract: method signatures only, with no attributes, constructors or bodies. By convention its name starts with I. Both inheritance and interfaces create subtypes (a Dog is an Animal) and enable polymorphism: the same behaviour description with different implementations.
  • Interfaces can extend interfaces, but only when the child can fully stand in for the parent. IVehicleMovement3D extends IVehicleMovement adds z-axis movement for planes and submarines without forcing it on cars and boats.
Module 3 · Design principles

Evaluating and improving a design

Coupling and cohesion Lego, not puzzle pieces

People can hold only about 7 things in short-term memory (George Miller's paper). A module here means any program unit, whether a class or a method.

Coupling: aim low (loose)Complexity between modules. Judge it by degree (how many connections), ease (are the connections obvious without reading the other module's code?) and flexibility (can the other modules be swapped?).
Cohesion: aim highComplexity within a module: how clear its responsibilities are. If a module has more than one purpose, split it.

Separation of concerns Supermarket departments · dog owner · smartphone

Information hiding Hide what may change, reveal assumptions

Give other modules the minimum they need. Implementation details, which may change, stay hidden. Assumptions, which shouldn't change, are published in the interface. String.concat() is the example: you rely on its signature, not its internals. In Java, encapsulation plus access modifiers is how you do it:

Conceptual integrity "As if one mind wrote it"

  • Ways to get there:
    • Communication: stand-ups and retrospectives where the team agrees on libraries and naming conventions.
    • Code reviews.
    • Shared interfaces and design patterns.
    • A well-defined architecture.
    • Unifying concepts: in Unix, everything is a file.
    • A small core group that accepts commits.
  • Fred Brooks, The Mythical Man-Month: it's better to omit features and reflect one set of design ideas than to have many good but uncoordinated ones.

When inheritance goes wrong Inheritance issues · Liskov substitution

  • Inheritance that adds nothing: PepperoniPizza extends Pizza only calls the parent's constructor and adds a topping. A single Pizza class with toppings is enough.
  • Liskov Substitution Principle: a subclass may replace its superclass only if it doesn't change the superclass's behaviour. Whale extends Animal overrides walk() and run() with swimming, which breaks it.
  • A real-world mistake: Java's Stack extends Vector. It inherits index access and insertion at any position, which a LIFO stack shouldn't allow.
  • When "is-a" doesn't fit, use decomposition. A smartphone has a camera; it shouldn't inherit from Phone and bolt camera methods on.

Model checking Exhaustively check a state model

  1. Modeling phase: describe the model and the properties it must satisfy, e.g. "no deadlock" or "a ticket is never held by two customers". Run quick sanity checks first.
  2. Running phase: the model checker explores every reachable state.
  3. Analysis phase: each violation comes with a counterexample, the exact steps that led to it. Fix the problem, add it as a test case, and repeat.

The limit is state-space explosion: n bits give 2n states, and the interviewee put practical tools at around 240. So you model only the parts that matter, relying on the small world assumption that bugs show up in small cases. Model checking complements testing; it doesn't replace it, and it suits concurrency and protocol bugs that are hard to reason about by hand.
