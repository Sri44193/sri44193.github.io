Section 7 · Cloning, exploring and modifying public repositories

Working with a real repository

The course clones a popular public project (a "Hello World in every language" repository) and looks inside it with the tools from course 1.

Clone, don't download Cloning a remote repository

  • Download ZIP gives you only the files: no .git folder, no history, no branches.
  • git clone <url> copies the whole repository and creates a folder named after it. The URL looks like https://github.com/<user>/<repo>.git.
  • You can clone and commit to any public repository locally, but you can't push to one you don't own. That needs write access or a pull request (Section 11).

What a real history looks like Exploring the cloned repository

  • git log shows many merge commits ("Merge pull request #505 from …") with a Merge: line listing two hashes.
  • git cat-file -p on such a commit shows two parent lines, a different author and committer (committer: GitHub), and a PGP signature.
  • Trees and blobs work exactly as in course 1. Executable files show mode 100755.

Pack files Unpacking Git objects

  • In a cloned repository, .git/objects holds only info/ and pack/. To save space Git has compressed every object into one .pack file, plus an .idx index.
  • To see the loose objects: move the pack file out of pack/, then cat pack-….pack | git unpack-objects.
  • This large project then fills all 256 possible object folders.

Tools GitHub Desktop · VS Code

  • GitHub Desktop: Add existing repository, Fetch origin button, History tab with per-commit diffs.
  • VS Code has Git built in:
    • Green and blue bars in the margin mark added and changed lines.
    • Letters mark file status: M modified, U untracked, D deleted, C conflict.
    • The Source Control panel lets you view diffs, stage, commit and discard changes.
    • The current branch shows in the bottom-left corner; click it to switch.
    • Alt/Option+Z toggles word wrap.

Reading git diff Committing in the clone · git diff

diff --git a/list_langs.py b/list_langs.py     # a = old version, b = new version
index 3f1a2c4..9be07d1 100755                    # old blob .. new blob, file mode
--- a/list_langs.py
+++ b/list_langs.py
@@ -3,6 +3,8 @@                                  # old: from line 3, 6 lines · new: from line 3, 8 lines
 unchanged line
+added line                                      # + only in b
-removed line                                    # - only in a
  • git diff compares the working directory with the staging area. It shows only changed sections (hunks), not whole files.
  • The new hash on the index line is calculated but not yet stored: git cat-file on it fails until you commit.
  • git commit -a -m "msg" stages every modified tracked file and commits in one step. New untracked files still need git add.
  • After committing in the clone, git log shows origin/master and origin/HEAD on the last commit from GitHub. Your new commits exist only locally.
Section 8 · Merging branches

Merging: fast-forward, 3-way, conflicts

Merging brings one branch's work into another, usually a feature branch into master or release.

The merging process Why merging · merging process

  1. Create a feature branch from the main branch.
  2. Commit and test your changes there.
  3. Check out the branch you're merging into, the receiving branch (e.g. git checkout master).
  4. git merge <feature-branch>. Git chooses fast-forward or 3-way by itself.
  5. Delete the merged branch: git branch -d <feature-branch>.

Fast-forward merge Concept · in action

3-way merge Concept · in action · observing the repository

  • In the course: BR-2 adds file5–7, master adds file8, then git merge BR-2 opens Vim for the merge commit message ("Merge branch 'BR-2'"). Output says "Merge made by the 'recursive' strategy" (ort on newer Git).
  • Why use a 3-way merge? It preserves the full history: who committed what on the feature branch, and when.
  • git branch -d BR-2 works without a warning because the branch is merged.
  • Sometimes one commit line shows as 3 insertions, 1 deletion when you added only two lines. The last line gained a newline at the end, so Git counts it as changed.

SourceTree Installing · in action

A free Atlassian GUI (Mac and Windows; it asks for a Bitbucket account). It draws the branch graph, which GitHub Desktop lacks, so you can see where branches split and merged. It also stages, commits, creates and merges branches, and checks out any commit on double-click (detached HEAD).

Merge conflicts What is a conflict · creating · observing · resolving

  • A conflict happens only in a 3-way merge, when both branches changed the same lines of the same file. Git stops right before creating the merge commit.
  • git status shows "You have unmerged paths" and "both modified: file7.txt". git merge --abort cancels the merge.
Just another file in the root of the working directory
<<<<<<< HEAD
Line replaced in master branch                     # current change (receiving branch)
=======
…and it was modified in the BR-3 branch as well    # incoming change (branch being merged)
>>>>>>> BR-3
  1. Edit each conflicted file: keep one side, both, or write something new, and delete the marker lines. In nano, Ctrl-K deletes a line. In VS Code, click Accept Current, Accept Incoming or Accept Both.
  2. git add <file> marks it resolved.
  3. git commit (no -m needed) concludes the merge. The default message lists the conflicted files.
Section 9 · GitHub and remote repositories

GitHub, accounts and remote repositories

Hosting services What is a Git hosting service

GitHub, Bitbucket and GitLab host remote copies of Git repositories. They give you a backup (delete your local copy and clone it again), collaboration with access control, code review and pull requests, and integrations such as CI systems. Public repositories can be read by anyone; private ones only by people you allow.

Account and personal access token Creating an account · personal access tokens

  • Your password works only for the GitHub website. For Git over HTTPS (push, and pull from private repositories) you need a personal access token.
  • Create one under Profile → Settings → Developer settings → Personal access tokens:
    • Classic token: tick the repo scope for full read and write access to your repositories.
    • Fine-grained token: limited to chosen repositories (up to 50) and specific permissions.
  • Always set an expiration (e.g. 90 days), not "no expiration". Copy the token immediately, because GitHub shows it only once. Paste it wherever Git or an app asks for a password.

A first repository on GitHub Exploring · another commit · new branch · changes

  • Naming: lowercase with dashes by convention (my-first-github-repository). Spaces become dashes.
  • Options: public or private; initialize with a README.md (recommended unless you're importing a repository); add .gitignore and a license.
  • Commits made on the website are marked Verified, signed with GitHub's key. You can edit files, create files (type folder/ in the name to make a folder), commit to the current branch, and comment on any commit.
  • History: "Browse the repository at this point" is like checking out an old commit. The diff view has unified and split modes.
  • New branch: create it from the branch dropdown. GitHub reports it as "even with master", then "1 commit ahead of master", and offers Compare & pull request.

Cloning your own repository Cloning · what is a remote

git clone https://github.com/mikegithubber/my-first-github-repository.git
cd my-first-github-repository       # folder named after the repo; you're on the default branch

A remote repository has the same structure as your local one. Nothing syncs by itself: you push your commits, and you fetch or pull other people's. GUIs can fetch periodically and tell you when there's something new. Writing needs permission; reading a public repository doesn't.

The point of one shared remote: with hundreds of collaborators, nobody sends changes to everyone else. Everyone pushes to and pulls from one place.

Section 10 · Git push, fetch and pull

Syncing local and remote

origin and remotes What is origin

git remote             # origin: the default name given when you clone
git remote -v          # origin  https://github.com/…/repo.git (fetch) and (push)

A repository can have several remotes with different names. Plain git pull and git push use the current branch's tracked remote, usually origin. A repository you created with git init has no remotes until you add one.

Remote and tracking branches Listing branches · tracking branch · checking out a remote branch

git branch          # local branches only
git branch -r       # remote: origin/master, origin/feature-1
git branch -a       # all: remotes/origin/HEAD -> origin/master …
git branch -vv      # local branches + the remote branch each one tracks
git checkout feature-1    # creates local feature-1 tracking origin/feature-1
  • git remote show origin gives the full picture: fetch and push URL, default (HEAD) branch, every remote branch (tracked, new or stale), what each local branch pulls from and pushes to, and whether each is up to date.
  • You can git branch -d an unmerged local branch if it still exists on the remote; Git warns but allows it.

Fetch, and cleaning up deleted remote branches git fetch in action · updating tracking status

git fetch -v                           # "* [new branch] temp -> origin/temp"; no local branch is created
# later the branch is deleted on GitHub …
git remote show origin                 # shows refs/remotes/origin/temp as stale
git remote prune origin                # or: git remote update origin --prune
git branch -vv                         # local temp now shows [origin/temp: gone]
git branch -D temp                     # -D needed: it was never merged

How git pull works Two-step process · how to pull · FETCH_HEAD

$ cat .git/FETCH_HEAD
ccc1f0…   branch 'feature-1' of https://github.com/…/repo     # current branch: this one gets merged
3c41ab…   not-for-merge  branch 'master' of https://github.com/…
  • Pull with only remote changes: a fast-forward. The local branch pointer jumps to the remote commit and the new file appears.
  • Doing it by hand: git fetch -v already creates the new commit, tree and blob objects in .git/objects, but your files don't change until git merge FETCH_HEAD. If both sides have commits, that's a 3-way merge with a merge commit.
  • Pull with a conflict works like any merge conflict. The incoming marker shows a commit hash instead of a branch name, because Git merged FETCH_HEAD. Resolve, then git commit -a.
  • After such merges, origin/feature-1 still points at the old remote commit until you push.

Pushing Pushing · another author · how branches sync

git push -v                                  # current tracking branch → its remote branch
git config user.name  "Mike Githubber"       # per-repository identity: overrides --global
git config user.email "mike.githubber@gmail.com"
  • Git asks for a username and a password (your token). Saved credentials can belong to another account. The course hits 403 Permission denied and fixes it by deleting the GitHub entry from macOS Keychain Access.
  • Commit authors can be anyone. GitHub accepts pushes of commits by any author, as long as you have write access.
  • Fully in sync means git pull and git push both say up to date, and origin/<branch> and the local branch point to the same commit. VS Code shows ↓0 ↑0 in the status bar.

Creating and deleting remote branches Remote branch from local · removing remotely · show-ref

git checkout -b feature-2
git push                              # fatal: The current branch feature-2 has no upstream branch
git push -u origin feature-2          # -u = --set-upstream: creates origin/feature-2 and tracks it
git push                              # from now on, plain push works

git push origin -d temp               # delete a branch on the remote
git show-ref feature-2                # local and remote hashes side by side

git show-ref prints refs/heads/… and refs/remotes/origin/…. Different hashes mean you have unpushed (or unpulled) commits.

Section 11 · Pull requests

Pull requests and code review

A pull request is a proposal of potential changes. It's a feature of GitHub, Bitbucket and GitLab, not of Git itself.

Why "pull request"? Collaboration · naming · PR vs merge request

  • Historically a developer pushed a branch and asked colleagues to pull it, try it and give feedback. GitHub kept the name and added comments, approvals, checks and merging.
  • GitLab calls it a merge request, which fits better inside one team: you want to merge into master.
  • "Pull request" fits better for forks: you ask the owner of another repository to pull your branch in.
  • Changes are "potential" because a pull request can be rejected and closed.

The workflow Pull request step by step

Opening a pull request New repo · amend author · push · open PR

git config user.name "Mike Githubber"; git config user.email "mike…@gmail.com"
git commit --amend --author="Mike Githubber <mike…@gmail.com>"   # fix the last commit's author
git push -u origin feature1                                       # Git prints a "create a pull request" link
  • Compare any two branches first: branch → Compare lists commits and file diffs, e.g. "3 commits ahead of master".
  • Compare & pull request shows "Able to merge" when there will be no conflicts. If there will be, resolve them first.
  • Title: start with the branch name in brackets, e.g. [feature1] First feature was implemented. It's easy to find, and tools like Jira can link it to the ticket with the same name.
  • Description: say clearly what changed (a Markdown list works well). The PR page has tabs for Conversation, Commits, Checks and Files changed.

Reviewing Comments and approval

  • Anyone can comment on a public repository's pull request. Hover a line in Files changed and click + to comment on it, or suggest a code change.
  • Add single comment notifies the author immediately. Start a review batches all your comments into one notification.
  • Review changes has three choices: Comment, Approve or Request changes.
  • Only people with write access can merge. Merge options: Create a merge commit (default, keeps all history), Squash and merge, Rebase and merge. The last two are covered in the Advanced course.

With GitHub Desktop Publish branch · sign in · create and merge

  • Check out master before creating a new branch; a new branch starts from whatever is checked out.
  • Publish branch does the same as git push -u. Create Pull Request needs you to be signed in under Preferences → Accounts.
  • After merging on GitHub, delete the branch there ("Restore branch" can undo that). Then Fetch origin and delete the local branch.

Collaborators and protected branches Collaborator · merging without approvals · protected branch

  • Settings → Collaborators → Add people: the invitee accepts by email and gets push access. They can then create branches, open pull requests and merge.
  • By default nothing stops anyone with write access from merging their own pull request with zero reviews.
  • Settings → Branches → Add rule for master:
    • Require pull request reviews before merging (choose 1–6 approvals). Direct commits to the branch are then blocked; work must come through pull requests.
    • Dismiss stale approvals when new commits are pushed, so a change made after approval needs a fresh approval. Recommended.
    • Optional: require review from Code Owners, require status checks to pass, require signed commits, include administrators.
  • After that, the merge button says "Merging is blocked" until approved. The repository admin still sees a red merge button and can override unless "include administrators" is set.

Real projects and issues Public pull requests · issues

  • Big projects (the course looks at Electron) show labels, required checks such as release notes, reactions, and thousands of closed pull requests.
  • Issues describe a bug, task or idea. They have labels (enhancement, a custom "work in progress"), assignees, and links to pull requests: mention #<number> or paste the issue link.
  • Close an issue when the fix is merged. Lock conversation lets only collaborators keep commenting. Pull requests can be assigned too.
Section 12 · Forks and contributing to public repositories

Forks, upstream and cross-repository pull requests

How to contribute to a repository you can't push to.

Keeping a fork in sync Syncing · adding upstream · fetching · synchronizing

git clone https://github.com/<you>/pull-requests.git && cd pull-requests
git remote add upstream https://github.com/<owner>/pull-requests.git
git remote -v                  # origin → your fork, upstream → parent
git fetch upstream -v          # upstream/* branches appear in git branch -a
git pull upstream master -v    # give remote and branch: master tracks origin, not upstream
git push                       # bring your fork on GitHub up to date
  • The pull is a fast-forward if your local master hasn't changed. Otherwise you get a 3-way merge, and maybe conflicts to resolve.
  • Equivalent two-step form: git fetch upstream, then git merge upstream/master.
  • Remote branch names with slashes become folders under .git/refs/remotes/upstream/.

Contributing with a pull request Plan · fork · commit · open · approve and merge

  1. Fork the parent repository. The copy says "forked from …" and you can now create branches and change settings in it.
  2. Create a uniquely named branch in your fork (e.g. feature5) and commit, on GitHub or locally plus push.
  3. New pull request → compare across forks. Set base repository / base branch to the parent's master, and head repository / compare to your fork and branch. Leave "Allow edits from maintainers" ticked.
  4. The pull request opens in the parent repository, not yours. It reads "bstashchuk wants to merge 2 commits into mikegithubber:master from bstashchuk:feature5". The owner is emailed, but you can't request reviewers.
  5. Branch protection still applies: an approval from someone with write access is needed, and only they can merge.
  6. After the merge, the owner can't delete your branch. You delete it in your fork, then sync your fork from upstream to get the merged result.

To find something to work on, browse Explore → Topics, open a project's Issues, and send a pull request that fixes one.

To give someone the same conditions as the public (no write access), remove them under Settings → Collaborators.
